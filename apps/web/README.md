# hacker_HP Web

React 19, TypeScript, Vite로 만든 프론트엔드 애플리케이션이다. MVP 화면은 전부 구현되어 있다 — 공개 랜딩, 개인정보처리방침, 로그인, 신청·대기, 공지 목록·상세·작성·수정, 회원 관리. `Post Launch`에서는 자료(시험·과목 정리본 목록, 상세, 등록·수정)와 즐겨찾기가 붙었다.

## UI 기반

shadcn/ui + Tailwind CSS를 쓴다 ([3-3 결정 10](../../spec/3-3-DESIGN-DECISIONS.md#3-3-11-결정-10--ui-기반으로-shadcnui--tailwind를-쓴다)). 컴포넌트는 `npx shadcn@latest add <이름>`으로 `src/components/ui/`에 복사해 쓰며, **그 화면을 만드는 이슈에서 필요한 것만** 추가한다.

색 토큰은 `src/index.css`에 있고 이름은 shadcn 규약(`--background`, `--foreground`, `--card`, `--border`, `--muted-foreground` …)을 그대로 쓴다. 컴포넌트들이 이 이름을 참조하므로 별도 이름 체계를 만들지 않는다. 값은 무채색뿐이며 유채색을 넣지 않는다.

**`:root`가 라이트(로그인 이후 화면), `.dark`가 다크(랜딩)다.** 랜딩은 최상위를 `.dark`로 감싸 팔레트를 뒤집어 쓴다.

폰트 Pretendard는 `index.html`에서 jsDelivr CDN으로 받으며 버전을 고정해 두었다. CDN이 실패하면 `--font-sans`의 시스템 폰트로 저하될 뿐 화면은 깨지지 않는다 — 외부 의존이므로 CSP를 걸 때 이 호스트를 빠뜨리지 않는다.

## 바깥에서 받은 것

**출처와 손대면 안 되는 이유를 파일 옆에 남긴다.** 활동사진은 `public/landing/README.md`에,
구글 G 로고는 `src/features/auth/GoogleLogo.tsx` 주석에 있다.

로고는 구글 배포본에서 **로고 부분만 그대로** 옮긴 것이라 색·비율을 고치지 않는다
(spec [3-1 §3-1-5](../../spec/3-1-DESIGN-ARCHITECTURE.md)). 왜 JSX가 아니라 마크업
문자열로 두었는지도 그 주석에 적혀 있다 — React가 `foreignObject` 안을 SVG 네임스페이스로
만들어 그라디언트가 칠해지지 않기 때문이다.

## 화면 폭과 여백

화면마다 폭을 새로 정하지 않는다. **아래 다섯 가지뿐이고 각각 이유가 있다.**

가르는 기준은 "글이냐 표냐"가 아니라 **글 길이를 우리가 아느냐**다.

| 종류 | 폭 | 화면 | 왜 |
|---|---|---|---|
| 우리가 쓴 긴 글 | `max-w-2xl` (672px) | 개인정보처리방침, 랜딩 소개·후원 | 길이를 우리가 정했고 처음부터 끝까지 순서대로 읽는 글이다. 한글은 전각이라 글자 폭이 폰트 크기와 비슷해서, 672px이면 16px 본문에서 42자·14px에서 48자다. 읽기 좋은 줄 길이(40~50자 안팎) 안에 든다 |
| 남이 쓴 글과 그 폼 | 제약 없음 (`<main>`의 1152px) | 공지 상세, 공지 작성·수정 | **길이도 형태도 우리가 모른다.** 실제 공지는 대부분 몇 줄이라 672px로 좁히면 글이 왼쪽에 쪼그라들고 오른쪽 480px이 빈 채 남는다 |
| 짧은 폼 | `mx-auto max-w-sm` (384px) | 신청·대기 | 입력이 두어 개뿐이라 넓힐 이유가 없다. 가운데 정렬해 화면을 오갈 때 좌우로 튀지 않게 한다 |
| 로그인 | `max-w-4xl` (896px) 두 카드 | 로그인 | **로그인만 예외다.** 왼쪽은 로고 자리, 오른쪽이 로그인 카드다 — 폼 하나가 아니라 두 장이라 짧은 폼 폭에 들어가지 않는다. 오른쪽 카드 안쪽은 여전히 짧은 폼이다. `lg` 미만에서는 왼쪽을 숨겨 오른쪽 카드만 남는다 |
| 표 | 제약 없음 (`<main>`의 1152px) | 공지 목록, 회원 관리, 자료 목록, 즐겨찾기 | 열이 많아 좁히면 잘리거나 줄바꿈이 생긴다 |

**공지 상세·작성·수정은 원래 읽기 폭이었다 (2026-08-11에 되돌림).** 근거는 줄 길이 계산이었다 — 1152px이면 한글이 한 줄에 82자까지 들어가 눈이 다음 줄 시작을 못 찾는다는 것. 계산 자체는 맞지만 **82자는 아주 긴 공지에서만 나오는 최악값**이었고, 대부분의 공지에서는 좁힌 쪽이 답답했다. 화면을 직접 보고 내린 판단이 계산보다 우선한다.

**공지 작성 폼이 상세와 같은 폭인 것은 의도다.** 거기서 쓴 본문이 상세에서 같은 폭으로 읽히므로, 폭이 다르면 작성자가 보는 줄바꿈과 독자가 보는 줄바꿈이 달라진다. 지금은 둘 다 1152px이다 — **한쪽만 고치면 어긋난다.**

### 상하 여백

**`AppLayout` 안이면 화면이 자기 상하 여백을 갖지 않는다.** `<main>`이 이미 `py-8`을 준다 — 화면에서 또 주면 겹친다.

**밖이면 갖는다.** 랜딩·개인정보처리방침·로그인은 헤더도 `<main>`도 없어 스스로 여백을 만든다. 로그인은 바깥 `p-6` + 카드 `p-8`(`sm:p-10`)이다.

### 폼 버튼

**가르는 기준은 "폼이냐"가 아니라 컨테이너 폭이다.**

| 컨테이너 | 배치 | 왜 |
|---|---|---|
| **좁은 카드** (카드 한 장이 폼 전부 — 로그인, 신청·대기) | **주 동작이 전체폭 하나**, 부수 동작은 그 아래 글자 버튼 | 400px 안팎의 카드에서 한쪽으로 밀면 버튼이 치우쳐 보인다. 로그인 카드의 구글 버튼이 이미 전체폭이라 같은 카드끼리 결이 맞는다 |
| **넓은 화면** (`<main>` 1152px — 공지 작성·수정, 자료 등록·수정) | **오른쪽 정렬**, `flex justify-end gap-2`에 `[취소] [저장]` | 1152px짜리 버튼은 우스워진다 |

**좁은 카드에서 버튼이 둘이면** 전체폭 둘을 세로로 쌓지 않는다 — 크기가 같아 취소가 저장만큼 중요해 보인다. 주 동작만 전체폭(`w-full`)으로 두고 부수 동작은 그 아래 `variant="ghost"` 글자 버튼으로 내린다. 폭은 채워 누를 자리를 넓게 준다. 로그인 카드가 구글 버튼 아래에 `← 동아리 소개로 돌아가기`를 두는 구조와 같다.

**넓은 화면에서 주 동작이 오른쪽 모서리인 이유**는 거기가 **시선과 커서가 끝나는 자리**이기 때문이다. 입력을 채우며 내려온 눈이 마지막으로 닿는 곳이고 마우스도 가장 짧게 움직인다. 정렬만 바꾸고 순서를 그대로 두면(`[저장] [취소]`가 오른쪽에) 취소가 모서리를 차지해 반대가 된다 — **둘은 한 쌍이라 같이 바꾼다.**

**확인 다이얼로그는 이 규칙 밖이다.** shadcn `AlertDialogFooter`가 자체 관례를 갖는다 — 넓으면 `sm:justify-end`에 `[취소] [삭제]`, 좁으면 `flex-col-reverse`로 **주 동작이 위**에 오게 쌓는다. 폭에 따라 스스로 바뀌므로 손대지 않는다.

**폼이 아닌 줄에도 적용하지 않는다.**

| 자리 | 배치 |
|---|---|
| 회원 관리 일괄 승인, 공지 상세 `수정`·`삭제` | 이미 오른쪽 끝 (`justify-between`) — 왼쪽에 설명·날짜를 두고 동작을 끝에 붙인 **툴바 줄**이다 |
| 헤더·랜딩 내비 | 왼쪽 (`flex gap-*`) |

### 푸터와 세로 정렬

**푸터는 화면 바닥에 붙는다.** `AppLayout`이 세로 flex(`min-h-screen flex-col`)이고 `<main>`이 `flex-1`이라, 내용이 짧아도 푸터가 맨 아래에 있고 길면 자연스럽게 아래로 밀린다. 푸터에 위쪽 여백을 줘서 가리던 방식은 걷었다 — 붙인 것이 아니라 덜 어색해 보이게 한 것이라 역할이 겹쳤다.

**세로 가운데는 `items-center`로 하지 않는다.** 자식이 화면보다 커지는 순간 위쪽이 컨테이너 밖으로 밀려나는데 그 영역은 `scrollHeight`에 잡히지 않아 **스크롤로 닿을 수 없다.** 대신 **자식에 `my-auto`**를 준다 — 남는 공간이 있으면 나눠 갖고 없으면 0이 되어 위에서 시작해 아래로 흐른다.

**가운데로 두는 화면은 정해져 있다.**

| 화면 | 정렬 | 왜 |
|---|---|---|
| 신청·대기, 로그인 | 세로 가운데 (`my-auto`) | 짧은 카드 하나가 전부고 길이가 거의 변하지 않는다 |
| 공지 목록·상세·작성·수정, 회원 관리, 자료 화면 전부 | 위에서 시작 | 가운데로 두면 **행 수나 글 길이에 따라 시작 위치가 위아래로 움직인다.** 목록은 첫 행이 늘 같은 자리에 있어야 하고, 공지 상세는 글마다 제목 위치가 달라지면 안 된다 |
| 랜딩, 개인정보처리방침 | 위에서 시작 | 원래 화면보다 긴 페이지라 가운데 정렬이 성립하지 않는다 |

## 요구 환경

- Node.js 24.15 이상
- npm 11 이상

## 실행

```bash
npm install
npm run dev
```

API base URL은 `/api/v1`로 고정되어 있다. 로컬에서는 `vite.config.ts`의 프록시가 `http://localhost:8080`으로 넘기므로 [`apps/api`](../api)를 함께 띄운다. 프록시 키는 `/api`라 `/api/v1`이 그대로 넘어간다.

## 백엔드 없이 실행하기

API 서버 없이 화면만 확인하려면 픽스처를 켠다.

```bash
cp .env.example .env.local
```

`.env.local`에서 `VITE_USE_FIXTURES=true`로 바꾸면 `src/api/` 함수들이 실제 요청 대신 더미 응답을 돌려준다. 기본값은 꺼짐이고, 꺼진 빌드에는 더미 값이 포함되지 않는다.

`VITE_FIXTURE_SCENARIO`로 어떤 사용자·실패 상황을 볼지 고른다.

| 값 | 상황 |
|---|---|
| `user` (기본) | ACTIVE / USER — 관리자 라우트가 막힌다 |
| `admin` | ACTIVE / ADMIN — 관리자 라우트가 열린다 |
| `applying` | PENDING, **신청서 제출 전** — 구글 로그인만 마친 상태. 학번이 비어 있다 |
| `pending` | PENDING, **신청서 제출 후** — 승인 대기 |
| `guest` | 세션 없음 — 보호 라우트가 로그인 화면으로 간다 |
| `blocked` | 세션은 있으나 서버가 403 `PENDING_APPROVAL`로 차단 |

`applying`과 `pending`을 나눈 것은 화면이 신청 폼과 대기 안내를 갈라야 하기 때문이다
(spec §3-1-4 — 승인 대상은 신청서를 낸 계정으로 한정된다).

회원 관리도 픽스처가 받는다. 명부에 **신청서를 내지 않은 PENDING**과 활성 관리자 여럿을
섞어 두었다 — 그런 계정이 없으면 "승인 대상이 아니다"와 "마지막 관리자는 자기를 정지할 수
없다"를 화면에서 확인할 수가 없다. 검색·필터·정렬·페이지네이션도 실제로 동작한다.

자료·즐겨찾기도 픽스처가 받는다. 자료 23건에 **업로더를 섞어 두었다** — 본인 것, 남의 것,
탈퇴한 회원의 것. 그래야 "본인 자료에만 수정·삭제 진입점이 보인다"를 화면에서 확인할 수 있다
(하나로 통일하면 그 분기가 늘 참이거나 늘 거짓이라 아무것도 못 잡는다). 과목·교수·연도도
흩어 두어 필터가 실제로 걸러낸다.

**업로드는 픽스처에서도 세 단계를 그대로 밟는다** — 발급 → PUT → 등록. 다만 발급된 주소는
`blob:`이라 진짜 S3로 나가지 않는다. 확장자·용량·개수는 픽스처도 서버처럼 거부한다
(`415`·`413`·`400`) — 통과시키면 그 오류 화면을 만들 수 없다.

**내려받기는 빈 파일을 준다.** 픽스처에는 진짜 파일이 없어서, 받기를 누르면 내용 없는
`blob:`이 열린다. 실제 파일 확인은 서버를 띄우고 해야 한다.

공지 쓰기(등록·수정·삭제·고정)도 픽스처가 받는다. **저장한 값이 메모리에 남아** 목록 →
작성 → 상세 → 수정 왕복을 그대로 확인할 수 있고, 새로고침하면 초기값으로 돌아간다.
권한(ADMIN)과 필수값·제목 200자 검사도 픽스처가 서버처럼 거부한다 — 통과시키면 오류
화면을 만들 수 없다. 쓰기를 보려면 `VITE_FIXTURE_SCENARIO=admin`으로 둔다.

**픽스처는 임시다.** [`src/api/fixtures.ts`](src/api/fixtures.ts)는 백엔드가 붙으면 통째로 지운다.
같이 지울 곳은 아래로 찾는다 — 파일 목록을 문서에 적으면 픽스처를 쓰는 파일이 늘 때마다 낡고,
낡은 목록대로 지우면 남은 import 때문에 빌드가 깨진다.

```sh
# apps/web에서 실행한다 (저장소 루트가 아니다)
rg -il "fixture" . --hidden
```

`fixture`라는 낱말 하나만 대소문자 없이 찾는다. `VITE_USE_FIXTURES`·`VITE_FIXTURE_SCENARIO`·
픽스처 파일 자체·정적 import·동적 `import('./fixtures')`·이 문서의 안내가 전부 그 낱말을
지나가므로, 패턴을 늘리지 않아도 새 참조가 걸린다. `--hidden`이 없으면 `.env.example`이 빠진다.
gitignore된 각자의 `.env.local`은 검색에 안 잡히니 따로 지운다.

## 배포

[`vercel.json`](vercel.json)에 rewrite가 두 개 있다. `/api/*`를 `api.khuhacker.com`으로 넘기는 프록시([docs/ops/deployment.md](../../docs/ops/deployment.md))와 SPA fallback이다. fallback은 `BrowserRouter`를 쓰기 때문에 필요하다 — 없으면 `/notices` 같은 경로를 새로고침할 때 404가 난다.

**순서를 바꾸면 안 된다.** Vercel은 위에서부터 첫 번째로 맞는 규칙을 적용하므로 `/api/*`가 SPA fallback **위에** 있어야 한다. 아래로 내려가면 fallback이 API 요청까지 `/index.html`로 삼켜 로그인이 되지 않는다.
