# 3-1. 인증 / 권한 아키텍처

**권한과 관련된 작업(새 API 추가, 화면 접근 제한 등)을 하기 전에 이 문서를 먼저 읽는다** (MUST). `@PreAuthorize`와 프론트엔드 라우트 가드는 §3-1-3 매트릭스와 반드시 일치해야 한다.

```text
§3-1-1   Role            권한 등급
§3-1-2   Status          계정 상태 — Role과 분리한다
§3-1-3   권한 매트릭스    이 표가 원본이다
§3-1-4   가입 신청       AUTH-01
§3-1-5   로그인·로그아웃  AUTH-02, AUTH-03
§3-1-6   대기중 안내      AUTH-04
§3-1-7   서버 재검증 원칙  UI 숨김은 권한이 아니다
```

## 3-1-1 Role

| Role | 설명 |
|---|---|
| `USER` | 일반 동아리원 |
| `ADMIN` | 관리자 |

## 3-1-2 Status

**Role과 Status는 분리하여 관리한다** (MUST). 가입 대기와 정지는 권한이 아니라 계정 상태다. 둘을 하나의 enum으로 합치면 "정지된 관리자" 같은 조합을 표현할 수 없다.

| Status | 설명 | 로그인 | 접근 가능 범위 |
|---|---|---|---|
| `PENDING` | 구글 로그인은 마쳤고 아직 승인되지 않음 | 가능 | 신청·대기 화면만 (공개 랜딩 제외) |
| `ACTIVE` | 정상 이용 | 가능 | 권한에 따른 전체 기능 |
| `SUSPENDED` | 관리자에 의한 이용 정지 | **차단** | 없음 (정지 안내 표시) |

**`PENDING`은 신청 전과 신청 후를 모두 포함한다.** 첫 구글 로그인만 마친 계정도 `PENDING`이다 (§3-1-4). 두 경우의 **접근 권한이 같으므로** — 둘 다 신청·대기 화면만 볼 수 있다 — Status를 나누지 않는다. 신청 여부는 권한이 아니라 데이터이며 `applied_at`으로 구분한다 ([3-2 §3-2-2](3-2-DESIGN-CONTRACT.md)).

| PENDING의 두 모습 | 구분 | 보는 화면 |
|---|---|---|
| 신청 전 | `applied_at IS NULL` | 신청 폼 |
| 신청 후 | `applied_at IS NOT NULL` | 승인 대기 안내 |

**신청 API는 `PENDING` 전체에 열려 있어야 한다** (MUST). 신청 전 계정을 차단하면 아무도 신청서를 낼 수 없다.

"접근 가능 범위"는 **인증이 필요한 화면**을 말한다. 공개 랜딩은 인증 영역 밖이라 어떤 상태에서도 열려 있다 (§3-1-3).

가입 **거부** 시에는 별도 상태를 두지 않고 계정 레코드를 삭제한다. 거부된 사용자는 재신청할 수 있다.

## 3-1-3 권한 매트릭스

| 기능 | 비로그인 | PENDING | USER (ACTIVE) | ADMIN (ACTIVE) |
|---|:---:|:---:|:---:|:---:|
| 랜딩 조회 | O | O | O | O |
| 구글 로그인 (가입 겸용) | O | O | O | O |
| 로그아웃 | - | O | O | O |
| CSRF 토큰 발급 | O | O | O | O |
| 신청서 제출·수정 | X | O | X | X |
| 신청·대기 화면 | - | O | - | - |
| 자료 목록·검색·다운로드 | X | X | O | O |
| 자료 업로드 | X | X | O | O |
| 자료 수정·삭제 | X | X | 본인 것만 | 전체 |
| 즐겨찾기 | X | X | O | O |
| 공지 조회 | X | X | O | O |
| 공지 등록·수정·삭제·고정 | X | X | X | O |
| 활동사진 조회 | X | X | O | O |
| 활동사진 업로드·삭제 | X | X | X | O |
| 회원 관리 | X | X | X | O |

랜딩은 인증 영역 밖의 공개 페이지라 Role·Status와 무관하게 열려 있고, 정적이라 **랜딩 콘텐츠를 가져오는 API를 호출하지 않는다** ([3-3 결정 8](3-3-DESIGN-DECISIONS.md#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다)). 랜딩을 열 때 나가는 `GET /auth/me`는 앱 셸이 경로와 무관하게 하는 세션 확인이지 랜딩의 요청이 아니다 (같은 결정의 2026-08-10 경계 명확화, [5-TESTING T-60](5-TESTING.md#5-2-프론트엔드-테스트)). 나머지 행은 모두 인증이 필요한 기능이며, 라우트 가드와 `@PreAuthorize`가 일치시켜야 할 대상도 그쪽이다.

**이 표에 없는 조합이 필요하면 추측하지 말고 먼저 확인한다** (MUST). 표를 늘리는 것이 결정이고, 코드에서 임의로 정하는 것은 결정이 아니다.

## 3-1-4 AUTH-01 가입 신청

**가입과 로그인은 구글 OAuth 하나로 처리한다** ([3-3 결정 13](3-3-DESIGN-DECISIONS.md#3-3-14-결정-13--가입로그인을-구글-oauth로-한다)). 자체 비밀번호를 받지도, 저장하지도 않는다 (MUST).

전체 흐름은 네 단계다.

```text
① 구글 로그인   →  ② 신청서 제출  →  ③ 관리자 승인  →  ④ 이용 가능
   계정 생성          학번·이름          PENDING → ACTIVE
   USER / PENDING
```

**① 구글 로그인 — 계정이 없으면 만든다**

- 허용 도메인은 **`khu.ac.kr`** 이다 (MUST). 설정 키 **`app.auth.allowed-email-domain`** 으로 주입하며 코드에 하드코딩하지 않는다. 값이 없으면 기동에 실패시킨다 (MUST) — 코드에 기본값을 심어두면 설정 누락이 조용히 지나가 도메인 제한이 무력해진다. 주입 방법은 [docs/ops/infra.md](../docs/ops/infra.md)에 있다.
- **도메인 검증은 서버가 한다** (MUST). 구글의 `hd` 파라미터는 로그인 화면에서 계정을 좁혀주는 힌트일 뿐 위조를 막지 못하므로, 서버가 ID 토큰의 `email`과 `email_verified`를 직접 확인한다.
- **`@` 뒤 도메인을 잘라내 설정값과 정확히 일치하는지 본다** (MUST). `endsWith`로 검사하면 `user@notkhu.ac.kr`이 통과한다. 하위 도메인(`user@cs.khu.ac.kr`)도 정확 일치가 아니므로 거부한다 — 필요해지면 허용 목록을 늘리는 것이 결정이고, 접미사 검사로 흘리는 것은 결정이 아니다.
- 도메인이 다르거나 `email_verified`가 거짓이면 계정을 만들지 않고 로그인을 거부한다 (`403 FORBIDDEN`).
- 처음 로그인한 계정은 `USER` / `PENDING`으로 생성된다. 이름은 구글 프로필에서 받아 채운다.
- 같은 구글 계정으로 다시 로그인하면 새 계정을 만들지 않고 기존 계정에 붙는다. 그래서 이메일 중복이라는 상황 자체가 생기지 않는다.

**② 신청서 제출 — 승인 심사에 필요한 정보를 받는다**

- 구글은 학번을 주지 않는다. 그래서 로그인 직후 계정에는 학번이 비어 있다.
- `PENDING` 사용자는 신청 화면에서 **학번과 이름**을 제출한다 (§3-1-6).
- 제출 시각을 기록한다. **승인 대상은 신청서를 낸 `PENDING` 계정으로 한정한다** (MUST) — 구글 로그인만 해보고 신청하지 않은 계정이 관리자의 승인 목록에 섞이면 운영이 어려워진다.
- 학번이 이미 다른 계정에 쓰이고 있으면 거부한다 (`409 DUPLICATE_STUDENT_NO`). 한 학번으로 여러 계정을 만드는 것을 막는다.
- 승인 전까지는 다시 제출해 고칠 수 있다.
- **신청서 저장은 승인과 직렬화한다** (MUST). `WHERE status = 'PENDING'` 조건부 갱신이나 행 잠금을 쓴다. 권한 검사만 통과시키고 저장을 나중에 하면, 그 사이 관리자가 승인해 `ACTIVE`가 된 계정의 학번·이름이 승인 뒤에 바뀐다 — 관리자가 심사한 내용과 저장된 내용이 달라진다.

**③ 관리자 승인 → ④ 이용 가능**

- 관리자가 승인하면 `PENDING` → `ACTIVE`가 되고 승인일시가 기록된다 ([2-2 §2-2-2](2-2-OPERATOR-REQUIREMENTS.md)).
- 승인은 기존 세션에 즉시 반영된다 (§3-1-5). 재로그인 없이 바로 이용할 수 있다.

> **인증 수단 결정** — 학번은 동아리 안에서 서로 알고 있는 값이므로 인증에 쓰지 않는다. 신원 확인(승인 심사)용으로만 저장한다. 신원 증명은 구글이 담당한다.

## 3-1-5 AUTH-02 로그인 / AUTH-03 로그아웃

- 로그인 수단은 **구글 OAuth 하나**다 (MUST). 비밀번호 입력란이 없다.
- 이미 계정이 있으면 그 계정으로, 없으면 만들면서 로그인한다 (§3-1-4). 화면상 "로그인"과 "가입"이 같은 버튼이다.
- 도메인·`email_verified` 검증은 매 로그인마다 수행한다 (MUST). 최초 가입 때 한 번만 확인하고 넘어가지 않는다.

Status별 처리:

| Status | 결과 |
|---|---|
| `ACTIVE` | 정상 로그인 |
| `PENDING` | 로그인은 허용하되 신청·대기 화면으로 강제 이동 |
| `SUSPENDED` | 로그인 차단. 세션을 발급하지 않고 로그인 화면으로 되돌린다 ([3-2 §3-2-3](3-2-DESIGN-CONTRACT.md) 콜백 리다이렉트) |

### 정지 안내는 로그인 화면이 띄운다 — 도달 경로가 둘이다

정지된 사람이 로그인 화면에 도착하는 길은 두 가지이고, **둘 다 같은 안내를 봐야 한다** (MUST).

| 경로 | 어떻게 도착하나 | 주소 |
|---|---|---|
| ① 로그인 시도가 막힘 | 서버가 세션을 발급하지 않고 되돌린다 ([3-2 §3-2-3](3-2-DESIGN-CONTRACT.md) 콜백 표) | `/login?error=suspended` |
| ② 이용 중 정지됨 | 관리자가 정지시킨 뒤([2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md) MUST) 다음 API 호출이 `403 SUSPENDED`로 막히고, 세션이 정지로 정리되어 라우트 가드가 로그인 화면으로 보낸다 | `/login` (쿼리 없음) |

**경로 ①이 안전망이다.** ②가 어떤 이유로 실패해도 — 서버가 세션을 지워 `401`이 오거나, 클라이언트가 코드를 놓치거나 — 사용자가 로그인을 다시 시도하면 콜백이 `?error=suspended`를 준다. 안내가 영영 안 뜨는 것은 아니다. 그래서 ②를 위해 과하게 설계할 필요는 없다.

**②가 막는 것은 그 한 번이다.** ②가 없으면 관리자가 정지시킨 직후 사용자는 **아무 설명 없는 로그인 화면으로 한 번 튕긴다.** 이유를 알려면 스스로 로그인을 다시 눌러 봐야 하고, 그 전까지는 무엇이 잘못됐는지 알 수 없다. 그래서 화면은 `?error=suspended`뿐 아니라 **세션이 정지 상태인 것만으로도** 안내를 띄운다.

**두 경로의 안내 문구는 같다** (MUST). 사용자에게는 같은 사실 — "이 계정은 정지되어 이용할 수 없다" — 이고, 도달 경로는 사용자가 알 필요도 구별할 수도 없는 내부 사정이다. 다르게 쓰면 왜 다른지 설명할 수 없고 한쪽만 고쳐지는 자리가 된다.

### 로그인 상태 유지 방식

**신원 증명은 JWT, 인가 상태는 서버 세션이 담당한다** ([3-3 결정 12](3-3-DESIGN-DECISIONS.md#3-3-13-결정-12--인증은-jwt-인가-상태는-서버-세션으로-나눈다)).

| 담당 | 수단 | 저장 위치 |
|---|---|---|
| 이 요청이 **누구인지** | JWT (`sub`만) | `httpOnly` 쿠키 |
| 그 사람이 **지금 무엇을 할 수 있는지** (`role`, `status`) | 서버 세션 | RDS |

- JWT에 `role`과 `status`를 담지 않는다 (MUST). 담으면 정지·승인이 토큰 만료까지 반영되지 않아 §3-1-2와 [2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md)을 어긴다.
- **세션이 없으면 인증이 성립하지 않는다** (MUST). 서명이 유효한 JWT만으로는 통과하지 못한다.
- **세션과 JWT가 같은 사용자의 것인지 매 요청 확인한다** (MUST). 세션에 사용자 id를 저장하고 JWT의 `sub`와 대조해, 다르면 인증 실패로 처리하고 양쪽 쿠키를 폐기한다. 이 검증이 없으면 A의 JWT와 B의 세션을 함께 보내 A의 신원으로 B의 권한을 쓰는 조합이 성립한다.
- 토큰은 `httpOnly` 쿠키로만 주고받는다. `localStorage`에 저장하지 않는다 (MUST).
- **인증 쿠키에는 `Secure`를 붙인다** (MUST). `SameSite=Lax`는 교차 사이트 요청만 제한할 뿐 평문 HTTP 전송을 막지 못하므로 별개로 지정한다. 로컬 개발(HTTP)만 설정으로 예외를 둔다.
- 쿠키가 자동 전송되므로 **상태를 바꾸는 요청은 CSRF 토큰을 검증한다** (MUST). 쿠키·헤더 이름과 발급 경로는 [3-2 §3-2-3](3-2-DESIGN-CONTRACT.md)에 있다.
- 세션은 RDS에 저장한다 (MUST). ECS 태스크가 Fargate Spot이라 메모리에 두면 회수 시 전원 로그아웃된다.

**로그아웃은 세션을 지우는 것으로 성립한다** (MUST). 세션이 사라지면 쿠키에 남은 JWT는 더 이상 인증에 쓰이지 못한다. 이후 로그인 화면으로 이동한다.

### 상태 변경을 기존 세션에 반영한다

`role`이나 `status`가 세션에 들어 있으므로, 관리자가 값을 바꾸면 **그 회원의 기존 세션에도 즉시 반영해야 한다** (MUST). 어느 쪽이든 **다음 요청부터 새 값이 적용되어야 한다.**

**정지는 세션을 지우지 않고 `status`를 갱신한다** (MUST). 세션을 지우면 다음 요청이 `401 UNAUTHENTICATED`가 되어([5-TESTING T-30](5-TESTING.md#5-2-필수-테스트-사례)) 클라이언트가 정지인지 단순 만료인지 구별하지 못하고, **정지 직후의 그 화면에서** 안내를 띄울 수 없다 (§3-1-5의 경로 ②, [3-3 결정 12의 2026-08-11 노트](3-3-DESIGN-DECISIONS.md#3-3-13-결정-12--인증은-jwt-인가-상태는-서버-세션으로-나눈다)). 승인·권한 변경은 갱신과 무효화 중 무엇을 써도 된다 — 그쪽은 결과를 사용자에게 설명할 필요가 없다.

| 작업 | 반영되지 않으면 |
|---|---|
| 정지 (`ACTIVE` → `SUSPENDED`) | 정지된 회원이 계속 이용한다 — [2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md) 위반 |
| **승인 (`PENDING` → `ACTIVE`)** | 승인된 회원이 세션 만료까지 `403 PENDING_APPROVAL`에 갇힌다 — §3-1-6 위반 |
| 권한 변경 (`USER` ↔ `ADMIN`) | 회수된 관리자 권한이 계속 살아 있다 |

승인은 일괄 처리이므로([2-2 §2-2-2](2-2-OPERATOR-REQUIREMENTS.md)) 선택된 회원 전원의 세션을 함께 처리한다.

## 3-1-6 AUTH-04 신청·대기 화면

- **인증이 필요한 화면 중** `PENDING` 사용자가 접근 가능한 **유일한** 화면이다 (MUST). 공개 랜딩은 인증 영역 밖이라 이 제한의 대상이 아니다 (§3-1-2, §3-1-3).
- 신청서를 냈는지에 따라 한 화면이 두 모습을 가진다.

| 상태 | 화면 |
|---|---|
| 신청 전 (`applied_at IS NULL`) | 학번·이름을 입력하는 **신청 폼** |
| 신청 후 (`applied_at` 있음) | 승인 대기 중임을 알리는 **안내**. 승인 전까지 신청 내용을 고칠 수 있다 |
| **신청 여부를 모름** | 폼도 안내도 띄우지 않는다 — 아래 참조 |

- 두 경우 모두 로그아웃 버튼을 제공한다.

**신청 여부를 모르는 상태가 실제로 존재한다** (MUST). 클라이언트가 `PENDING`임을 `403 PENDING_APPROVAL`로만 알아낸 경우다 — 보호 API가 그 코드로 막으면 세션은 "대기 중"이라는 것만 알고 `applied_at`은 모른다. **이때 기본값으로 폼을 띄우면 이미 신청한 사람이 다시 쓰게 된다.** 화면은 `GET /auth/me`를 다시 불러 신청 여부를 확인한 뒤에 무엇을 보일지 정하고, 그 사이에는 어느 쪽도 띄우지 않는다.

**승인은 이 화면에 저절로 반영되지 않는다.** 서버는 승인을 기존 세션에 즉시 반영하지만(§3-1-5), 대기 화면은 이미 그려져 있어 스스로 알지 못한다. 그래서 **"다시 확인" 버튼을 둔다** (MUST) — 누르면 `GET /auth/me`를 다시 불러 `ACTIVE`가 되었으면 그때 화면이 풀린다.

**자동 폴링은 하지 않는다.** 승인은 몇 분에서 며칠이 걸리는 일이라, 대기자 전원이 주기적으로 요청을 보내는 비용을 계속 낼 이유가 없다. 필요해지면 그때 결정으로 올린다.

**다만 화면이 "저절로 바뀌지 않는다"는 것을 사용자에게 알려야 한다** (MUST). 버튼만 두고 설명이 없으면 누를 이유를 모르고, 승인된 뒤에도 대기 화면에 머문다.
- 인증 API와 신청 API 외의 모든 API 호출은 `403 PENDING_APPROVAL`로 차단한다 (MUST). 프론트엔드는 이 코드를 감지해 이 화면으로 리다이렉트한다.
- 신청 API는 `PENDING` 전용이다. `ACTIVE`가 된 뒤에는 이 경로로 학번을 바꿀 수 없다 (MUST). 거부 코드는 `403 FORBIDDEN`이다 ([3-2 §3-2-7](3-2-DESIGN-CONTRACT.md), [5-TESTING T-50](5-TESTING.md#5-2-필수-테스트-사례)) — 코드가 정해져 있지 않으면 화면이 무엇을 보여줄지 정할 수 없다.

## 3-1-7 서버 재검증 원칙

- **모든 관리자 API는 서버 측에서 권한을 재검증한다** (MUST). UI 숨김만으로 권한을 통제하지 않는다.
- 본인이 마지막 남은 활성 관리자일 때는 본인 권한 회수·계정 삭제·본인 정지를 서버에서 차단한다 (MUST) — [2-2 §2-2-7](2-2-OPERATOR-REQUIREMENTS.md).
- 자료 수정·삭제의 "본인 것만" 조건도 서버에서 소유자를 확인한다 (MUST).
