# 3-1. 인증 / 권한 아키텍처

**권한과 관련된 작업(새 API 추가, 화면 접근 제한 등)을 하기 전에 이 문서를 먼저 읽는다** (MUST). `@PreAuthorize`와 프론트엔드 라우트 가드는 §3-1-3 매트릭스와 반드시 일치해야 한다.

```text
§3-1-1   Role            권한 등급
§3-1-2   Status          계정 상태 — Role과 분리한다
§3-1-3   권한 매트릭스    이 표가 원본이다
§3-1-4   가입 신청       AUTH-01
§3-1-5   로그인·로그아웃  AUTH-02, AUTH-03
§3-1-6   대기중 안내      AUTH-04
§3-1-7   서버 재검증 원칙  UI 숨김은 권한이 아니다
```

## 3-1-1 Role

| Role | 설명 |
|---|---|
| `USER` | 일반 동아리원 |
| `ADMIN` | 관리자 |

## 3-1-2 Status

**Role과 Status는 분리하여 관리한다** (MUST). 가입 대기와 정지는 권한이 아니라 계정 상태다. 둘을 하나의 enum으로 합치면 "정지된 관리자" 같은 조합을 표현할 수 없다.

| Status | 설명 | 로그인 | 접근 가능 범위 |
|---|---|---|---|
| `PENDING` | 가입 신청 후 승인 대기 | 가능 | 대기중 안내 화면만 (공개 랜딩 제외) |
| `ACTIVE` | 정상 이용 | 가능 | 권한에 따른 전체 기능 |
| `SUSPENDED` | 관리자에 의한 이용 정지 | **차단** | 없음 (정지 안내 표시) |

"접근 가능 범위"는 **인증이 필요한 화면**을 말한다. 공개 랜딩은 인증 영역 밖이라 어떤 상태에서도 열려 있다 (§3-1-3).

가입 **거부** 시에는 별도 상태를 두지 않고 계정 레코드를 삭제한다. 거부된 사용자는 재신청할 수 있다.

## 3-1-3 권한 매트릭스

| 기능 | 비로그인 | PENDING | USER (ACTIVE) | ADMIN (ACTIVE) |
|---|:---:|:---:|:---:|:---:|
| 랜딩 조회 | O | O | O | O |
| 구글 로그인 (가입 겸용) | O | O | O | O |
| 로그아웃 | - | O | O | O |
| CSRF 토큰 발급 | O | O | O | O |
| 신청서 제출·수정 | X | O | X | X |
| 신청·대기 화면 | - | O | - | - |
| 자료 목록·검색·다운로드 | X | X | O | O |
| 자료 업로드 | X | X | O | O |
| 자료 수정·삭제 | X | X | 본인 것만 | 전체 |
| 즐겨찾기 | X | X | O | O |
| 공지 조회 | X | X | O | O |
| 공지 등록·수정·삭제·고정 | X | X | X | O |
| 활동사진 조회 | X | X | O | O |
| 활동사진 업로드·삭제 | X | X | X | O |
| 회원 관리 | X | X | X | O |

랜딩은 인증 영역 밖의 공개 페이지라 Role·Status와 무관하게 열려 있고, 정적이라 API를 호출하지 않는다 ([3-3 결정 8](3-3-DESIGN-DECISIONS.md#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다)). 나머지 행은 모두 인증이 필요한 기능이며, 라우트 가드와 `@PreAuthorize`가 일치시켜야 할 대상도 그쪽이다.

**이 표에 없는 조합이 필요하면 추측하지 말고 먼저 확인한다** (MUST). 표를 늘리는 것이 결정이고, 코드에서 임의로 정하는 것은 결정이 아니다.

## 3-1-4 AUTH-01 가입 신청

**가입과 로그인은 구글 OAuth 하나로 처리한다** ([3-3 결정 13](3-3-DESIGN-DECISIONS.md#3-3-14-결정-13--가입로그인을-구글-oauth로-한다)). 자체 비밀번호를 받지도, 저장하지도 않는다 (MUST).

전체 흐름은 네 단계다.

```text
① 구글 로그인   →  ② 신청서 제출  →  ③ 관리자 승인  →  ④ 이용 가능
   계정 생성          학번·이름          PENDING → ACTIVE
   USER / PENDING
```

**① 구글 로그인 — 계정이 없으면 만든다**

- 허용 도메인은 **`khu.ac.kr`** 이다 (MUST). 설정값으로 관리하며 코드에 하드코딩하지 않는다.
- **도메인 검증은 서버가 한다** (MUST). 구글의 `hd` 파라미터는 로그인 화면에서 계정을 좁혀주는 힌트일 뿐 위조를 막지 못하므로, 서버가 ID 토큰의 `email`과 `email_verified`를 직접 확인한다.
- 도메인이 다르거나 `email_verified`가 거짓이면 계정을 만들지 않고 로그인을 거부한다 (`403 FORBIDDEN`).
- 처음 로그인한 계정은 `USER` / `PENDING`으로 생성된다. 이름은 구글 프로필에서 받아 채운다.
- 같은 구글 계정으로 다시 로그인하면 새 계정을 만들지 않고 기존 계정에 붙는다. 그래서 이메일 중복이라는 상황 자체가 생기지 않는다.

**② 신청서 제출 — 승인 심사에 필요한 정보를 받는다**

- 구글은 학번을 주지 않는다. 그래서 로그인 직후 계정에는 학번이 비어 있다.
- `PENDING` 사용자는 신청 화면에서 **학번과 이름**을 제출한다 (§3-1-6).
- 제출 시각을 기록한다. **승인 대상은 신청서를 낸 `PENDING` 계정으로 한정한다** (MUST) — 구글 로그인만 해보고 신청하지 않은 계정이 관리자의 승인 목록에 섞이면 운영이 어려워진다.
- 학번이 이미 다른 계정에 쓰이고 있으면 거부한다 (`409 DUPLICATE_STUDENT_NO`). 한 학번으로 여러 계정을 만드는 것을 막는다.
- 승인 전까지는 다시 제출해 고칠 수 있다.

**③ 관리자 승인 → ④ 이용 가능**

- 관리자가 승인하면 `PENDING` → `ACTIVE`가 되고 승인일시가 기록된다 ([2-2 §2-2-2](2-2-OPERATOR-REQUIREMENTS.md)).
- 승인은 기존 세션에 즉시 반영된다 (§3-1-5). 재로그인 없이 바로 이용할 수 있다.

> **인증 수단 결정** — 학번은 동아리 안에서 서로 알고 있는 값이므로 인증에 쓰지 않는다. 신원 확인(승인 심사)용으로만 저장한다. 신원 증명은 구글이 담당한다.

## 3-1-5 AUTH-02 로그인 / AUTH-03 로그아웃

- 로그인 수단은 **구글 OAuth 하나**다 (MUST). 비밀번호 입력란이 없다.
- 이미 계정이 있으면 그 계정으로, 없으면 만들면서 로그인한다 (§3-1-4). 화면상 "로그인"과 "가입"이 같은 버튼이다.
- 도메인·`email_verified` 검증은 매 로그인마다 수행한다 (MUST). 최초 가입 때 한 번만 확인하고 넘어가지 않는다.

Status별 처리:

| Status | 결과 |
|---|---|
| `ACTIVE` | 정상 로그인 |
| `PENDING` | 로그인은 허용하되 신청·대기 화면으로 강제 이동 |
| `SUSPENDED` | 로그인 차단, `403 SUSPENDED` |

### 로그인 상태 유지 방식

**신원 증명은 JWT, 인가 상태는 서버 세션이 담당한다** ([3-3 결정 12](3-3-DESIGN-DECISIONS.md#3-3-13-결정-12--인증은-jwt-인가-상태는-서버-세션으로-나눈다)).

| 담당 | 수단 | 저장 위치 |
|---|---|---|
| 이 요청이 **누구인지** | JWT (`sub`만) | `httpOnly` 쿠키 |
| 그 사람이 **지금 무엇을 할 수 있는지** (`role`, `status`) | 서버 세션 | RDS |

- JWT에 `role`과 `status`를 담지 않는다 (MUST). 담으면 정지·승인이 토큰 만료까지 반영되지 않아 §3-1-2와 [2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md)을 어긴다.
- **세션이 없으면 인증이 성립하지 않는다** (MUST). 서명이 유효한 JWT만으로는 통과하지 못한다.
- **세션과 JWT가 같은 사용자의 것인지 매 요청 확인한다** (MUST). 세션에 사용자 id를 저장하고 JWT의 `sub`와 대조해, 다르면 인증 실패로 처리하고 양쪽 쿠키를 폐기한다. 이 검증이 없으면 A의 JWT와 B의 세션을 함께 보내 A의 신원으로 B의 권한을 쓰는 조합이 성립한다.
- 토큰은 `httpOnly` 쿠키로만 주고받는다. `localStorage`에 저장하지 않는다 (MUST).
- **인증 쿠키에는 `Secure`를 붙인다** (MUST). `SameSite=Lax`는 교차 사이트 요청만 제한할 뿐 평문 HTTP 전송을 막지 못하므로 별개로 지정한다. 로컬 개발(HTTP)만 설정으로 예외를 둔다.
- 쿠키가 자동 전송되므로 **상태를 바꾸는 요청은 CSRF 토큰을 검증한다** (MUST). 쿠키·헤더 이름과 발급 경로는 [3-2 §3-2-3](3-2-DESIGN-CONTRACT.md)에 있다.
- 세션은 RDS에 저장한다 (MUST). ECS 태스크가 Fargate Spot이라 메모리에 두면 회수 시 전원 로그아웃된다.

**로그아웃은 세션을 지우는 것으로 성립한다** (MUST). 세션이 사라지면 쿠키에 남은 JWT는 더 이상 인증에 쓰이지 못한다. 이후 로그인 화면으로 이동한다.

### 상태 변경을 기존 세션에 반영한다

`role`이나 `status`가 세션에 들어 있으므로, 관리자가 값을 바꾸면 **그 회원의 기존 세션에도 즉시 반영해야 한다** (MUST). 세션 속성을 갱신하든 세션을 무효화해 재로그인시키든 방식은 구현이 고른다. 어느 쪽이든 **다음 요청부터 새 값이 적용되어야 한다.**

| 작업 | 반영되지 않으면 |
|---|---|
| 정지 (`ACTIVE` → `SUSPENDED`) | 정지된 회원이 계속 이용한다 — [2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md) 위반 |
| **승인 (`PENDING` → `ACTIVE`)** | 승인된 회원이 세션 만료까지 `403 PENDING_APPROVAL`에 갇힌다 — §3-1-6 위반 |
| 권한 변경 (`USER` ↔ `ADMIN`) | 회수된 관리자 권한이 계속 살아 있다 |

승인은 일괄 처리이므로([2-2 §2-2-2](2-2-OPERATOR-REQUIREMENTS.md)) 선택된 회원 전원의 세션을 함께 처리한다.

## 3-1-6 AUTH-04 신청·대기 화면

- `PENDING` 사용자가 접근 가능한 **유일한** 화면이다 (MUST).
- 신청서를 냈는지에 따라 한 화면이 두 모습을 가진다.

| 상태 | 화면 |
|---|---|
| 신청 전 | 학번·이름을 입력하는 **신청 폼** |
| 신청 후 | 승인 대기 중임을 알리는 **안내**. 승인 전까지 신청 내용을 고칠 수 있다 |

- 두 경우 모두 로그아웃 버튼을 제공한다.
- 인증 API와 신청 API 외의 모든 API 호출은 `403 PENDING_APPROVAL`로 차단한다 (MUST). 프론트엔드는 이 코드를 감지해 이 화면으로 리다이렉트한다.
- 신청 API는 `PENDING` 전용이다. `ACTIVE`가 된 뒤에는 이 경로로 학번을 바꿀 수 없다 (MUST).

## 3-1-7 서버 재검증 원칙

- **모든 관리자 API는 서버 측에서 권한을 재검증한다** (MUST). UI 숨김만으로 권한을 통제하지 않는다.
- 본인이 마지막 남은 활성 관리자일 때는 본인 권한 회수·계정 삭제·본인 정지를 서버에서 차단한다 (MUST) — [2-2 §2-2-7](2-2-OPERATOR-REQUIREMENTS.md).
- 자료 수정·삭제의 "본인 것만" 조건도 서버에서 소유자를 확인한다 (MUST).
