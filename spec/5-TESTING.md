# 5. 테스트와 오류 처리

무엇을 검증해야 머지할 수 있는지, 오류가 났을 때 어떻게 응답하는지를 잡아준다. **이 문서에 적힌 검증을 통과하지 못한 PR은 머지하지 않는다** (MUST).

> **출시 단계** — MVP에서는 공개 랜딩([3-3 결정 8](3-3-DESIGN-DECISIONS.md#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다))·인증·회원 관리·공지에 해당하는 테스트를 출시 조건으로 삼는다. 자료·즐겨찾기·S3·사진·회원 제거·권한 변경 테스트는 해당 `Post Launch` 기능을 구현하는 PR부터 적용한다. 구현되지 않은 기능의 테스트 때문에 MVP 출시를 막지 않되, 구현한 기능에 해당하는 MUST 테스트는 미룰 수 없다.

```text
§5-1   테스트 범위       무엇을 테스트하고 무엇을 안 하는가
§5-2   필수 테스트 사례   권한·경계 조건 중심
§5-3   수동 검증         자동화하기 어려운 것
§5-4   오류 응답 규칙     형식과 로깅
```

## 5-1 테스트 범위

동아리 프로젝트다. **커버리지 목표를 세우지 않는다.** 대신 **틀리면 사고가 나는 것**만 반드시 테스트한다.

| 대상 | 테스트 | 이유 |
|---|---|---|
| 권한 검사 | **MUST** | 틀리면 미승인자가 시험 자료를 본다 |
| 소유자 검사 (본인 것만 수정·삭제) | **MUST** | 틀리면 남의 자료가 지워진다 |
| 마지막 관리자의 본인 권한 회수·삭제·정지 차단 | **MUST** | 틀리면 시스템에 아무도 못 들어간다 |
| 관리자 부트스트랩(이메일+토큰) | **MUST** | 틀리면 이메일만 아는 공격자가 관리자를 탈취한다 |
| Status 전이 (`PENDING`/`SUSPENDED` 차단) | **MUST** | 틀리면 승인제가 무의미해진다 |
| 구글 계정의 도메인·`email_verified` 검증 | **MUST** | 틀리면 외부인이 가입한다 |
| JWT와 세션의 사용자 결합 | **MUST** | 틀리면 남의 세션을 빌려 그 권한을 쓴다 |
| 상태 변경이 기존 세션에 반영되는지 | **MUST** | 틀리면 정지해도 계속 쓰고, 승인해도 계속 막힌다 |
| CSRF 토큰 검증 | **MUST** | 틀리면 다른 사이트가 관리자 대신 회원을 승인·정지한다 |
| presigned URL 발급 조건 (용량·확장자) | **MUST** | 틀리면 임의 파일이 버킷에 쌓인다 |
| 검색·필터 조합 | SHOULD | 틀리면 불편하지만 사고는 아니다 |
| 페이지네이션 경계 | SHOULD | |
| DTO 매핑, getter | 안 한다 | 프레임워크를 테스트하는 것이다 |

**API 계층은 통합 테스트로 검증한다** (SHOULD). Spring Security 필터를 태우지 않는 단위 테스트는 권한 버그를 잡지 못한다. `@SpringBootTest` + Testcontainers(또는 CI의 postgres service container)를 쓴다.

기반은 `apps/api`의 `AbstractIntegrationTest`(Testcontainers·세션·JWT)와 `testsupport`(`Accounts`·`TestSessions`·`Csrf`)다 (2026-08-14, #90). 새 API 이슈는 **그 위에 T 번호 사례만 얹는다.**

- 로그인 상태는 `sessions.as(user, request)` 한 줄이다. **세션은 진짜 저장소에 만든다** — `MockHttpSession`을 쓰려면 세션 자동설정을 꺼야 하고, 그러면 테스트마다 어느 방식인지 골라야 한다.
- 계정은 `Accounts.signedIn/applied/approved/admin/suspended`로 만든다. **가입 단계를 그대로 밟는다** — 상태를 손으로 조립하면 실제로는 만들어질 수 없는 계정이 생긴다.
- **구글 OAuth 콜백 전체 흐름은 통합으로 타지 않는다.** 도메인·`email_verified` 검증(위 표의 MUST)은 `GoogleOidcUserServiceTest`가 서비스 단위로 덮고, 배선은 #82·#48이 실제 구글로 밟는다. 가짜 OIDC 서버를 띄우는 것은 별도 결정이 필요하다.
- **CI에서 도는 것은 #45가 붙인다.** 러너에 Docker가 있어야 Testcontainers가 뜬다.

| T-148 | `USER`가 **본문이 깨진** 관리자 쓰기 API 호출 | `403 FORBIDDEN`. **`400`이 아니다** — 본문을 읽기 전에 끊는다 |
| T-149 | 정렬을 지정하지 않은 `GET /admin/users` | 가입 신청일(`applied_at`) 최신순. **신청하지 않은 계정이 맨 뒤에 온다** |

| T-152 | 검색어에 `_` 또는 `%` | 글자 그대로 찾는다. **전원이 결과에 나오지 않는다** |

| T-155 | 여러 `PENDING` 신청자를 한 요청으로 승인 | 전원이 `ACTIVE`가 되고 `approved_at`이 채워진다 |
| T-156 | 성공·실패가 섞인 일괄 승인 | **성공한 건은 그대로 승인된다.** 실패 한 건이 나머지를 되돌리지 않는다 |
| T-157 | 이미 `ACTIVE`이거나 `SUSPENDED`인 id | `NOT_PENDING`으로 집계된다. **`NOT_APPLIED`가 아니다** — 사유를 뭉개면 화면이 거짓 안내를 한다 |
| T-158 | 같은 id를 두 번 담아 승인 | 한 번만 집계된다. 화면이 읽는 건수가 부풀려지지 않는다 |
| T-159 | 빈 배열 또는 101개 이상 | `400 VALIDATION_ERROR`. **같은 id를 101번 담아도 마찬가지다** — 상한은 중복을 거르기 전의 원본 배열에 건다 |
| T-160 | CSRF 토큰 없이 일괄 승인 | `403`. 계정 상태가 바뀌지 않는다 |

T-144는 **막는 것만큼 여는 것이 중요하다**는 점을 지킨다. 신청 API를 막으면 **아무도 신청서를 낼 수 없고**(신청 전 계정도 `PENDING`이다), `GET /auth/me`를 막으면 화면이 상태를 몰라 신청 폼도 정지 안내도 띄우지 못한다. **정지된 사람에게도 열어야 한다** — 막으면 `401`로 보여 "로그아웃됨"과 구별되지 않는다 ([3-3 결정 12](3-3-DESIGN-DECISIONS.md#3-3-13-결정-12--인증은-jwt-인가-상태는-서버-세션으로-나눈다)).

T-146은 **잊는 것**을 막는다. 권한 매트릭스는 표가 원본이고 코드가 그것을 따르는데, 옮겨 적기를 잊어도 코드는 그냥 동작한다 — 인증만 되면 통과하는 엔드포인트가 조용히 생긴다. 클래스가 아니라 **실제로 매핑된 핸들러**를 훑는다. 열려 있는 것은 매핑이지 클래스가 아니다.

T-147은 `@PreAuthorize`에 `ACTIVE` 조건을 반복해 적지 않는 근거다. 매트릭스의 `ADMIN` 열은 "`ADMIN`이면서 `ACTIVE`"지만, 상태는 `AccountStatusFilter`가 인가보다 먼저 본다. **같은 규칙을 두 곳에 두면 한쪽만 고쳐진다.**

T-05가 여기서 처음으로 실제 확인된다. 계약이 정한 지 오래됐지만 `GET /admin/users`가 없어 미뤄져 있었다(#28 PR에 그렇게 적어 뒀다).

T-149~T-151은 **이 목록이 곧 승인·정지의 대상이 되기 때문에** 있다. 순서가 어긋나거나 신청하지 않은 계정이 승인 대기로 섞이면 관리자가 잘못된 사람을 처리한다. T-149의 "맨 뒤"가 특히 그렇다 — PostgreSQL은 `DESC`에서 널을 **맨 앞에** 올리므로, 널 처리를 빠뜨리면 관리자가 첫 화면에서 보는 것이 승인 대상이 아닌 사람들이 된다.

T-150이 **거절**인 이유는 무시가 더 위험하기 때문이다. 정렬이 적용된 줄 알고 틀린 순서의 명단을 신뢰하는 것보다 `400`을 받는 편이 낫다. T-152도 같다 — `_`를 escape하지 않으면 "아무 글자 하나"로 해석되어 검색 결과에 **전원이 나오고**, 관리자는 그것을 검색 결과로 믿는다.

T-154의 완료 조건은 이슈에 "비밀번호 해시가 응답에 없다"로 적혀 있었다. 구글 OAuth뿐이라 비밀번호 컬럼 자체가 없으므로 **같은 취지로 새면 안 되는 것**을 확인한다 — `google_sub`(구글 계정 식별자)와 `version`(동시성 제어용)이다.

T-155~T-160은 T-49와 한 벌이다. **가입 승인은 되돌릴 수 없고 여러 명을 한 번에 처리한다.** T-156이 특히 그렇다 — 실패를 예외로 던지면 관리자가 20명을 골랐을 때 한 명이 신청서를 내지 않았다는 이유로 **아무도 승인되지 않는다.**

T-157이 사유를 가르는 이유는 화면이 그것을 그대로 안내하기 때문이다. 전부 `NOT_APPLIED`로 뭉개면 **신청서를 내고 이미 승인까지 받은 사람에게 "신청서를 내지 않은 계정입니다"라고 말하게 된다.**

T-148은 **인가가 본문보다 먼저인지**를 본다. MVC는 메서드를 부르기 전에 본문을 역직렬화하고 `@Valid`를 돌리므로, `@PreAuthorize`에만 기대면 권한 없는 사람이 깨진 본문을 보냈을 때 `400 INVALID_INPUT`을 받는다 — **권한이 없다는 사실이 본문 모양에 가려진다.** 그래서 관리자 경로는 필터 체인에서도 막는다 (`POST /auth/application`이 T-50 때문에 그런 것과 같은 이유다).

T-145가 그 경계다. 신청 API를 상태와 무관하게 열면 **정지된 사람이 제출했을 때 인가 규칙이 거절해 `FORBIDDEN`이 나간다** — 화면은 정지를 알아채지 못하고 "권한이 없습니다"만 띄운 채 남는다. 대기 중에 정지당한 사람이 딱 이 경로를 밟는다.

T-02·T-32의 코드가 `FORBIDDEN`이 아닌 이유도 같다. **셋 다 같은 상태 코드를 쓰므로 화면이 가르는 근거는 코드뿐이다** (T-116).

| T-179 | 승격에 성공한 계정이 **같은 요청을 다시** 보냄 | `204`. 아무것도 바뀌지 않고 세션만 다시 맞춘다 — 세션 갱신 실패의 복구 수단이다 |
| T-180 | 대소문자만 다른 두 계정이 각각 호출 | **한 명만 승격된다.** 이메일 비교는 대소문자를 가리지 않지만 `UNIQUE`는 가린다 |

T-17~T-20·T-175·T-177의 응답이 **모두 같아야 한다** (MUST). 사유가 갈리면 *"이메일은 맞았고 토큰만 틀렸다"* 를 알아낼 수 있어 토큰 추측의 탐색 공간이 줄어든다. 설정 여부까지 같은 응답인 이유도 같다 — 알 수 있으면 **이 경로가 언제 열리는지를 지켜볼 수 있다.**

T-179가 필요한 이유는 **세션 갱신 실패를 예외로 올리지 않기** 때문이다([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md)). 승격은 커밋됐는데 세션만 옛 값으로 남으면 본인이 할 수 있는 일은 다시 부르는 것뿐인데, "활성 관리자가 이미 있다"로 거절하면 그 재시도가 막혀 **재로그인 전까지 관리자 화면을 못 연다.** 이메일·토큰을 이미 확인한 뒤라 여는 문이 넓어지지도 않는다.

T-180은 **자격을 만족하는 행이 둘일 수 있다**는 데서 온다. `users.email`의 `UNIQUE`는 대소문자를 구분하므로 `a@b`와 `A@B`가 함께 존재할 수 있고, 각자 자기 행만 잠그면 둘 다 "활성 관리자 0명"을 보고 통과한다. 같은 이메일을 쓰는 계정을 **전부** 잠가 이 경로의 요청을 한 줄로 세운다.

T-16은 `AccountStatusFilter`가 이 경로를 `PENDING`에게 열어 두는지도 함께 확인한다. 막혀 있으면 **최초 관리자는 영영 승격할 수 없다** — 이 경로를 부를 수 있는 상태가 `PENDING`뿐이기 때문이다.

| T-197 | 활성 관리자가 둘일 때 **관리자가 자기 자신을 제거** | 그 요청의 **다음 요청이 `401`** (MUST). 응답을 내보낼 때 현재 세션이 되살아나지 않는다 |
| T-195 | 비로그인으로 `/privacy` 열람 (화면) | "보관과 파기"가 **콘텐츠는 남고 표시만 바뀐다**는 것과 **본문에 담긴 정보는 그대로 남는다**는 것을 함께 알린다 |

**T-196과 T-197은 "폐기했다"만 보면 놓친다.** T-196은 폐기가 **실패한** 경우이고, T-197은 폐기한 세션이 **응답을 내보낼 때 되살아나는** 경우다. 둘 다 정상 경로(T-191)를 통과한 뒤에 열린다.

**T-193은 미룰 수 없다.** 폐기하는 쪽에서 아직 보이지 않는 세션이 잠시 뒤 저장되면 **계정은 없는데 `ACTIVE`·`ADMIN` 세션만 남는다.** 승인·정지는 재로그인이 회복 수단이지만([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md)) **제거에는 돌아갈 계정이 없어 만료까지 아무것도 되돌리지 못한다.** 그래서 회원 제거(#58)는 [#127](https://github.com/HackerKHU/hacker_HP/issues/127) 뒤에 온다.

**T-187이 나머지의 전제다.** 세 FK 중 하나라도 `ON DELETE` 절이 빠지면 기본값 `NO ACTION`이라 **삭제 자체가 FK 위반으로 실패한다** — 그러면 T-188~T-192는 실행조차 되지 않는다.

T-191은 T-32와 짝이다. 정지는 세션을 **갱신**해 `403 SUSPENDED`가 되고, 제거는 세션을 **폐기**해 `401`이 된다. 지울 계정에는 세션에 써넣을 `role`·`status`가 없다.

### 세션·CSRF

신원은 JWT, 인가 상태는 서버 세션이 담당한다 ([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md), [3-3 결정 12](3-3-DESIGN-DECISIONS.md#3-3-13-결정-12--인증은-jwt-인가-상태는-서버-세션으로-나눈다)). 아래는 **Spring Security 필터 체인을 통과하는 통합 테스트로 검증한다** (MUST). 필터를 태우지 않으면 이 결합과 CSRF 검사가 실제로 도는지 알 수 없다.

**자격 증명 결합**

| # | 조건 | 기대 |
|---|---|---|
| T-29 | 사용자 A의 JWT 쿠키와 사용자 B의 세션 쿠키를 함께 전송 | `401 UNAUTHENTICATED`. **A의 신원으로 B의 `role`이 쓰이지 않는다.** 응답이 JWT·세션 쿠키를 모두 폐기한다 |
| T-30 | 유효한 JWT만 있고 세션이 없다 (로그아웃·만료 이후) | `401 UNAUTHENTICATED`. 서명이 유효해도 통과하지 못한다. **정지는 여기 해당하지 않는다** — 세션을 남기므로 T-32의 `403 SUSPENDED`다 |
| T-31 | 세션만 있고 JWT 쿠키가 없다 | `401 UNAUTHENTICATED` |

**상태 변경이 기존 세션에 반영되는가** — 새로 로그인하지 않고 **같은 세션으로** 다음 요청을 보내 확인한다.

| # | 조건 | 기대 |
|---|---|---|
| T-32 | 로그인 중인 `ACTIVE` 회원을 관리자가 `SUSPENDED`로 변경 | 그 회원의 다음 요청이 **`403 SUSPENDED`로** 차단된다 — 세션을 지우지 않고 갱신하므로 T-30의 `401`이 아니다 ([2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md), [3-3 결정 12의 2026-08-11 노트](3-3-DESIGN-DECISIONS.md#3-3-13-결정-12--인증은-jwt-인가-상태는-서버-세션으로-나눈다)). 코드가 다르면 T-99의 경로(쿼리 없이 도착한 정지 세션)에서 안내를 띄우지 못한다 |
| T-33 | 로그인 중인 `PENDING` 회원을 관리자가 일괄 승인 | 그 회원의 다음 요청이 더 이상 `403 PENDING_APPROVAL`을 받지 않는다 |
| T-34 | 로그인 중인 `ADMIN`의 role을 `USER`로 회수 | 그 사용자의 다음 관리자 API 요청이 `403 FORBIDDEN` |

**로그인 세션이 만들어지는 중에 상태가 바뀌면** (#127) — 진짜 `SessionRepositoryFilter`를 통과시켜 확인한다. 이 창의 정체가 **"세션이 언제 저장소에 들어가는가"** 라서, 필터를 흉내 내면 확인하려는 것이 사라진다.

| # | 조건 | 기대 |
|---|---|---|
| T-198 | 로그인이 끝난 직후 | 발급된 `SESSION` 쿠키가 가리키는 세션이 **이미 저장소에 있다** (MUST). `PRINCIPAL_NAME` 색인도 채워져 있다 |
| T-199 | 로그인 전후의 세션 id | **다르다** (MUST) — 세션 고정 보호 |
| T-200 | 로그인 뒤 인가 요청이 쓰던 세션 | 저장소에 **남지 않는다.** 그 사람의 세션은 하나뿐이다 |
| T-201 | 로그인 **전에** 커밋된 승인 | 발급된 세션이 처음부터 `ACTIVE`다 |
| T-202 | 로그인과 정지를 **동시에** 실행 | 어느 쪽이 먼저 잠그든 **세션과 DB가 같다** (MUST). 어긋나면 정지된 사람이 만료까지 계속 이용한다 ([2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md) "즉시 차단") |
| T-203 | 로그인 **뒤에** 커밋된 승인 | 동기화 조회가 그 세션을 찾아 갱신한다 |
| T-204 | 계정을 읽은 뒤 세션이 만들어지기 전에 그 계정이 삭제됨 | 세션이 **하나도 만들어지지 않고** 로그인이 실패한다 (MUST) |

**T-202가 본체다.** 순서를 고정해 놓고 결과를 보는 것이 아니라 **두 순서를 실제로 겨루게 하고, 어느 쪽이 이기든 세션과 DB가 같은지**를 본다 — 그것이 이 창이 닫혔다는 뜻이다. T-201·T-203은 그 양 끝을 결정적으로 고정한다.

**"저장한 뒤에 대조한다"로는 부족하다.** 세션은 응답이 커밋될 때 저장되는데, 응답이 나가면 **대조가 끝나기 전에 그 쿠키로 요청이 도착할 수 있다.** 그래서 응답을 내보내는 호출까지 잠금 안에 있어야 하고, T-202는 그 구조라야 통과한다.

**T-198은 쿠키와 저장소를 함께 본다.** 한쪽만 맞기 쉽다 — 저장은 됐는데 쿠키가 다른 세션을 가리키면 로그인이 안 되고, 쿠키는 맞는데 저장이 늦으면 창이 그대로 열려 있다. 세션을 저장소에 직접 만들면 필터가 자기 판단으로 쿠키를 덮어쓰거나 만료시킨다.

**T-199·T-200은 실제로 저장된 인가 세션을 써야 한다.** 콜백 안에서 즉석으로 만든 세션은 저장소에 없어서, **지우지 않아도 "지웠다"가 통과한다.**

**T-204는 T-193의 로그인 쪽 절반이다.** 이쪽은 아직 응답을 내보내기 전이라 로그인 실패로 되돌릴 수 있다. 이미 만들어진 세션 쪽은 갱신 경로가 지운다 — 필터는 매 요청 `users`를 읽지 않으므로([3-3 결정 12](3-3-DESIGN-DECISIONS.md)) 남겨 두면 계정 없는 사람이 만료까지 인증된다.
| T-162 | 한 사람이 두 브라우저에 로그인한 상태에서 정지 | **두 세션 모두** 다음 요청이 막힌다 |
| T-163 | 상태 변경 트랜잭션이 롤백됨 | 세션도 옛 값 그대로다. 되돌아간 변경이 세션에만 남지 않는다 |
| T-164 | 로그인해 만들어진 세션 | 사용자 id로 찾을 수 있다 (`PRINCIPAL_NAME` 색인) |
| T-165 | `PATCH /admin/users/{id}/status`로 정지·해제 | `200` + **갱신된 회원 본문.** 화면이 재조회 없이 그 행을 고친다 |
| T-166 | 이미 그 상태인데 다시 요청 | `200` + 현재 상태. 아무것도 바뀌지 않는다 |
| T-167 | `PENDING` 계정의 상태를 이 경로로 변경 | `400 VALIDATION_ERROR`. 승인은 `POST /admin/users/approve`가 한다 |
| T-168 | 활성 관리자가 **한 명 더 있을 때** 자기 자신을 정지 | 성공한다. 막는 것은 "마지막 1명이 사라지는 것"이지 "자기를 건드리는 것"이 아니다 |
| T-169 | 남은 다른 관리자가 `SUSPENDED`인 상태에서 자기 정지 | `403 FORBIDDEN`. **정지된 관리자는 세지 않는다** |
| T-170 | 활성 관리자 둘이 **동시에 서로를** 정지 | 최소 한쪽은 실패한다. **자기 정지가 아니어도 막혀야 한다** |
| T-171 | 세션 갱신이 실패한 뒤 같은 상태 변경을 재요청 | 세션이 다시 맞춰진다. 재시도가 복구 수단이다 |
| T-172 | 요청이 인가를 지난 **뒤에** 요청자가 정지되거나 권한을 잃음 | 그 요청은 커밋되지 않는다 — **상태 변경도 일괄 승인도** 마찬가지다. 코드는 필터가 막았을 때와 같다 |
| T-173 | 세션에 더 새 값이 반영된 뒤 **옛 변경의 갱신이 도착** | 덮어쓰지 않는다. 정지가 해제로 되돌아가지 않는다 |
| T-174 | 옛 갱신과 새 갱신이 **동시에** 도착 | 새 값이 남는다. 비교와 저장이 한 연산이어야 한다 |

DB만 바꾸고 세션을 그대로 두는 구현을 잡아내는 것이 이 사례들의 목적이다.

**실제 세션 저장소로 검증한다** (MUST). `MockHttpSession`으로는 확인할 수 없다 — 저장소에 없는 세션은 애초에 찾을 수 없고, 색인이 채워지는지도 드러나지 않는다.

T-164가 나머지의 전제다. 색인이 비면 **찾지 못한 세션은 갱신되지 않고 어디에서도 오류가 나지 않는다** — T-32~T-34가 조용히 무의미해진다.

T-165~T-169는 정지·해제 API다. **T-32가 여기서 실제 API로 닫힌다** — 그전까지는 공통 경로를 직접 불러서만 확인했다.

T-170이 T-15와 한 벌이다. **자기 정지만 막으면 목표를 달성하지 못한다** — 서로를 정지하면 두 요청 모두 자기 검사에 걸리지 않고 0명이 된다. 검사는 "요청자가 대상인가"가 아니라 **"이 조작 뒤에도 활성 관리자가 남는가"**여야 한다 ([2-2 §2-2-7](2-2-OPERATOR-REQUIREMENTS.md)).

T-174가 T-173의 짝이다. 버전을 견주는 것만으로는 부족하다 — 둘이 **같은 옛 세션을 함께 읽으면 둘 다 비교를 통과한다.** 읽기부터 저장까지가 한 연산이어야 한다.

T-173은 **커밋 순서와 세션 저장 순서가 다르다**는 데서 온다. 행 잠금은 DB 변경만 직렬화하고, 잠금이 풀린 뒤의 세션 저장에는 순서 보장이 없다 — 해제와 정지가 잇따르면 늦게 도착한 해제가 정지를 지운다. 세션이 들고 있는 계정 버전보다 낮은 갱신은 버린다.

T-172는 **인가와 저장 사이**를 본다. 인가는 세션 값으로 이루어지므로 요청이 필터를 지난 뒤에도 요청자의 권한이 바뀔 수 있고, 잠금을 기다리는 동안이면 그 사이가 더 길다. 되돌릴 수 없는 조작 전에 잠근 요청자 행으로 다시 확인하지 않으면 **이미 정지된 관리자의 요청이 그대로 커밋된다.**

T-171은 **삼킨 실패의 복구 경로**를 지킨다. 세션 갱신 실패를 예외로 올리지 않는 대신(그러면 이미 커밋된 변경까지 실패한 것처럼 보인다) 관리자가 다시 누르는 것이 유일한 수단인데, "이미 그 상태"라고 일찍 돌아가면 그 재시도가 아무 일도 하지 않는다.

T-169가 T-15와 짝이다. 활성 관리자 수를 셀 때 `SUSPENDED`인 관리자를 포함하면 **DB에 role만 남은 계정을 믿고 마지막 한 명을 정지시킨다** — 그 사람은 로그인할 수 없으므로 실제로는 0명이다 ([2-2 §2-2-7](2-2-OPERATOR-REQUIREMENTS.md) MUST).

T-163은 방향이 중요하다. 갱신이 실패하면 세션은 옛 값(권한이 더 좁은 쪽)으로 남고 만료까지 기다리면 되지만, 반대로 두면 **롤백된 정지 때문에 멀쩡한 회원이 이유도 모른 채 막힌다.**

**CSRF**

| # | 조건 | 기대 |
|---|---|---|
| T-35 | 비로그인 상태로 `GET /auth/csrf` | `XSRF-TOKEN` 쿠키 발급. 인증 없이 접근 가능 |
| T-36 | CSRF 토큰 없이 `POST /auth/application` | `403 FORBIDDEN`. 인증 영역 경로도 검사 대상이다 |
| T-37 | 쿠키와 `X-XSRF-TOKEN` 헤더의 값이 서로 다른 상태로 `POST /notices` | `403 FORBIDDEN` |
| T-38 | **`PENDING` 세션**이 T-35의 토큰을 헤더에 실어 `POST /auth/application` | 성공 |
| T-39 | **`ADMIN` 세션**이 T-35의 토큰을 헤더에 실어 `POST /notices` | 성공 |
| T-40 | 구글 로그인 시작 요청에서 `state`를 지우거나 바꿔 콜백 | 로그인 거부 — OAuth `state` 검증을 끄면 로그인 CSRF가 열린다 |
| T-143 | 계약과 다른 이름(`X-CSRF-TOKEN`·`CSRF-TOKEN`)으로 토큰을 실어 보냄 | `403 FORBIDDEN`. **이름은 계약이 정한 둘뿐이다** |

T-36는 `permitAll` 경로를 CSRF 검사에서까지 빼는 구현을, T-37은 관리자 쓰기 요청의 검사를 끈 구현을 잡는다.

**T-38과 T-39는 서로 다른 세션이다** (MUST). `POST /auth/application`은 `PENDING`만, 관리자 쓰기는 `ACTIVE`·`ADMIN`만 성공할 수 있어 한 세션으로 둘 다 통과할 수 없다. 정상 경로가 CSRF 때문에 막히지 않는지를 각 권한에서 따로 확인한다.

T-143이 필요한 이유는 **Spring의 기본 헤더 이름이 `X-CSRF-TOKEN`이기 때문이다.** 저장소 설정을 손대다 기본값으로 돌아가면 화면이 보내는 `X-XSRF-TOKEN`이 무시되어 **모든 쓰기가 403이 된다** — 서버는 정상이고 화면만 죽는, 원인을 찾기 어려운 형태다.

**로그인 시 CSRF 토큰 회전은 `CsrfAuthenticationStrategy`가 맡는다.** `CsrfConfigurer`가 그것을 세션 인증 전략에 등록하므로 구성상 보장되지만, 실제로 도는지는 **구글 로그인을 한 바퀴 돌려야** 볼 수 있어 자동 검증에서 빠져 있다. 회전이 없으면 공격자가 미리 심어둔 토큰 값이 로그인 후에도 유효하다(토큰 고정). §5-3 수동 검증에 넣어 두었다.

### 구글 OAuth·신청

가입과 로그인은 구글 OAuth 하나로 처리한다 ([3-1 §3-1-4](3-1-DESIGN-ARCHITECTURE.md), [3-3 결정 13](3-3-DESIGN-DECISIONS.md#3-3-14-결정-13--가입로그인을-구글-oauth로-한다)). 구글 응답은 스텁으로 대체하되 **서버의 검증 경로는 그대로 태운다** (MUST).

### 공개 랜딩

랜딩은 인증 영역 밖의 정적 페이지다 ([3-1 §3-1-3](3-1-DESIGN-ARCHITECTURE.md#3-1-3-권한-매트릭스)). 비로그인·`PENDING`·`ACTIVE`·`SUSPENDED` **어느 상태에서도** 열려야 하고, 세션 가드에 걸려 리다이렉트되면 안 된다.

| # | 조건 | 기대 |
|---|---|---|
| T-57 | 비로그인으로 랜딩 접근 | 랜딩이 그대로 렌더된다. 로그인 화면으로 보내지 않는다 |
| T-58 | `PENDING` 사용자로 랜딩 접근 | 랜딩이 그대로 렌더된다. 대기 안내 화면으로 되돌리지 않는다 |
| T-59 | `ACTIVE` 사용자로 랜딩 접근 | 랜딩이 그대로 렌더된다 |
| T-60 | 랜딩을 열었을 때 나가는 `fetch`/XHR 요청 | **나가는 요청이 전부 앱 셸의 세션 확인(`GET /auth/me`)이어야 한다.** 랜딩 콘텐츠(소개·활동·통계·FAQ·후원)를 가져오는 요청은 0건이다. 경로를 가리지 않는다 — 문서·스크립트·스타일·이미지·폰트 같은 정적 자산 요청만 세지 않는다 |
| T-61 | `SUSPENDED` 세션으로 랜딩 접근 | 랜딩이 그대로 렌더된다. 로그인 화면으로 보내지 않는다 |
| T-62 | 서빙되는 `index.html`의 `<head>` | `title`, `meta[name=description]`, `og:title`·`og:description`·`og:image`가 모두 존재한다 |

T-58가 특히 중요하다. `PENDING`을 대기 안내 화면으로 되돌리는 가드가 랜딩까지 잡으면, 승인 대기 중인 지원자가 동아리 소개를 볼 수 없게 된다. T-61도 같은 이유다. 프론트엔드는 정지된 세션을 세션 없음으로 수렴시켜 로그인 화면으로 보내는데, 그 정책이 랜딩까지 적용되면 정지된 사람이 공개 페이지조차 못 본다.

T-60이 재는 것은 **랜딩이 백엔드에 의존하는가**이지 요청 수가 아니다. 세션 확인은 랜딩이 시키는 일이 아니라 **앱 셸(`SessionProvider`)이 경로와 무관하게 하는 일**이다 — `/notices`로 들어가도 똑같이 나간다. 헤더가 세션 상태에 따라 네 갈래로 갈리므로(비로그인·신청 전·승인 대기·`ACTIVE`) 어느 화면에서든 필요하다. 그래서 랜딩 컴포넌트가 부르는 API는 여전히 **0건**이고, [3-3 결정 8](3-3-DESIGN-DECISIONS.md#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다)의 "콘텐츠를 전부 코드에 포함하고 API를 호출하지 않는다"는 그대로 참이다. 세션 확인이 실패해도 소개·활동·통계·FAQ·후원은 그대로 렌더된다 — 백엔드가 죽어도 랜딩은 뜬다.

**횟수로 규정하지 않는다** (MUST). React `StrictMode`는 개발에서 effect를 두 번 실행하므로 `GET /auth/me`가 2회 나간다. 이건 개발 모드 산물이지 랜딩이 백엔드에 의존한다는 신호가 아니다. 횟수를 스펙에 박으면 이런 산물에 스펙이 끌려다닌다. 검사 대상은 **어떤 요청이 나가는가**지 몇 번 나가는가가 아니다.

**대상을 넓히지 않는다** (MUST). 허용되는 것은 세션 확인 하나뿐이다. `GET /auth/me`가 아닌 요청이 하나라도 나가면 — 그것이 랜딩 콘텐츠든 통계든 활동사진이든 — 랜딩이 백엔드에 의존하기 시작한 것이므로 T-60 위반이다.

T-62은 서빙되는 HTML을 직접 본다. 링크 미리보기 봇은 JS를 실행하지 않으므로, 런타임에 태그를 꽂는 방식으로는 통과할 수 없다 ([3-3 결정 8](3-3-DESIGN-DECISIONS.md#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다)). 이 검증이 없으면 카카오톡·인스타그램에 뿌린 홍보 링크의 미리보기가 깨진 채로 MVP 출시 조건을 만족한다.

| T-69 | 삭제 버튼을 누른 직후 (확인 전) | 삭제 요청이 나가지 않는다. 확인 창에 **지울 공지의 제목**이 보인다 |
| T-70 | 등록·수정·삭제 성공 | 각각 새 공지 상세 · 그 공지 상세 · 공지 목록으로 이동한다 |
| T-71 | 고정하지 않은 공지를 목록의 관리 모드에서 고정 | 목록을 다시 조회해 **그 공지가 고정 표시와 함께 위로 올라간다** |

T-63~T-65가 한 벌이다. **T-65는 권한 통제가 아니다** — 진입점을 감추는 것은 편의이고, 실제 차단은 T-63·T-64의 라우트 가드와 서버다 ([3-1 §3-1-7](3-1-DESIGN-ARCHITECTURE.md)). 그래서 T-65만 통과하고 T-63이 깨지면 화면은 멀쩡해 보여도 뚫린 것이다. 이 케이스들은 컴포넌트를 직접 렌더해서 확인할 수 없다 — 가드는 라우트에 붙어 있으므로 **실제 경로로 앱을 띄워야** 밟힌다.

T-66과 T-67은 스키마에서 온다 (`title varchar(200) NOT NULL`, `content text NOT NULL`, [3-2 §3-2-2](3-2-DESIGN-CONTRACT.md)). 화면이 먼저 막는 것은 서버 검증을 대신하는 것이 아니라 같은 규칙을 앞당겨 적용하는 것이다 — 그래서 T-68이 따로 있다. 서버가 거부했는데 화면이 성공한 것처럼 넘어가면, 사용자는 올린 줄 알고 자리를 뜨고 공지는 없다.

T-69의 확인 창은 **무엇을 지우는지 제목으로 보여준다.** "이 항목을 삭제할까요?"로는 잘못된 글을 지우는 중인지 알 수 없고, 삭제는 되돌릴 수 없다.

T-71은 **호출 여부가 아니라 결과를 본다.** 고정의 효과는 "그 글이 위로 올라간다"이고 정렬은 서버가 한다 ([3-2 §3-2-2](3-2-DESIGN-CONTRACT.md) — `is_pinned DESC, created_at DESC`). 그래서 토글 후 목록을 다시 조회하지 않으면 화면 순서가 그대로다. 재조회가 곧 이 기능의 동작이므로 화면에 보이는 순서로 확인한다.

### 회원 관리 (화면)

가입 승인은 **되돌릴 수 없고 여러 명을 한 번에 처리한다.** 그래서 "무엇을 대상으로 하는가"를 화면이 정확히 말하는지가 이 절의 중심이다. API 레벨 차단은 T-05가 이미 본다.

| # | 조건 | 기대 |
|---|---|---|
| T-72 | `USER`로 `/admin/members`에 주소로 직접 접근 | 화면이 그려지지 않고 공지 목록으로 되돌린다 |
| T-73 | 신청서를 내지 않은 `PENDING`(`applied_at IS NULL`) 행 | 상태가 **"미승인"**으로 보인다. 승인 대상이 아니므로 체크박스도 승인 버튼도 없다 |
| T-74 | `PENDING`이 아닌 회원 행 | 체크박스를 선택할 수 없다 |
| T-75 | 전체 선택 체크박스 | **현재 페이지의 승인 대상만** 선택된다. 신청 안 한 계정과 다른 상태의 회원은 선택되지 않는다 |
| T-76 | 선택된 상태의 화면 문구 | 선택 범위가 **이 페이지**임과 전체 인원이 함께 보인다 |
| T-183 | 상태 필터에서 "승인 대기" 선택 | `status=PENDING`과 `applied=true`를 **함께** 보낸다. 화면이 받아서 거르지 않는다 |
| T-184 | `?status=PENDING&applied=true`로 직접 접근 | 그 필터가 선택된 상태로 그려진다 — 뒤로가기·링크 공유에 살아남는다 |
| T-185 | 필터를 쪼개기 전의 주소(`?status=PENDING`)로 접근 | "승인 대기"로 맞추고 **그 사실을 알린다.** 화면이 "전체"라고 말하면서 일부만 보여주면 안 된다 |
| T-77 | 승인·정지·해제 버튼을 누른 직후 (확인 전) | 요청이 나가지 않는다. 확인 창에 **대상의 이름과 무엇이 일어나는지**가 보인다 |
| T-78 | 확인 후 일부가 실패한 응답 | **성공·실패 건수와 실패한 사람**을 안내한다. 사유가 섞여 있으면 **사유별로 갈라서** 말한다 |
| T-161 | 승인 요청을 보낸 뒤의 선택 | 성공이든 실패든 **보낸 사람은 선택에서 빠진다.** 실패한 사람을 남기면 해제할 수 없는 선택이 된다 |
| T-79 | 승인·상태 변경 요청이 서버 오류로 실패 | 실패를 그대로 알린다. 성공 문구가 나오지 않는다 |
| T-80 | 마지막 활성 관리자가 자기 자신을 정지 | 화면이 미리 막지 않고 **서버의 거부 사유를 그대로 보여준다** |
| T-81 | 목록의 "가입 신청일" 칸 | `applied_at`을 보여준다. `created_at`이 아니다 |
| T-186 | 목록의 "학과" 칸 | `department`를 보여준다. 이 필드가 생기기 전에 승인된 회원과 신청 전 계정은 `—`로 보인다 — 값이 없는 것이지 오류가 아니다 (#100) |
| T-82 | 검색·상태·권한·정렬을 바꿈 | 그 값으로 다시 조회하고 **첫 페이지로 돌아간다** |
| T-83 | 선택이 있는 상태에서 조회 조건을 바꿈 | 선택이 해제되고 **그 사실을 알린다.** 선택이 없었으면 아무 안내도 하지 않는다 |
| T-84 | 검색 후 브라우저 뒤로가기 | 검색 입력창이 URL의 검색어를 따라간다 — 목록과 입력창이 어긋나지 않는다 |
| T-85 | 범위를 넘은 `page`로 접근 | 마지막 유효 페이지로 되돌린다 |
| T-86 | 행의 승인 버튼 | 체크박스를 거치지 않고 그 한 명만 승인한다. 확인 창을 똑같이 거치고 **다른 사람의 선택은 건드리지 않는다** |
| T-87 | 확인 창이 열린 상태에서 조회 조건이 바뀜 | 확인 창이 닫히고 이유를 알린다. 사라진 조건의 대상이 승인되지 않는다 |

T-183이 **화면에서 거르지 않는다**를 지킨다. 서버가 20건을 주고 화면이 그중 일부를 버리면 페이지마다 보이는 건수가 들쭉날쭉하고 **총 건수와 총 페이지 수가 실제와 어긋난다** — 관리자가 "12명 남았다"고 읽는 숫자가 틀리게 된다.

필터의 낱말은 **행의 상태 칸과 같아야 한다.** 전에는 필터의 "미승인"이 `PENDING` 전부였고 행의 "미승인"은 그중 신청 안 한 계정만이라 **같은 낱말이 두 범위로 쓰였다** — 서버가 둘을 갈라 주므로(§3-2-6) 그 임시 조치는 끝났다 (2026-08-15, #142).

T-73~T-76이 한 벌이다. 승인 대상은 `status = PENDING AND applied_at IS NOT NULL`이고([3-2 §3-2-6](3-2-DESIGN-CONTRACT.md) MUST), 신청하지 않은 계정을 승인하면 **학번이 빈 `ACTIVE`가 만들어진다.** 서버가 거르지만 화면도 같은 조건으로 잠근다.

**그 계정이 목록에 안 보이는 것이 아니다** (T-48도 같은 기준이다). 계약이 말하는 것은 승인의 **대상 집합**이지 회원 목록 화면이 아니다(§3-2-6의 2026-08-10 명확화) — 신청하지 않은 사람이 있다는 것 자체가 운영 정보다. 대신 **상태 칸이 "미승인"과 "승인 대기"를 가른다.** 둘 다 "승인 대기"로 쓰면 그 구분이 사라지고, 사라진 구분을 액션 칸이 문구로 대신 떠맡게 된다 — 실제로 그랬다. 상태에서 갈리면 액션 칸이 비어 있는 이유가 자명해진다.

T-77과 T-86은 **되돌릴 수 없는 조작 전부**에 확인 창이 붙는다는 같은 규칙이다. 승인만 확인받고 정지는 그냥 나가면 앞뒤가 안 맞는다 — 정지는 즉시 로그인을 막는다([2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md) MUST).

T-75와 T-76도 짝이다. 전체 선택이 "검색 결과 전부"를 뜻하면 관리자가 보지 못한 3페이지의 사람까지 승인된다. 그래서 범위를 현재 페이지로 한정하는데, **범위를 화면이 말하지 않으면 그것대로 관리자를 속이는 것이다.** 둘 중 하나만 지키면 안 된다.

T-80은 **로그인한 관리자 본인의 행**을 눌러야 의미가 있다. 남의 행을 누르고 403을 주입하면 "서버가 거부하면 보여준다"만 확인될 뿐 자기 정지 경로는 밟지 않는다. 화면이 **판단하지 않는 것**을 확인하는 케이스다. 활성 관리자가 몇 명인지 화면은 모르므로 미리 비활성화하지 않고([2-2 §2-2-7](2-2-OPERATOR-REQUIREMENTS.md) — 검사는 서버에서 한다), 서버가 403으로 막으면 그 사유를 그대로 보여준다. T-79와 같은 뿌리다 — 막힌 것을 성공처럼 보이게 하면 관리자가 정지된 줄 알고 자리를 뜬다.

T-78과 T-161이 짝이다. 실패 사유는 셋이고([3-2 §3-2-6](3-2-DESIGN-CONTRACT.md)) 화면이 그것을 하나로 뭉치면 **거짓 원인을 안내한다** — 두 관리자가 같은 신청을 연달아 처리하면 서버는 `NOT_PENDING`을 주는데, 그것을 "신청서를 내지 않았다"로 옮기면 운영자가 이미 승인된 사람에게 신청서를 내라고 연락한다.

T-161이 실패까지 선택에서 빼는 이유는 **세 사유 모두 재조회 뒤에는 승인 대상이 아니기 때문이다.** 체크박스가 잠기거나(T-73·T-74) 행이 아예 사라진다. 선택에만 남으면 관리자는 그것을 해제할 수도 없는데 버튼은 계속 살아 있어, 언제나 실패하는 요청을 다시 보내게 된다. 누가 왜 실패했는지는 T-78의 안내가 이미 말했다.

T-83·T-86·T-87은 **선택과 확인 창이 조용히 어긋나는 경우**를 모아 본다. 지우는 것 자체는 맞다 — 화면에 안 보이는 사람이 승인 대상에 남으면 안 된다. 문제는 말없이 지우거나(T-83), 필요 없는 것까지 지우거나(T-86), 지워야 할 것을 안 지우는 것(T-87)이다. 셋 다 관리자가 "지금 무엇이 대상인지"를 화면과 다르게 믿게 만든다.

### CSRF 토큰 (클라이언트)

서버가 토큰을 검증하는지는 [T-35~T-39](#5-2-필수-테스트-사례)가 본다. 여기는 **클라이언트가 헤더를 싣는가**만 다룬다 — 서버가 아무리 올바르게 검증해도 클라이언트가 안 실으면 모든 쓰기가 403이다.

| # | 조건 | 기대 |
|---|---|---|
| T-88 | `POST`·`PATCH`·`DELETE` 요청 | `XSRF-TOKEN` 쿠키 값이 `X-XSRF-TOKEN` 헤더로 실린다 |
| T-89 | `GET`·`HEAD`·`OPTIONS` 요청 | 헤더가 실리지 않고 발급도 부르지 않는다. **대소문자를 가리지 않는다** (`get`도 안전) |
| T-90 | 계약이 열거하지 않은 쓰기 메서드(`PUT` 등) | 헤더가 실린다 — 대상을 나열하지 않고 안전한 메서드만 나열한다 |
| T-91 | 쿠키가 없는 상태의 첫 쓰기 요청 | `GET /auth/csrf`를 **먼저** 부르고 받은 값을 싣는다 |
| T-92 | 쿠키가 이미 있는 상태의 쓰기 요청 | 발급을 부르지 않는다 |
| T-93 | 쿠키가 없는 상태에서 쓰기 요청이 **동시에** 여러 개 | 발급은 **한 번만** 나간다 |
| T-94 | 쿠키 값이 퍼센트 인코딩되어 있음 | 디코딩해서 싣는다 |
| T-95 | 이름이 비슷한 다른 쿠키(`XSRF-TOKEN-BACKUP` 등)가 함께 있음 | `XSRF-TOKEN`만 정확히 읽는다 |
| T-96 | 발급이 실패하거나 성공했는데 쿠키가 없음 | **쓰기 요청을 보내지 않고** 그 실패를 그대로 알린다 |

T-89가 T-60과 이어진다. 발급을 앱 시작에 미리 부르거나 안전한 메서드에까지 태우면 **랜딩에서 `GET /auth/csrf`가 나가 T-60이 깨진다.** 계약도 "첫 상태 변경 요청 전에"라고 쓴다([3-2 §3-2-3](3-2-DESIGN-CONTRACT.md)) — 앱 시작이 아니다.

T-96이 중요한 이유는 **오진 때문이다.** 토큰 없이 보내면 서버는 `403 FORBIDDEN`을 주고 화면은 그 메시지를 "권한이 없습니다"로 보여준다 — 원인은 토큰인데 사용자는 자기 권한 문제로 읽는다. 실패가 확정된 요청을 보내는 것이기도 하다.

이 절은 `request()`를 mock하고는 검증할 수 없다. **전역 `fetch`를 감시해 실제로 나간 요청의 헤더를 봐야 한다** — mock 뒤에서는 헤더가 실렸는지 알 수 없다.

| T-117 | 로그인 버튼의 이름 | **`Google로 계속하기`** — 승인된 CTA의 한글판이다 ([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md)) |
| T-118 | 버튼 안의 구글 로고 | **공식 배포본의 모양 그대로다.** 직접 그리거나 색을 바꾸지 않는다 |

T-99가 이 절의 핵심이다. 정지 안내가 필요한 경로는 둘인데(§3-1-5) **쿼리가 없는 쪽이 더 흔하다** — 이용 중 정지된 사람은 관리자가 정지시킨 직후 자기 화면에서 튕겨 나온다. 이 경우를 빠뜨리면 **설명 없는 로그인 화면으로 한 번 튕긴다.** 다시 로그인하면 콜백이 `?error=suspended`를 주므로 안내가 영영 안 뜨지는 않지만, 그때까지는 무엇이 잘못됐는지 알 수 없다.

T-100은 **쿼리 값을 그대로 그리지 않는 것**까지 본다. 계약이 쿼리에 이메일·토큰·예외 메시지를 담지 않기로 했지만(§3-2-3 MUST), 화면이 받은 값을 출력하면 그 규정이 깨졌을 때 그대로 새어나간다. 알려진 코드를 문구로 매핑하고 매핑에 없으면 아무것도 띄우지 않는다.

T-117은 문구가 **승인 목록 안에 있는지**를 본다. 가이드라인이 세 가지 CTA만 허용하고 그 현지화를 허용한다 — 임의 표현을 쓰면 승인 범위 밖이다.

T-118은 로고가 **공식 모양 그대로인지**를 본다. 로고는 우리가 그리는 것이 아니므로 모양이 바뀌었다는 것은 누가 손댔다는 뜻이고, 눈으로는 알기 어려워 자동으로 잡는다.

**다만 자동으로 잡는 범위에 끝이 있다.** 로고 마크업이 공식 배포본과 같은지, 그리고 로고와 버튼에 직접 건 표시 속성 일부가 기본값인지를 본다. **정확히 무엇을 보는지는 테스트가 원본이다** (`apps/web/src/features/auth/LoginPage.test.tsx`) — 여기 말로 옮겨 적으면 검사와 설명이 어긋난다. 실제로 세 번 어긋났고 그때마다 설명 쪽이 넓었다.

**CSS로 최종 표시를 바꾸는 경로를 전부 막지는 못한다.** 그 경로는 열거할 수 없어서, 하나를 막으면 다른 하나가 나오고 목록을 늘릴수록 정당한 변경까지 막을 위험만 커진다.

**그래서 T-118을 통과한 것이 가이드라인 준수의 증명은 아니다.** 로고 주변의 CSS를 새로 건드리는 변경은 사람이 화면을 보고 확인한다. 이 경계를 적어 두는 이유는, 모른 채로 경계 밖으로 나가는 것과 알고 나가는 것이 다르기 때문이다.

T-101은 `fetch`가 아니라 **브라우저 이동**임을 확인한다. OAuth는 리다이렉트 흐름이라 `fetch`로는 성립하지 않는다 — 구글 화면이 떠야 하는데 응답만 받아온다.

### 신청·대기 화면

서버가 무엇을 저장하고 무엇을 거부하는지는 [T-46·T-47·T-50·T-51·T-52·T-07](#5-2-필수-테스트-사례)이 본다. 여기는 **한 화면이 두 모습을 어떻게 가르는가**만 다룬다.

| # | 조건 | 기대 |
|---|---|---|
| T-104 | 신청 전 `PENDING`(`appliedAt` 없음)으로 `/pending` | 학번·이름 **신청 폼**이 뜬다 |
| T-105 | 신청 후 `PENDING`(`appliedAt` 있음)으로 `/pending` | **대기 안내**가 뜨고, 신청 내용을 고칠 수 있다 |
| T-106 | **신청 여부를 모르는** `PENDING`(403으로만 알아낸 상태) | **폼도 안내도 띄우지 않는다.** `GET /auth/me`로 확인한 뒤에 정한다 |
| T-107 | 신청서 제출 성공 | 서버에서 다시 읽어 대기 안내로 바뀐다. 새로고침해도 유지된다 |
| T-108 | `409 DUPLICATE_STUDENT_NO`·`400 VALIDATION_ERROR` | 화면에 사유가 뜨고 **입력이 남는다.** 성공한 것처럼 보이지 않는다 |
| T-109 | 대기 안내의 **"다시 확인"** 버튼 | `GET /auth/me`를 다시 부른다. 승인되었으면 그때 화면이 풀린다 |
| T-110 | 대기 안내 문구 | **저절로 바뀌지 않는다**는 것과 다시 확인해야 한다는 것을 알린다 |
| T-111 | `PENDING`이 `/notices` 등 다른 인증 화면에 접근 | `/pending`으로 되돌린다 — 인증 화면 중 여기만 열린다 |

T-106이 이 절의 핵심이다. 신청 여부를 모르는 상태가 실제로 존재하고(§3-1-6), **기본값으로 폼을 띄우면 이미 신청한 사람이 다시 쓰게 된다.** 그 사람은 자기가 낸 내용을 볼 수 없어 학번을 새로 기억해내야 하고, 재제출은 성공하므로 잘못된 값이 그대로 저장된다.

T-109·T-110도 한 벌이다. 승인은 화면에 저절로 반영되지 않으므로(§3-1-6) 버튼이 필요한데, **버튼만 두고 설명이 없으면 누를 이유를 모른다.** 둘 중 하나만 지키면 승인된 사람이 대기 화면에 머문다.

T-108의 "입력이 남는다"가 중요하다. 학번을 다시 입력하게 하면 사용자는 무엇이 거부됐는지 확인할 방법이 없다.

### 세션 상태 판단 (클라이언트)

서버가 어떤 코드를 주는지는 [T-01·T-02·T-32](#5-2-필수-테스트-사례) 등이 본다. 여기는 **클라이언트가 그 응답으로 세션을 어떻게 바꾸는가**만 다룬다 ([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md)).

| # | 조건 | 기대 |
|---|---|---|
| T-112 | 세션이 있는 상태에서 `GET /auth/me`가 **네트워크 오류**로 실패 | 세션을 그대로 둔다. 로그인 화면으로 보내지 않는다 |
| T-113 | 같은 상황에서 **5xx**·계약에 없는 코드로 실패 | 같다 — 세션을 바꾸지 않는다 |
| T-114 | `401 UNAUTHENTICATED` | 비로그인으로 정리한다 |
| T-115 | `403 SUSPENDED` | 정지 세션으로 정리한다. 화면은 정지 안내로 간다 (T-99) |
| T-116 | 화면의 조작이 `403 SUSPENDED`로 실패 | 화면이 그 코드를 세션 계층에 넘긴다 — 오류 문구만 그리고 넘어가지 않는다 |

T-112·T-113이 이 절의 이유다. **"서버에 못 닿았다"는 "로그아웃됐다"가 아니다.** 이 둘을 섞으면 네트워크가 잠깐 끊긴 것만으로 로그인 화면으로 튕기고, 사용자는 자기가 무엇을 잘못했는지 알 수 없다.

T-116은 화면마다 빠지기 쉽다. `403`은 `PENDING_APPROVAL`·`SUSPENDED`·`FORBIDDEN`이 함께 쓰므로 **화면이 코드를 세션 계층에 넘겨야** 정지·승인 대기가 감지된다. 넘기지 않으면 오류 문구만 뜨고 세션은 옛 상태로 남는다.

T-81은 헷갈리기 쉬운 자리라 따로 둔다. `created_at`(첫 구글 로그인)과 `applied_at`(신청서 제출)은 며칠 차이가 나므로([2-2 §2-2-1](2-2-OPERATOR-REQUIREMENTS.md) MUST) 바꿔 쓰면 운영자가 다른 날짜를 보고 판단한다. 형태가 같은 두 날짜라 눈으로는 안 걸린다.

## 5-4 오류 응답 규칙

- 모든 오류는 커스텀 예외 + `@RestControllerAdvice`로 일괄 처리한다 (MUST). 컨트롤러에서 `try-catch`로 응답을 만들지 않는다.
- 응답 본문 형식:

  ```json
  { "code": "PENDING_APPROVAL", "message": "승인 대기 중인 계정입니다." }
  ```

- `message`는 사용자에게 보여줄 수 있는 문장으로 쓴다 (MUST). **스택 트레이스, SQL, 내부 경로를 응답에 담지 않는다.**
- 로그인 거부 사유는 이용자가 스스로 고칠 수 있는 수준으로만 알린다 (MUST). 도메인이 다르면 "`khu.ac.kr` 계정으로 로그인하세요"처럼 안내한다 — 구글이 이미 본인을 인증했으므로 계정 존재 여부가 새어나가는 문제가 아니다.
- 서버 오류(5xx)는 로그에 스택 트레이스를 남기고, 응답에는 일반 메시지만 반환한다. 본문의 `code`는 `INTERNAL_ERROR`다 — **§3-2-7 표에는 넣지 않는다.** 5xx는 화면이 코드로 분기할 일이 없고, 웹은 계약에 없는 코드를 `INVALID_RESPONSE`로 격리해 일반 문구를 보여준다 (T-113). 표에 넣으면 서버 내부 사정이 프론트 분기 대상이 된다.
- 코드 목록은 [3-2 §3-2-7](3-2-DESIGN-CONTRACT.md)이 원본이다. 새 코드를 추가하면 그 표를 같은 PR에서 갱신한다 (MUST).
- **`@RestControllerAdvice`는 `DispatcherServlet` 안에서만 동작한다.** 그 앞의 필터에서 거절되는 요청(`UNAUTHENTICATED`, CSRF `FORBIDDEN`, 세션 상태 검사의 `PENDING_APPROVAL`·`SUSPENDED`)은 advice에 도달하지 않는다. 그 경로도 같은 본문 형식을 내보내야 한다 (MUST) — 형식을 각자 만들면 계약이 두 갈래로 갈라진다.

### 공통 예외 처리

advice가 계약대로 응답하는지 본다. 필터 계층에서 나가는 응답은 T-02·T-32·T-36·T-37이 각각 본다.

| # | 조건 | 기대 |
|---|---|---|
| T-141 | `BusinessException(PENDING_APPROVAL)`을 던지는 핸들러 호출 | `403` + `{"code":"PENDING_APPROVAL", ...}`. 상태·코드·기본 메시지가 코드 정의에서 나온다 |
| T-142 | 같은 응답의 본문 필드 수 | `code`·`message` **둘뿐이다.** 필드가 늘면 웹의 파싱 계약이 흔들린다 |
| T-119 | 메시지를 덮어쓴 `BusinessException` | 메시지만 바뀌고 코드·상태는 그대로다 |
| T-120 | `@Valid` 실패 | `400 VALIDATION_ERROR`. 메시지는 **DTO에 적은 문장**이 그대로 나온다 (T-108) |
| T-121 | 본문이 JSON으로 읽히지 않음 | `400 VALIDATION_ERROR`. 파서 위치·클래스명이 응답에 없다 |
| T-122 | 경로변수 타입 불일치 | `400 VALIDATION_ERROR` |
| T-123 | 매핑된 핸들러가 없는 경로 | `404 NOT_FOUND`. Spring 기본 형식이 나가면 웹이 사유를 읽지 못한다 |
| T-124 | 계약에 없는 예외 | `500` + `INTERNAL_ERROR`. **예외 메시지의 접속 문자열이 응답에 없다** |
| T-125 | 에러 코드 정의와 §3-2-7 표 대조 | 코드 9개가 모두 있고 **그 밖의 코드는 없다.** 상태도 표와 같다 |
| T-126 | 필터 계층용 응답 작성기 | advice와 같은 형식·상태를 쓰고 UTF-8을 선언한다 |
| T-127 | `POST` 전용 경로에 `GET` | **`405`다.** 포괄 핸들러가 삼켜 `500`이 되면 안 된다. `Allow` 헤더가 남는다 |

T-142와 T-125가 이 절의 이유다. 웹은 `ERROR_CODES` 목록에 없는 코드를 `INVALID_RESPONSE`로 버리므로, **서버가 코드를 늘리고 웹을 안 고치면 화면에서 사유가 조용히 사라진다.** 두 테스트가 표·enum·웹 목록을 같이 고쳤는지 되묻는 자리다.

T-124의 "접속 문자열"은 실제 사고 형태다. 예외 메시지를 그대로 `message`에 담는 구현이 흔한데, JDBC URL·호스트명이 그 안에 들어 있다.

T-127은 **매핑하지 않는 것과 삼키는 것이 다르다**는 점을 지킨다. 405·406·415는 계약에 코드가 없어 계약 형식으로 바꾸지 않지만, 포괄 예외 처리가 먼저 잡으면 `500 INTERNAL_ERROR`가 되어 클라이언트 실수가 서버 오류 로그로 쌓인다. 상태와 헤더는 Spring이 정한 대로 내보낸다.

| T-138 | 저장된 인가 요청 없이 콜백 도착 (`state` 불일치와 같은 경로) | `/login?error=failed`로 리다이렉트. JSON을 반환하지 않는다 |
| T-139 | 허용 도메인 계정이 구글 인증에 **성공** | **세션이 남지 않는다.** 계정 조회·세션 발급이 붙기 전까지 로그인이 성립하지 않는다 |
| T-140 | `@PreAuthorize`가 거절한 요청 | `403 FORBIDDEN` + 계약 형식 본문. **`500`이 되면 안 된다** |

T-140이 없으면 권한 부족이 서버 오류로 기록된다. 메서드 보안은 핸들러를 부르는 도중에 예외를 던지므로 `DispatcherServlet`이 먼저 잡고, 시큐리티의 `ExceptionTranslationFilter`까지 올라가지 못한다 — 포괄 예외 처리가 그대로 삼킨다.

T-136이 **로그인 자체를 막는 유일한 검사다.** 기본 `oauth2Login()`은 토큰 교환에 성공하면 그대로 신원을 세션에 올리므로, 이 검사를 걸지 않으면 아무 구글 계정이나 통과한다. 도메인은 `contains`가 아니라 `@도메인` 접미사로 본다 — 포함으로 짜면 `someone@khu.ac.kr.evil.com`이나 `khu.ac.kr@gmail.com`이 통과한다.

T-138이 없으면 사용자가 **SPA 밖의 빈 화면에 갇힌다.** 콜백은 브라우저 전체가 이동한 흐름이라 프론트엔드의 공통 오류 처리(`request()`)를 거치지 않는다.

T-139는 **계정 조회(#25)와 세션 발급(#26)이 붙을 때까지만 유효하다.** 인증은 JWT와 서버 세션이 함께 성립해야 하는데(§3-1-5 MUST), 둘 다 없는 상태에서 구글 인증만으로 세션을 만들면 **`users` 행도 `status` 확인도 없는 신원이 `authenticated()`를 통과한다.** 허용 도메인을 지났다는 것은 "우리 학교 사람"이라는 뜻일 뿐 "가입이 승인된 회원"이 아니다. 그 두 이슈가 이 테스트를 정상 로그인 사례로 바꾼다.

T-134가 막는 것은 조용한 낭비다. 시큐리티 기본 설정은 401로 돌려보내기 전에 그 요청을 세션에 저장하는데, 화면은 랜딩을 포함해 **최초 렌더마다 `GET /auth/me`를 부른다.** 그대로 두면 비로그인 방문자 한 명당 세션 행 하나가 RDS에 쌓이고, 로그인 후 돌아갈 곳도 저장된 API 경로가 되어 SPA 대신 JSON 응답에 멈춰 선다. 오류가 나지 않아 배포 후에도 모른 채 지나간다.

T-135는 **설정 파일을 실제로 읽어서** 본다. 값을 테스트에서 흉내 내면 정작 그 파일이 바뀌었을 때 아무것도 잡지 못한다.

T-130과 T-132가 같은 사고를 막는다. **로컬에서는 되고 배포하면 안 되는** 종류라 눈으로는 걸리지 않는다. 프록시가 두 겹(Vercel → ALB)이라 Spring이 요청 host로 조립한 `redirect_uri`는 구글 등록값과 어긋나 `redirect_uri_mismatch`로 거부되고([docs/ops/infra.md](../docs/ops/infra.md)), 기본 경로에 남아 있으면 Vercel rewrites가 `/api/*`만 프록시하므로 콜백이 ALB에 닿지 않는다.

T-133은 **실패하는 쪽이 안전한** 경우다. 기본값을 코드에 심어두면 설정 누락이 조용히 지나가고, 도메인 제한 없이 아무 구글 계정이나 가입할 수 있는 상태로 서비스가 떠 있게 된다.
