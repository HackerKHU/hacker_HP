## 3-3-1 결정 1 — 모노레포로 구성한다

**상태** 승인됨 · 2026-08-01

**배경** 백엔드(Spring Boot), 프론트엔드(React), 인프라(Terraform)로 구성된다. 인원이 적고 저장소를 여러 개로 나눠 관리할 여력이 없다.

**결정** `apps/api`, `apps/web`, `infra/terraform`을 GitHub Organization 안의 단일 저장소에 둔다.

**이유** 이슈·PR·문서를 한곳에서 추적할 수 있고, 프론트-백엔드 계약이 바뀔 때 한 PR로 같이 리뷰할 수 있다. 소규모 팀에서 멀티레포는 동기화 비용만 늘린다.

**트레이드오프** CI 워크플로에서 `paths` 필터를 신경 써야 한다. 팀·제품이 커지면 각 앱을 독립 배포 주기로 떼어낼 필요가 생길 수 있다.

## 3-3-2 결정 2 — NAT Gateway를 쓰지 않는다

**상태** 승인됨 · 2026-08-01

**배경** 프라이빗 서브넷에서 인터넷으로 나가려면 보통 NAT Gateway가 필요하다. 그런데 NAT Gateway는 월 5~6만원으로, 프로젝트 전체 예산(월 3.5만원 목표)을 그것만으로 초과한다.

**결정** NAT Gateway를 두지 않는다. ECS 태스크는 퍼블릭 서브넷에 `assign_public_ip = true`로 배치해 ECR·SSM에 접근하고, 인바운드는 보안그룹(ALB SG만 허용)으로 막는다. RDS는 아웃바운드가 필요 없으므로 프라이빗 서브넷에 완전히 격리한다.

**이유** NAT은 "프라이빗 서브넷에서 인터넷 나가는 배관"일 뿐 그 자체로 보안 요소가 아니다. SG를 CIDR이 아니라 **SG 참조**로 제한하면 퍼블릭 서브넷에 있어도 외부에서 태스크에 직접 접근할 수 없다.

**트레이드오프** 태스크의 퍼블릭 IP가 노출된다(SG로 차단되지만 네트워크 경로 자체는 열려 있다). 부원 수·예산이 늘면 라우트 테이블 수정 수준으로 NAT을 다시 추가할 수 있다.

## 3-3-3 결정 3 — ECS Fargate Spot을 쓴다

**상태** 승인됨 · 2026-08-01

**배경** EC2 직접 관리, Fargate 온디맨드, Fargate Spot을 검토했다. 동아리 규모상 서버 관리 인력이 없고, dev 환경은 24/7 무중단이 필수가 아니다.

**결정** ECS Fargate Spot을 기본 용량 공급자로 쓴다(`FARGATE_SPOT`, weight 1). EC2를 직접 운영하지 않는다.

**이유** Fargate는 서버 패치·스케일링을 직접 하지 않아도 된다. Spot은 온디맨드 대비 약 1/3 비용이며, 배포 서킷 브레이커와 ALB 헬스체크를 같이 쓰면 회수 시에도 대부분 무중단으로 넘어간다.

**트레이드오프** AWS가 용량을 회수하면 태스크가 재시작되며 짧은 응답 끊김이 생길 수 있다. 엄격한 무중단이 필요해지면 온디맨드 weight를 섞어야 한다.

## 3-3-4 결정 4 — 시크릿은 SSM Parameter Store로 관리한다

**상태** 승인됨 · 2026-08-01

**배경** DB 비밀번호 등을 어디에 둘지 정해야 했다. 후보는 AWS Secrets Manager와 SSM Parameter Store(SecureString)였다.

**결정** SSM Parameter Store의 `SecureString`으로 관리하고, ECS 태스크 정의의 `secrets` 블록에서 직접 참조한다. Secrets Manager는 쓰지 않는다.

**이유** SecureString은 Standard 티어에서 무료다. Secrets Manager는 시크릿 하나당 월 0.4달러다. 자동 로테이션 같은 전용 기능은 지금 단계에서 불필요하다. 어느 쪽이든 앱 코드에 시크릿이 하드코딩되지 않는다는 목표는 동일하게 달성된다.

**트레이드오프** 자동 로테이션, 크로스 계정 공유를 포기한다. 필요해지면 Terraform 리소스 교체 수준의 마이그레이션이다.

## 3-3-5 결정 5 — 도메인 없이 Vercel 프록시로 HTTPS를 우회한다

**상태** 승인됨 — **임시 조치. 공개 전 재검토 필수** · 2026-08-01 · **[결정 15](#3-3-16-결정-15--api에-커스텀-도메인과-acm-인증서를-붙인다)가 대체함**

**배경** ALB 기본 DNS(`*.elb.amazonaws.com`)에는 ACM 인증서를 발급할 수 없어 ALB가 HTTP만 제공한다. 프론트엔드는 Vercel(HTTPS)에 있어 브라우저가 mixed content로 HTTP API 호출을 차단한다. 도메인은 아직 구매 전이다.

**결정** `apps/web/vercel.json`의 rewrites로 `/api/*`를 Vercel Edge가 ALB(HTTP)로 프록시한다. 브라우저는 Vercel과만 HTTPS로 통신한다.

**이유** 도메인 구매·ACM 발급 없이 기능 개발과 통합 테스트를 즉시 시작할 수 있다. 부수 효과로 same-origin이 되어 쿠키 설정이 `SameSite=Lax`로 단순해진다.

**트레이드오프** Vercel↔ALB 구간이 평문 HTTP로 공개 인터넷을 지난다. 더구나 **ALB 자체가 `0.0.0.0/0:80`으로 열려 있어, ALB DNS를 아는 누구나 프록시를 건너뛰고 평문으로 API를 직접 호출할 수 있다.**

> **실제 부원 계정·비밀번호·시험 자료를 이 상태로 다루지 않는다** (MUST). 개발·테스트와 더미 데이터에만 쓴다. 공개 전 조건은 [7-DEPLOYMENT](7-DEPLOYMENT.md)에 있다.


## 3-3-6 결정 6 — 프론트엔드는 React + Vite로 간다

**상태** 승인됨 · 2026-08-03

**배경** 프론트엔드 프레임워크로 React + Vite(SPA)와 Next.js를 검토했다. 배포처는 어느 쪽이든 Vercel이다. 이 결정은 원래 기술 스택 표에 한 줄로만 있었고 근거가 기록되어 있지 않아, 뒤늦게 결정으로 남긴다.

**결정** React 19 + TypeScript + Vite로 SPA를 만든다. Next.js를 쓰지 않는다.

**이유**

이 사이트는 **로그인하지 않으면 아무것도 볼 수 없는 폐쇄형 서비스**다. 그래서 Next.js가 제공하는 값어치의 대부분이 적용되지 않는다.

| Next.js를 쓰는 이유 | 이 프로젝트에서 |
|---|---|
| SEO / SSR | 승인된 부원만 접근한다. 크롤러가 색인할 페이지가 없다 |
| 서버 컴포넌트, Server Actions | 백엔드가 Spring Boot다. 서버 로직을 둘 자리가 없다 |
| Route Handlers (BFF) | Spring API와 중복된다 |
| `next/image` | 이미지가 presigned URL이라 최적화 대상이 될 수 없다 (공개 URL이 필요하다) |

Next.js를 넣으면 `브라우저 → Next 서버 → Spring → DB` 3계층이 되고, 가운데 Next 서버가 하는 일은 프록시뿐이다. 그 프록시는 이미 `vercel.json`의 rewrites가 하고 있다 ([결정 5](#3-3-5-결정-5--도메인-없이-vercel-프록시로-https를-우회한다)).

Vite SPA는 정적 번들이므로 Vercel에서 CDN으로만 서빙되고, 서버 런타임 비용이 들지 않는다. 백엔드가 완전히 분리된 구조와도 맞는다.

**트레이드오프**

- 나중에 공개 페이지(동아리 소개, 모집 공고 등)가 필요해지면 SEO를 직접 해결해야 한다. 범위가 그렇게 넓어지면 그때 Next.js 마이그레이션을 새 결정으로 기록한다.
- 초기 로딩이 클라이언트 렌더링에 의존한다. 내부 도구 규모에서는 문제되지 않는 수준이다.
- **팀원이 Next.js 경험을 쌓을 기회를 포기한다.** 동아리 프로젝트에서는 학습 가치도 실제 고려사항이었으나, 쓰지 않을 기능을 위해 App Router의 server/client 경계 규칙을 익히는 비용이 더 크다고 판단했다.

## 3-3-7 비기능 제약

### 보안 원칙

- 비밀번호는 bcrypt 등 단방향 해시로 저장한다 (MUST). — 자체 비밀번호를 받지 않기로 하면서 저장할 대상이 사라져 **현재는 해당 사항이 없다** ([결정 13](#3-3-14-결정-13--가입로그인을-구글-oauth로-한다)). 제약을 철회한 것은 아니다.
- **S3 버킷은 완전 비공개로 두고 퍼블릭 액세스 차단을 켠다** (MUST). 파일 접근은 짧은 유효시간의 presigned URL로만 제공하며, 영구적인 공개 URL을 만들지 않는다.
- 업로드 파일명은 서버에서 UUID로 재생성해 저장하고, 원본 파일명은 DB에만 보관한다 (MUST).
- 모든 관리자 API는 서버 측에서 권한을 재검증한다 (MUST) — [3-1 §3-1-7](3-1-DESIGN-ARCHITECTURE.md).
- 시크릿을 코드나 yml에 하드코딩하지 않는다 (MUST).

### 제약값

| 항목 | 값 |
|---|---|
| 자료 파일 최대 용량 | 20MB / 파일 |
| 자료 최대 첨부 개수 | 10개 |
| 이미지 리사이즈 기준 | 가로 최대 1920px, JPEG 품질 85 |
| 목록 기본 페이지 크기 | 20 |

### 대상 환경

데스크톱 웹 브라우저(Chrome, Edge 최신 버전 기준). 화면 전체의 모바일 대응은 범위 밖이다
([1-BACKGROUND §1-2](1-BACKGROUND.md)). 다만 두 헤더는 공통 진입점이라 320 CSS px부터
1023px까지 모바일 메뉴로 모든 진입점을 제공하고, 1024px 이상에서만 한 줄 nav로 전환해
가로 스크롤·겹침 없이 동작해야 한다 (#249). 이 예외를 내부 콘텐츠의 모바일 지원으로
넓히지 않는다. 자료게시판의 갈래·즐겨찾기 메뉴도 공통 진입 조작이라 320 CSS px부터
한 줄과 44px 터치 높이를 유지한다 ([결정 19](#3-3-20-결정-19--자료게시판-갈래-메뉴만-320px-반응형-예외로-둔다)).
이 예외를 자료 표·검색·필터 전체의 모바일 지원으로 넓히지 않는다.

## 3-3-8 결정 7 — 1차 출시를 인증·회원 관리·공지로 제한한다

**상태** 승인됨 · 2026-08-08

**배경** 짧은 기간 안에 운영을 시작해야 하고, 구현 코드는 아직 없다. 세 명 모두 백엔드 개발자이며 한 명이 PM과 프론트엔드를 전담한다. 전체 제품 범위를 한 번에 구현하면 통합·배포·운영 검증 시간이 부족하다.

**결정** 1차 출시(MVP)는 가입·로그인·로그아웃·승인 대기, 관리자 가입 승인·회원 상태 관리, 공지 CRUD·상단 고정, 해당 관리자 화면으로 제한한다. 가입 거부, 자료 CRUD·검색·즐겨찾기·S3, 활동사진, 관리자 권한 부여·회수와 회원 제거는 `Post Launch`로 미룬다.

**이유** 인증과 권한, 프론트·백엔드 통합, 실제 배포 경로를 먼저 안정화한다. 공지 기능은 파일 업로드 없이 전체 구조를 관통할 수 있어 1차 운영 기능으로 적합하다.

**트레이드오프** 1차 출시만으로는 자료 공유와 활동사진이라는 최종 제품 가치를 모두 제공하지 못한다. 따라서 1차 출시는 전체 기능 완성이 아니라 운영 기반을 검증하는 단계이며, 연기한 요구사항은 삭제하지 않고 `Post Launch` 백로그로 유지한다.

> 1차 출시 범위는 [결정 8](#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다)이 수정한다 — 공개 랜딩이 MVP에 추가되었다.

## 3-3-9 결정 8 — 공개 랜딩 페이지를 1차 출시에 포함하고 정적으로 구현한다

**상태** 승인됨 · 2026-08-09 · [결정 7](#3-3-8-결정-7--1차-출시를-인증회원-관리공지로-제한한다)을 수정함

**배경** 지금까지 이 제품은 회원 승인제 내부용 사이트로만 정의되어 있었다. 그래서 로그인하지 않은 사람이 볼 수 있는 화면이 로그인·가입 신청뿐이고, 동아리가 무엇을 하는 곳인지 보여줄 자리가 없다. 대외적으로는 이 사이트가 동아리의 얼굴이며, 신입 지원자는 가입 신청 버튼을 누르기 전에 먼저 판단할 근거가 필요하다.

**결정** 로그인 없이 볼 수 있는 공개 랜딩 페이지를 MVP에 포함한다. 동아리 소개, 활동사진, 활동 통계, FAQ, 후원을 한 페이지에 섹션으로 담고 앵커로 이동한다. **콘텐츠는 전부 코드에 포함하는 정적 페이지로 만들고 API를 호출하지 않는다.** 관리자가 랜딩 콘텐츠를 편집하는 기능은 `Post Launch`로 미룬다.

**이유** 정적으로 두면 MVP가 커지지 않는다. 랜딩 때문에 API 계약(`3-2`)에 엔드포인트가 하나도 늘지 않고, 스키마·권한 매트릭스도 그대로다. 특히 활동사진 조회는 이미 `Post Launch`인데([§1-6](1-BACKGROUND.md#1-6-1차-출시-범위)) 랜딩이 그 API를 쓰면 `Post Launch` 기능을 MVP로 끌어오게 된다 — 정적이면 이 충돌이 아예 생기지 않는다. 랜딩은 인증 영역 밖이라 회원 데이터를 담지 않으므로 폐쇄형 원칙([§1-1](1-BACKGROUND.md))과도 충돌하지 않는다.

**트레이드오프** 소개 문구 한 줄, 활동사진 한 장, 통계 숫자 하나를 바꾸려 해도 코드를 고치고 배포해야 한다. 관리자가 화면에서 직접 고칠 수 없다. 1차 출시 시점에는 콘텐츠가 거의 바뀌지 않으므로 감당할 수 있는 비용으로 본다.

> **정정 (2026-08-09 추가)** — 위 **이유**에 "스키마·권한 매트릭스도 그대로다"라고 적었으나 사실과 다르다. 같은 PR에서 [§3-1-3](3-1-DESIGN-ARCHITECTURE.md#3-1-3-권한-매트릭스) 매트릭스에 네 열이 모두 `O`인 "랜딩 조회" 행이 추가되었다. 그대로 유지된 것은 스키마와 **기존 보호 기능의 권한 조합**이다.
>
> 원문은 고치지 않고 이 노트만 덧붙인다. 결정 자체는 유효하므로 새 번호를 만들지 않는다 — 뒤집는 것이 아니라 사실관계 정정이다.

> **경계 명확화 (2026-08-10 추가)** — 위 **결정**의 "API를 호출하지 않는다"가 무엇의 요청을 말하는지 분명히 한다. **랜딩 컴포넌트가 부르는 API는 0건이다** — 소개·활동사진·통계·FAQ·후원 어느 것도 서버에서 가져오지 않고 전부 `content.ts`에 있다. 이 결정은 그대로 유효하다.
>
> 다만 랜딩을 열면 `GET /auth/me` 요청이 나간다. 이것은 **앱 셸(`SessionProvider`)이 경로와 무관하게 하는 세션 확인**이지 랜딩이 시키는 일이 아니다 — `/notices`로 들어가도 똑같이 나가고, 실패해도 랜딩 콘텐츠는 그대로 렌더된다. 헤더가 세션 상태에 따라 네 갈래로 갈리므로(비로그인·신청 전·승인 대기·`ACTIVE`) 어느 화면에서든 필요하다.
>
> 즉 이 노트는 결정을 뒤집는 것이 아니라 **"랜딩 컴포넌트의 요청"과 "앱 셸의 세션 확인"을 가르는 경계**를 긋는 것이다. 검증 기준은 [5-TESTING T-60](5-TESTING.md#공개-랜딩)이고, 같은 경계가 [§3-1-3](3-1-DESIGN-ARCHITECTURE.md#3-1-3-권한-매트릭스) 설명과 [결정 9](#3-3-10-결정-9--api-경로에-버전을-붙인다)의 "공개 랜딩은 정적이라 API를 호출하지 않으므로"에도 그대로 적용된다. 두 결정 원문은 고치지 않고 이 노트만 덧붙인다.

**언제 뒤집는가** 콘텐츠 변경이 잦아져 배포 비용이 실제로 아파오면, `Post Launch`의 "랜딩 콘텐츠 관리자 편집"을 구현한다. 그 시점에 랜딩 조회 API와 편집 화면을 새 결정으로 기록하고 이 결정을 대체한다.

**발견 가능성 — 메타 태그로 해결하고 Vite에 남는다**

[결정 6](#3-3-6-결정-6--프론트엔드는-react--vite로-간다)은 "크롤러가 색인할 페이지가 없다"를 근거의 하나로 Next.js를 쓰지 않기로 했고, 트레이드오프에 "나중에 공개 페이지가 필요해지면 SEO를 직접 해결해야 한다"고 적어두었다. 랜딩이 바로 그 공개 페이지다. **결정 6은 유효하며, 여기서 그것을 재확인한다.**

랜딩이 생기면서 결정 6이 든 네 근거 중 SEO 하나가 약해졌다. 나머지 셋은 그대로다 — 백엔드가 Spring Boot라 서버 컴포넌트를 둘 자리가 없고, Route Handlers는 Spring API와 중복이며, 자료 이미지는 presigned URL이라 `next/image`의 대상이 될 수 없다. 그리고 결정 6의 가장 강한 근거인 **"Next 서버가 하는 일은 프록시뿐"은 랜딩이 정적이라 그대로 성립한다** — 랜딩은 서버에서 가져올 데이터가 없다.

**랜딩의 발견 가능성은 `index.html`의 `title`·`meta description`·OG 태그로 해결한다.** 랜딩은 한 페이지이고([2-1 §2-1-10](2-1-USER-STORIES.md#2-1-10-화면-목록)) Vite SPA는 모든 경로에서 같은 `index.html`을 서빙하므로 태그 한 벌이면 된다.

이게 실질적인 이유는 검색 색인이 아니다. 구글은 JS를 실행해 SPA를 색인하지만, **카카오톡·인스타그램 같은 링크 미리보기 봇은 JS를 실행하지 않는다.** 동아리 홍보는 대부분 이 경로로 링크를 뿌리므로, 서빙되는 HTML 자체에 태그가 들어 있어야 미리보기에 제목과 설명이 뜬다. 검색 유입보다 이쪽이 훨씬 자주 쓰인다.

**Next.js 마이그레이션은 하지 않는다.** 얻는 것이 랜딩 한 페이지의 렌더링 방식뿐인데, 대가로 라우팅과 권한 가드를 전부 재작성해야 한다.

**언제 다시 검토하는가** 랜딩이 블로그나 프로젝트 쇼케이스 같은 콘텐츠 사이트로 커질 때. 또는 팀이 Next.js 학습 자체를 프로젝트 목표로 삼기로 할 때 — 후자는 기술 판단이 아니라 목표 설정이므로, 그렇게 결정한다면 그 이유를 그대로 정직하게 기록한다. 랜딩을 정적으로 만들었으므로 프리렌더링을 나중에 붙이기도 쉬운 상태다.

## 3-3-10 결정 9 — API 경로에 버전을 붙인다

**상태** 승인됨 · 2026-08-09

**배경** API 계약([3-2](3-2-DESIGN-CONTRACT.md))은 확정됐지만 서버 구현은 아직 시작 전이다. 프론트엔드는 API 클라이언트 레이어까지 올라와 있고([#65](https://github.com/HackerKHU/hacker_HP/pull/65)) base URL을 한 곳(`client.ts`)에서만 잡고 있다. 1차 출시 범위가 인증·회원 관리·공지로 좁아져 있어([결정 7](#3-3-8-결정-7--1차-출시를-인증회원-관리공지로-제한한다)) 자료·즐겨찾기·활동사진 API는 `Post Launch`에 가서야 구현되고, 그 사이에 1차 출시 API의 응답 형태를 고쳐야 할 일이 생길 수 있다.

**결정** base path를 `/api`가 아니라 `/api/v1`로 둔다. 기존 클라이언트를 깨는 변경이 필요하면 `/api/v1`을 고치지 않고 `/api/v2`를 새로 연다. `/actuator`와 springdoc 경로(`/v3/api-docs`, Swagger UI)는 클라이언트 계약이 아니므로 버전을 붙이지 않는다.

**이유** 지금이 경로를 바꾸는 비용이 가장 싼 시점이다. 서버에 컨트롤러가 아직 없고, 프론트는 base URL이 `client.ts` 한 줄로 격리되어 있어 상수 하나만 바뀐다. 이미 배포된 뒤에 버전을 도입하려면 기존 경로를 유지하면서 새 경로를 얹어야 하고, 그동안 두 경로를 모두 관리해야 한다. Vercel rewrites 프록시는 `/api/*` 전체를 넘기므로([결정 5](#3-3-5-결정-5--도메인-없이-vercel-프록시로-https를-우회한다)) 나중에 `/api/v2`가 생겨도 프록시 설정은 그대로 둔다.

공개 랜딩([결정 8](#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다))은 정적이라 API를 호출하지 않으므로 이 결정의 영향을 받지 않는다.

**트레이드오프** 부원 규모의 내부 사이트라 클라이언트가 프론트엔드 하나뿐이고, 프론트와 API를 같은 저장소에서 같이 배포한다. 그래서 버전 분리의 실익이 큰 편은 아니고, 모든 경로가 세 글자만큼 길어진다. 그럼에도 붙이는 쪽을 택한 이유는 비용이 지금 거의 0이고, 나중에 필요해졌을 때의 비용은 0이 아니기 때문이다. `v2`를 열 일이 끝내 없다면 `v1`이라는 접두사만 남고 손해는 그것뿐이다.

> **2026-08-26 노트 ([#228](https://github.com/HackerKHU/hacker_HP/issues/228) 리뷰) — enum에 값을 더하는 것은 `v1` 안에서 한다.**
>
> `status`에 `INACTIVE`를 더하면서 *"이건 기존 클라이언트를 깨는 변경이니 `v2`여야 하지 않나"* 가 나왔다. **깨는 것은 맞다** — 웹은 상태를 빠짐없이 가르도록 되어 있어([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md#클라이언트가-세션-상태를-바꾸는-근거)) 모르는 값을 받으면 그 자리에서 멈춘다. 그런데도 `v1` 안에서 한다: **상태 하나 때문에 모든 경로를 두 벌로 만드는 것은 위 트레이드오프가 감수하기로 한 범위를 넘는다.** 클라이언트가 프론트 하나뿐이고 같은 저장소에서 같이 배포한다는 전제가 여전히 참이라, `v2`를 열면 두 벌을 관리하는 비용만 남고 얻는 것이 없다.
>
> 대신 조건을 붙인다 (MUST). **새 값이 사람의 조작으로만 생겨야 하고, 웹 → API → 조작 순서로 배포해야 하며, 웹과 API를 같은 릴리스에 담지 않는다.** 마지막 조건이 필요한 것은 `deploy-api.yml`과 Vercel이 같은 push에서 **독립적으로** 돌아 순서를 강제하지 않기 때문이다.
>
> **막지 못하는 것도 적어 둔다** (2026-08-28 리뷰). **이미 열려 있는 탭은 소급해 고칠 수 없다.** 웹을 먼저 배포해도 그 전에 열린 탭은 낡은 번들을 든 채 새 값을 받을 수 있고, 그러면 그 탭은 로그인 화면으로 떨어지거나 "다시 시도" 안내를 반복한다. **데이터가 새거나 권한이 잘못 열리지는 않는다** — 못 알아본 상태를 `ACTIVE`로 취급하지 않기 때문이다. 손실은 그 탭 하나가 새로 고칠 때까지 쓸모없어지는 것이고, `v2` 비용과 견주어 이쪽을 감수한다. 유일한 대책은 **관용("모르는 값을 만나면 던지지 않는다")을 새 값을 아는 배포보다 앞서 따로 내보내는 것**이다 — 고칠 수 있는 시점을 앞당기는 것 말고는 방법이 없다.
>
> **배포만으로 값이 생기는 상태를 더한다면 그때는 `v2`를 검토한다.** 규칙 원문은 [3-2의 API 공통 규약](3-2-DESIGN-CONTRACT.md), 검증은 [T-353](5-TESTING.md#비활동-부원과-학기-전환-228)이다.
>
> 결정을 뒤집는 것이 아니라 *"기존 클라이언트를 깨는 변경"* 의 경계를 긋는 노트다. 원문은 고치지 않는다.

## 3-3-11 결정 10 — UI 기반으로 shadcn/ui + Tailwind를 쓴다

**상태** 승인됨 · 2026-08-09

**배경** 만들 화면이 [§2-1-10](2-1-USER-STORIES.md#2-1-10-화면-목록) 기준 8개이고 여기에 공개 랜딩([결정 8](#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다))이 더해졌는데, UI 기반이 정해져 있지 않았다. `apps/web`은 Vite 보일러플레이트 상태로 CSS 파일 두 개가 전부였고, 이대로 화면을 만들기 시작하면 사람마다 다른 방식으로 스타일을 쌓게 된다.

**결정** shadcn/ui + Tailwind CSS를 UI 기반으로 쓴다. shadcn/ui는 npm 의존성이 아니라 **필요한 컴포넌트만 골라 레포에 복사해 쓰는** 방식이다. 컴포넌트를 미리 다 받아두지 않고, 그 화면을 만드는 이슈에서 필요한 것만 추가한다.

**이유**

랜딩이 추가되면서 UI 표면적이 눈에 띄게 커졌다. FAQ 아코디언, 통계 카드, 사진 그리드가 전부 새로 만들어야 할 컴포넌트다. 내부 화면만 있을 때와 규모가 다르다.

그중 접근성이 걸린 것들은 직접 짜면 미묘하게 틀린다. 아코디언의 키보드 조작, 다이얼로그의 포커스 트랩, 체크박스의 중간 상태(회원 관리의 일괄 선택에 필요하다)가 그렇다. shadcn/ui가 얹혀 있는 Radix가 이 부분을 해결한다.

컴포넌트 코드가 레포에 복사되므로 라이브러리 버전에 묶이지 않는다. 디자인이 우리 팔레트와 안 맞으면 그 파일을 직접 고치면 되고, 업스트림이 방향을 틀어도 우리 코드는 그대로다.

국내 동아리 사이트를 조사했을 때도 같은 선택이 확인됐다. 동아리 관리 서비스 오픈소스인 `ddingdong-fe`(COW-dev)가 같은 스택을 쓴다. 비슷한 규모·성격의 프로젝트에서 검증된 조합이다.

**트레이드오프** Tailwind 클래스가 한 줄에 길게 늘어져 처음에는 읽기 불편하다. 팀에 Tailwind 경험자가 없으면 유틸리티 클래스 이름을 익히는 비용이 든다. 컴포넌트 파일이 우리 레포에 들어오므로 업스트림 개선을 자동으로 받지도 못한다.

**언제 뒤집는가** 컴포넌트를 거의 쓰지 않게 되면 — 화면이 단순해서 Radix가 푸는 문제가 생기지 않으면 — 걷어내고 순정 CSS로 돌아간다. 의존성이 아니라 복사된 파일이라 걷어내기도 쉽다.

## 3-3-12 결정 11 — 최초 관리자는 가입 후 토큰으로 본인을 승격한다

**상태** 승인됨 · 2026-08-08 (2026-08-03 초안을 이메일 소유권 검증 누락 문제로 대체)

**배경** 가입 승인은 관리자만 할 수 있는데, 최초에는 승인해 줄 관리자가 없다([1-BACKGROUND §1-5](1-BACKGROUND.md) #3이었음). DB에 직접 `INSERT`하거나 Flyway 마이그레이션에 계정을 심는 방법을 검토했다.

초안은 "SSM의 `ADMIN_BOOTSTRAP_EMAIL`과 이메일이 일치하면 부팅 시 자동 승격"이었다. 이건 뚫린다 — [AUTH-01](3-1-DESIGN-ARCHITECTURE.md#3-1-4-auth-01-가입-신청)은 학교 이메일 **도메인**만 검증하고 **소유권**은 검증하지 않는다. `ADMIN_BOOTSTRAP_EMAIL` 값을 알거나 추측한 사람이 그 이메일로 먼저 가입해 자기 비밀번호를 정하면, 이메일 일치 조건만으로 그 계정이 그대로 승격된다.

**결정** 최초 관리자가 될 사람은 일반 가입 절차(AUTH-01)로 그대로 가입한다(→ `PENDING`). 운영자는 SSM Parameter Store에 `ADMIN_BOOTSTRAP_EMAIL`과 `ADMIN_BOOTSTRAP_TOKEN`(무작위 시크릿)을 등록해둔다. 로그인한 사용자가 `POST /auth/bootstrap-admin`(body: `{ "token": "..." }`)을 호출하면, 서버는 다음을 **모두** 확인한 뒤에만 요청자 본인을 `role=ADMIN`, `status=ACTIVE`로 승격하고 `approved_at`을 기록한다:

1. 활성 관리자(`role=ADMIN`, `status=ACTIVE`)가 0명
2. 요청자의 이메일이 `ADMIN_BOOTSTRAP_EMAIL`과 일치
3. 요청 본문의 `token`이 `ADMIN_BOOTSTRAP_TOKEN`과 일치 (상수 시간 비교, MUST)

이메일 일치만으로는 승격되지 않는다. 토큰은 SSM 접근 권한이 있는 사람만 알 수 있으므로, 이메일을 알거나 추측하는 것만으로는 이 경로를 탈 수 없다.

**이유**

- 이메일 하나만 조건이면 소유권 없이도 통과한다는 게 초안의 핵심 결함이었다. 토큰을 추가하면 "그 이메일을 안다"와 "SSM 값을 안다"가 분리되어, 후자를 AWS 콘솔/CLI 접근 권한자로 좁힐 수 있다.
- 비밀번호는 본인이 가입 시 직접 정한다. 이 프로젝트에는 비밀번호 재설정 기능이 없어서, 초기화 스크립트가 임시 비밀번호를 발급하는 방식은 "그 비밀번호를 나중에 어떻게 바꾸나"라는 문제가 생긴다.
- RDS가 프라이빗 서브넷에 있어 DB 직접 접근에는 ECS Exec이 필요하다([2-2 §2-2-7](2-2-OPERATOR-REQUIREMENTS.md)). 매 환경(로컬 포함)에서 반복해야 하는 수동 절차보다 API 호출 하나가 낫다.
- 시크릿(이메일·토큰)은 SSM에만 있고 git에 남지 않는다 — [결정 4](#3-3-4-결정-4--시크릿은-ssm-parameter-store로-관리한다)와 같은 원칙.

**트레이드오프**

- 부팅 시 자동이 아니라 명시적 API 호출이 필요하다. "가입 후 이 엔드포인트를 호출한다"는 절차를 운영 문서(런북·배포 체크리스트)에 남겨야 하고, 안 하면 최초 가입자가 계속 `PENDING`으로 남는다.
- 토큰은 재사용 가능한 영구 시크릿이다. 유출되면 활성 관리자가 0명인 시점에 누구든 승격될 수 있다. 최초 부트스트랩 후 SSM에서 토큰을 회전하는 절차는 지금 단계에서는 강제하지 않는다 — 필요해지면 별도 결정으로 남긴다.
- 엔드포인트를 영구히 열어두면 공격 표면이 하나 늘어난다. 다만 트리거 조건(활성 관리자 0명 **그리고** 토큰 일치)이 둘 다 필요해, 관리자가 정상적으로 존재하는 동안에는 아무 일도 하지 않는다.
  > **시도 횟수 제한을 더했다** (2026-08-21, #144). 위 트리거 조건이 성립하는 순간 — 최초 배포 직후, 관리자 사고 복구 중 — 은 정확히 **아무도 막을 수 없는 시점**인데, 그때 토큰을 무제한으로 추측할 수 있었다. 계정별 **15분 5회**, 전체 **15분 20회**이며 상세는 [3-2 §3-2-3](3-2-DESIGN-CONTRACT.md)에 있다. **정상 절차(1회)는 영향받지 않는다.** 이 엔드포인트는 [2-2 §2-2-7](2-2-OPERATOR-REQUIREMENTS.md)에서 말하는 마지막 관리자 사고의 복구 경로도 겸한다.

> 이 결정의 전제 하나가 [결정 13](#3-3-14-결정-13--가입로그인을-구글-oauth로-한다)으로 바뀌었다. "AUTH-01이 이메일 소유권을 검증하지 않는다"는 근거는 구글 OAuth로 전환하면서 사라졌다. 그럼에도 **결정은 유지한다** — 토큰 요구는 이제 소유권 문제의 대비책이 아니라, 관리자 승격 경로에 SSM 접근 권한이라는 두 번째 조건을 두는 심층 방어다.
>
> 다만 **전제조건이 하나 늘었다.** "정상 가입"의 의미가 `구글 로그인 + 신청서 제출`로 바뀌었으므로, 위 검사 목록에 **`applied_at IS NOT NULL`(신청서 제출 완료)** 을 더한다 (MUST). 신청 API는 `PENDING` 전용이라, 신청 없이 곧장 `ACTIVE ADMIN`이 되면 `student_no`를 채울 방법이 영영 없어진다 — [3-2 §3-2-3](3-2-DESIGN-CONTRACT.md), [5-TESTING T-16·T-20](5-TESTING.md).
## 3-3-13 결정 12 — 인증은 JWT, 인가 상태는 서버 세션으로 나눈다

**상태** 승인됨 · 2026-08-09 · [1-BACKGROUND §1-5](1-BACKGROUND.md#1-5-미결정-사항) #2를 닫음

**배경** 로그인 상태를 서버 세션 쿠키로 유지할지 JWT로 할지 정해지지 않아 인증 구현([#21](https://github.com/HackerKHU/hacker_HP/issues/21), [#26](https://github.com/HackerKHU/hacker_HP/issues/26))과 SSM 파라미터 구성이 함께 막혀 있었다.

이 제품은 가입 승인제가 전제라 **계정 상태가 자주, 그리고 즉시 바뀐다.** 관리자가 정지하면 이미 로그인한 회원도 다음 요청에서 막혀야 하고([2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md) MUST), 승인하면 `PENDING` 화면에 갇혀 있던 회원이 바로 풀려야 한다([3-1 §3-1-6](3-1-DESIGN-ARCHITECTURE.md)). 순진하게 `role`과 `status`를 JWT에 담으면 토큰 만료 전까지 옛 값이 살아 있어 두 요구사항을 모두 어긴다.

**결정** 두 관심사를 분리한다.

| | 담당 | 저장 위치 |
|---|---|---|
| **신원 증명** | JWT | `httpOnly` 쿠키 |
| **인가 상태** (`role`, `status`) | 서버 세션 | RDS (Spring Session JDBC) |

- JWT에는 `sub`(사용자 id)만 담는다. **`role`과 `status`를 넣지 않는다** (MUST).
- **세션이 없으면 인증이 성립하지 않는다** (MUST). JWT는 "이 요청이 누구인지"만 말하고, "그 사람이 지금 무엇을 할 수 있는지"는 세션이 정한다.
- **세션은 자신이 어느 사용자의 것인지 저장하고, 매 요청 JWT의 `sub`와 일치하는지 검증한다** (MUST). 하나라도 어긋나면 인증 실패로 처리하고 양쪽 쿠키를 모두 폐기한다.
- 토큰은 `httpOnly` 쿠키로만 오간다. `localStorage`에 두지 않는다 (MUST).
- **인증 쿠키에는 `Secure`를 붙인다** (MUST). 로컬 개발(HTTP)만 설정으로 예외를 둔다.
- 쿠키가 자동 전송되므로 **CSRF 토큰으로 대비한다** (MUST). 상태를 바꾸는 요청은 CSRF 토큰 검증을 통과해야 한다. 쿠키·헤더 이름과 발급 경로는 [3-2 §3-2-3](3-2-DESIGN-CONTRACT.md)이 원본이다.
- 세션은 메모리가 아니라 **RDS에 저장한다** (MUST).
- **회원의 `role`이나 `status`를 바꾸는 작업은 그 회원의 기존 세션에 즉시 반영한다** (MUST). 정지뿐 아니라 승인·권한 변경도 포함한다.

**이유**

*왜 세션이 인증의 필수 조건인가* — 이 구조의 핵심이다. JWT는 서명만 맞으면 통과하므로 서버가 회수할 수 없고, 그래서 로그아웃이 "클라이언트가 토큰을 버린다"에 그친다. 유출된 토큰은 만료까지 살아 있다. 세션을 필수로 두면 **세션을 지우는 것만으로 로그아웃과 강제 차단이 모두 성립한다.** 관리자가 정지하면 그 회원의 세션을 지우거나 상태를 갱신하고, 다음 요청은 바로 막힌다. `jti` denylist나 `token_version` 같은 장치를 따로 만들 필요가 없다.

*왜 두 자격 증명을 결합해야 하는가* — 신원과 인가를 나눠 가지면, 둘이 같은 사람의 것인지 확인하지 않는 순간 조합 공격이 열린다. 공격자가 자기 계정의 유효한 JWT와 훔친 관리자 세션 쿠키를 함께 보내면, 서버가 각각을 따로 신뢰할 경우 자기 신원으로 관리자 권한을 쓰게 된다. 그래서 세션에 사용자 id를 함께 저장하고 매 요청 JWT의 `sub`와 대조한다. 이 검증이 빠지면 분리 설계가 그대로 취약점이 된다.

*왜 세션을 RDS에 두는가* — ECS 태스크는 Fargate Spot이라 AWS가 언제든 회수한다([결정 3](#3-3-3-결정-3--ecs-fargate-spot을-쓴다)). 메모리에 두면 회수될 때마다 전원이 로그아웃된다. 비용 절감을 위해 유휴 시간에 `desired_count = 0`으로 내리는 운영([docs/ops/infra.md](../docs/ops/infra.md))에서도 마찬가지다. 캐시 계층(Redis/ElastiCache)은 인프라에 없고 동아리 규모에 도입할 이유도 없으므로, 이미 있는 RDS를 쓴다.

*왜 `httpOnly` 쿠키인가* — `localStorage`에 둔 토큰은 XSS 한 번으로 그대로 털린다. `httpOnly`면 스크립트가 읽지 못한다. Vercel rewrites 프록시 덕분에 브라우저 입장에서 same-origin이라([결정 5](#3-3-5-결정-5--도메인-없이-vercel-프록시로-https를-우회한다)) `SameSite`는 `None`이 아니라 `Lax`로 충분하고, 프론트엔드는 이미 `credentials: 'include'`로 호출하고 있어 바꿀 것이 없다.

`SameSite`와 `Secure`는 별개다. `Lax`는 교차 사이트 요청을 제한할 뿐 평문 HTTP 전송을 막지 않으므로, **`Secure`는 독립적으로 붙인다.** 같은 호스트의 `http://` URL에 접근하는 순간 리다이렉트되기 전에 쿠키가 그대로 노출될 수 있다.

*왜 CSRF 토큰인가* — 쿠키는 브라우저가 자동으로 붙이므로, 다른 사이트가 사용자 브라우저로 요청을 보내면 인증이 딸려 간다. `SameSite=Lax`가 대부분의 교차 사이트 POST를 막지만 그것 하나에 기대지 않는다. 승인제 사이트에서 관리자 계정이 노려질 경우 회원 일괄 승인·정지 같은 조작이 CSRF로 가능해진다.

로그인도 검증 대상에 넣는다. 로그인 CSRF는 피해자를 공격자 계정에 로그인시켜 이후 활동을 공격자 계정에 쌓게 만든다. 대신 세션도 토큰도 없는 최초 진입에서 토큰을 받을 경로가 필요하므로 발급 엔드포인트를 계약에 명시했다 ([3-2 §3-2-3](3-2-DESIGN-CONTRACT.md)). 인증 엔드포인트를 검증에서 빼는 방식은 쓰지 않는다 — 구현마다 예외 범위가 달라져 보안 계약이 흔들린다.

> **선택지 좁힘 (2026-08-11 추가)** — 위 **이유**의 "관리자가 정지하면 그 회원의 세션을 지우거나 상태를 갱신하고"에서 **정지에는 "지운다"를 쓰지 않는다.** 세션을 남기고 `status`를 갱신해 다음 요청이 `403 SUSPENDED`로 막히게 한다 ([3-2 §3-2-7](3-2-DESIGN-CONTRACT.md)).
>
> 세션을 지우면 다음 요청은 [T-30](5-TESTING.md#5-2-필수-테스트-사례)에 따라 `401 UNAUTHENTICATED`가 되고, **클라이언트는 그것이 정지인지 단순 만료·로그아웃인지 구별할 방법이 없다.** [2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md)의 MUST는 "이미 로그인된 세션도 다음 요청에서 차단"인데, **왜 차단됐는지 말해줄 수 있어야 차단이 완결된다** — 아무 설명 없이 로그인 화면으로 튕기는 것은 절반만 한 것이다. 정지 안내를 띄우는 경로는 [3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md)에 있다.
>
> 승인·권한 변경은 그대로 두 방식 중에서 고를 수 있다. 그쪽은 결과를 사용자에게 설명할 필요가 없고, 재로그인해도 새 권한이 그대로 적용된다.
>
> 원문은 고치지 않고 이 노트만 덧붙인다. 결정 자체는 유효하다 — 뒤집는 것이 아니라 **구현이 고를 수 있던 두 선택지 중 하나를 닫는 것**이다.

**트레이드오프** JWT의 대표적 장점인 "서버에 상태를 두지 않는다"를 **의도적으로 포기한다.** 세션 조회가 요청마다 일어나므로 순수한 무상태 구성보다 느리고, 세션 테이블과 만료 정리가 필요하며, `JWT_SECRET`도 함께 관리해야 한다. 서버 세션만 쓰는 구성과 비교하면 관리 대상이 하나 더 늘어난다.

그럼에도 이 조합을 택한 이유는 두 가지다. 첫째, 즉시 차단과 즉시 승인 반영이 MUST인 이상 어떤 방식을 골라도 요청마다 서버 상태를 확인해야 한다 — 무상태는 애초에 선택지가 아니었다. 둘째, **팀이 JWT 기반 인증을 직접 다뤄보는 것을 학습 목표로 삼았다.** 이건 기술적 우열 판단이 아니라 목표 설정이며, [결정 8](#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다)의 선례대로 그대로 기록해 둔다. 순수하게 단순함만 따지면 서버 세션 단독이 더 적은 부품으로 같은 요구사항을 만족한다.

**언제 뒤집는가** 세션 조회가 실제로 병목이 되거나, 브라우저가 아닌 클라이언트(모바일 앱, 서드파티)가 생겨 무상태 토큰이 필요해질 때. 그 시점에는 짧은 만료의 액세스 토큰과 서버 보관 리프레시 토큰으로 재설계하고, 즉시 차단 요구사항을 어떻게 유지할지 새 결정으로 기록한다.

## 3-3-14 결정 13 — 가입·로그인을 구글 OAuth로 한다

**상태** 승인됨 · 2026-08-09 · [1-BACKGROUND §1-5](1-BACKGROUND.md#1-5-미결정-사항) #1을 닫음

**배경** 지금까지 스펙은 `학교 이메일 + 비밀번호`를 전제로 쓰여 있었다. 그런데 이 제품에는 비밀번호 재설정이 없고, 이메일 발송 수단도 없다(알림은 범위 밖 — [§1-2](1-BACKGROUND.md#1-2-범위)). 비밀번호를 잊은 부원을 복구할 방법이 관리자의 DB 직접 수정밖에 없다.

더 큰 문제는 **이메일 소유권을 검증할 수단이 없다는 것**이다. 가입 시 도메인만 확인하고 그 주소가 실제 본인 것인지는 확인하지 않는다. 이 구멍은 이미 [결정 11](#3-3-12-결정-11--최초-관리자는-가입-후-토큰으로-본인을-승격한다)에서 최초 관리자 부트스트랩을 뚫을 뻔했고, 거기서는 토큰을 덧붙여 막았다. 근본 원인은 그대로 남아 있었다.

**결정** 가입과 로그인을 **구글 OAuth 하나**로 처리한다. 자체 비밀번호를 받지도 저장하지도 않는다. 허용 도메인은 **`khu.ac.kr`** 이다.

흐름은 네 단계다.

```text
① 구글 로그인   →  ② 신청서 제출  →  ③ 관리자 승인  →  ④ 이용 가능
   계정 생성          학번·이름          PENDING → ACTIVE
   USER / PENDING
```

- 도메인과 `email_verified` 검증은 **서버가** 한다 (MUST). 구글의 `hd` 파라미터는 로그인 화면에서 계정을 좁혀주는 힌트일 뿐 위조를 막지 못한다.
- 계정의 신원 키는 이메일이 아니라 ID 토큰의 `sub`다 (MUST). 이메일은 학교 정책에 따라 바뀔 수 있다.
- 구글은 학번을 주지 않으므로 계정 생성 시점에 학번이 비어 있다. **학번은 ② 신청서에서 받는다.**
- **승인 대상은 신청서를 낸 `PENDING` 계정으로 한정한다** (MUST).
- **최초 관리자 부트스트랩([결정 11](#3-3-12-결정-11--최초-관리자는-가입-후-토큰으로-본인을-승격한다))도 신청서 제출을 마친 계정만 가능하다** (MUST). 승격 경로가 신청 단계를 건너뛰면 학번 없는 관리자가 만들어지고, 신청 API는 `PENDING` 전용이라 되돌릴 수 없다.
- OAuth 경로는 base path `/api/v1` 아래에 둔다 (MUST) — [3-2 §3-2-3](3-2-DESIGN-CONTRACT.md).

**이유**

*왜 비밀번호를 없애는가* — 비밀번호를 두면 저장·해시·재설정·유출 대응을 전부 우리가 진다. 재설정 수단이 없는 상태에서는 잊어버린 부원이 곧 운영 사고가 된다. 구글에 넘기면 이 부담이 통째로 사라지고, 부원 전원이 이미 학교 구글 계정을 쓰고 있어 새로 만들 것도 없다.

*왜 이메일 소유권 문제가 풀리는가* — 구글이 인증한 계정만 들어오므로 "그 주소가 정말 본인 것인가"를 우리가 확인할 필요가 없다. 도메인 제한과 합치면 `khu.ac.kr` 계정을 **실제로 가진** 사람만 가입할 수 있다. 도메인만 보던 기존 설계와의 차이가 여기다.

*왜 신청서를 따로 받는가* — 구글이 주는 정보는 이메일과 이름뿐이다. 승인 심사에 필요한 학번이 없다. 로그인과 신청을 한 화면에 합치면 "로그인은 됐는데 승인 대상은 아닌" 상태를 표현할 수 없다. 단계를 나누고 신청 시각을 기록하면 관리자 목록에 구경만 하고 간 계정이 섞이지 않는다.

*왜 Status를 늘리지 않는가* — "신청 전 `PENDING`"과 "신청 후 `PENDING`"을 새 Status로 나눌 수도 있다. 그러나 [§3-1-2](3-1-DESIGN-ARCHITECTURE.md)의 Role·Status 분리 모델과 권한 매트릭스는 이미 자리를 잡았고, 두 상태의 **권한이 완전히 같다** — 둘 다 신청·대기 화면만 접근한다. 권한이 같은 것을 Status로 가르면 매트릭스에 의미 없는 행이 늘어난다. 신청 여부는 권한이 아니라 데이터이므로 `applied_at`으로 표현한다.

**트레이드오프**

- **구글에 의존한다.** 구글 로그인이 막히면 아무도 들어오지 못한다. 자체 비밀번호가 없으므로 우회 경로도 없다. 다만 학교 계정 자체가 구글이라 구글이 죽으면 학교 메일도 못 쓰는 상황이라, 실질적으로 의존 범위가 늘어난 것은 아니다.
- **`khu.ac.kr` 구글 계정이 없는 사람은 가입할 수 없다.** 이 사이트가 교내 동아리용이므로 의도한 제약이다. 졸업생·교류 학생처럼 예외가 필요해지면 새 결정으로 기록한다.
- 로컬 개발에 구글 클라이언트 자격이 필요해진다. 프론트엔드 픽스처 모드([apps/web/README.md](../apps/web/README.md))로 화면 개발은 계속 가능하다.
- [§3-3-7](#3-3-7-비기능-제약)의 "비밀번호는 bcrypt 등 단방향 해시로 저장한다"는 저장할 비밀번호가 없어져 **해당 사항이 없다.** 제약을 철회하는 것이 아니라 대상이 사라진 것이다.

**결정 12와의 관계** — [결정 12](#3-3-13-결정-12--인증은-jwt-인가-상태는-서버-세션으로-나눈다)는 그대로 유효하다. 구글은 **최초 신원 확인**만 담당하고, 그 뒤 세션 유지는 우리가 발급한 JWT와 서버 세션이 맡는다. 구글이 준 토큰을 그대로 세션 대용으로 쓰지 않는다 — 그러면 즉시 차단([2-2 §2-2-3](2-2-OPERATOR-REQUIREMENTS.md))이 다시 불가능해진다.

**언제 뒤집는가** 학교 계정이 구글에서 다른 제공자로 바뀌거나, 외부 인원에게 문을 열어야 할 때. 그 시점에도 "신원 확인은 외부, 인가는 우리"라는 구조는 유지하고 제공자만 교체한다.

## 3-3-15 결정 14 — 신청서는 이름을 받지 않는다

**상태** 승인됨 · 2026-08-23 · [결정 13](#3-3-14-결정-13--가입로그인을-구글-oauth로-한다)의 ② 단계를 수정함

**배경** 결정 13의 ② 신청서는 **학번·이름·학과**를 받았다. 이름을 다시 받은 이유는 구글이 주는 표시 이름을 믿을 수 없다고 봤기 때문이다 — 학교 Google Workspace는 실명 뒤에 학적 정보를 붙여 내려준다.

```text
강경현[학생](소프트웨어융합대학 컴퓨터공학부)
```

화면(#132)은 한 발 더 나아가 **최초 신청에서 이름 칸을 일부러 비웠다.** 그럴듯한 값이 채워져 있으면 그대로 제출되어 저 문자열이 회원 목록에 남기 때문이다.

그런데 #215가 **계정을 만들 때 그 접미사를 걷어냈다.** 첫 `[`·`(` 앞까지만 남기므로 저장된 `users.name`은 이제 실명이다. 이름을 다시 받을 근거가 사라졌다.

**결정** `POST /auth/application`이 `name`을 받지 않는다. 이름은 구글 계정에서 온 `users.name`을 그대로 쓴다. 신청 화면은 이름과 **이메일**을 채워진 읽기 전용 칸으로 보여준다 — 이메일은 원래 신청 항목이 아니었고, 계정이 여럿인 사람이 어느 계정으로 신청하는지 폼 안에서 확인해야 해서 표시만 더한다.

**서버가 필드를 없애는 것이 통제다.** 화면만 잠그면 API를 직접 부르는 경로가 남는다. `User.submitApplication`에도 이름 인자를 두지 않아 어느 호출자도 그 값을 바꿀 수 없게 했다.

**이유** 본인이 고칠 수 있게 두면 관리자가 심사하는 이름이 구글 계정과 다른 값이 될 수 있다. 신원 확인은 구글이 담당한다는 결정 13의 구조에서, 심사 자료인 이름만 자기 신고로 두는 것은 앞뒤가 맞지 않는다. 입력 칸이 둘에서 하나로 줄어 신청 화면도 짧아진다.

**트레이드오프** 구글 표시 이름을 별명으로 바꿔 둔 사람은 그 별명으로 승인 심사를 받는다. 본인이 고칠 방법이 화면에 없고, 운영진이 DB를 직접 고쳐야 한다. 실제로 문제가 되면 **관리자가 회원의 이름을 고치는 기능**을 새로 만든다 — 신청자 본인에게 되돌려주는 것이 아니라, 심사하는 쪽에 두는 것이 이 결정의 방향과 맞는다.

**언제 뒤집는가** 구글 표시 이름이 실명과 다른 사례가 실제로 쌓일 때. 그때도 신청서로 되돌리지 않고 위의 관리자 편집 경로를 먼저 검토한다.

## 3-3-16 결정 15 — API에 커스텀 도메인과 ACM 인증서를 붙인다

**상태** 승인됨 · 2026-08-22 · [결정 5](#3-3-5-결정-5--도메인-없이-vercel-프록시로-https를-우회한다)를 대체함

**배경** 결정 5는 도메인을 사기 전에 개발을 시작하려고 택한 **임시 조치**였고, 스스로 "공개 전 재검토 필수"라고 적어 두었다. 그 트레이드오프는 두 가지였다 — Vercel↔ALB 구간이 평문으로 공개 인터넷을 지나고, **ALB가 `0.0.0.0/0:80`으로 열려 있어 ALB DNS를 아는 누구나 프록시를 건너뛰고 평문으로 API를 부를 수 있다.** 그래서 "실제 부원 계정·시험 자료를 이 상태로 다루지 않는다"를 MUST로 걸었다.

`khuhacker.com`을 확보하면서 그 조건이 풀렸다. 실제 부원 데이터로 운영을 시작하려면 이 결정을 먼저 닫아야 했다.

**결정** `api.khuhacker.com`으로 ACM 인증서를 발급하고 ALB에 443 리스너를 연다 (#156).

- 80은 443으로 **301 리다이렉트**만 한다. 앱 트래픽은 평문을 타지 않는다
- TLS는 1.2 이상만 받는다 (`ELBSecurityPolicy-TLS13-1-2-2021-06`) — ALB 기본값(2016-08)은 더 오래된 프로토콜까지 허용한다
- `vercel.json`의 rewrites 대상도 `https://api.khuhacker.com`으로 바꾼다

**인증서 검증은 이 계정 Route53이 아니다.** `khuhacker.com`을 관리하는 곳에 AWS가 주는 CNAME을 직접 넣어야 `PENDING_VALIDATION`에서 `ISSUED`로 바뀐다 — `terraform apply` 한 번으로 끝나지 않는다는 뜻이다. 그 레코드는 `terraform output acm_validation_record`로 본다.

**이유** 결정 5의 두 트레이드오프가 모두 사라진다. **특히 두 번째가 중요하다** — 평문 구간을 없애도 ALB의 80이 그대로 열려 있으면 프록시를 건너뛰는 길이 남는다. 리다이렉트 전용으로 바꿔야 그 길이 닫힌다.

**rewrites는 그대로 유지한다. 다만 이유가 바뀌었다.** 이제는 HTTPS 우회가 아니라 **same-origin** 때문이다 — 브라우저가 웹 도메인 하나와만 통신해 쿠키가 `SameSite=Lax`로 충분하고, 프론트는 `fetch('/api/v1/...')`만 부르면 된다. 결정 5가 "부수 효과"로 적었던 것이 지금은 **유일한 이유**다. 프론트가 `https://api.khuhacker.com`을 직접 부르면 CORS와 크로스 사이트 쿠키 설정이 따라붙는다.

**트레이드오프** 도메인 비용과 인증서 갱신이라는 운영 항목이 생긴다. ACM은 DNS 검증이 유지되는 한 자동 갱신하지만, **`khuhacker.com`의 DNS를 다른 곳으로 옮기면서 검증 CNAME을 빠뜨리면 갱신이 조용히 실패한다.**

**언제 뒤집는가** 도메인을 놓거나 API를 다른 오리진으로 옮길 때. 그 시점에 새 결정으로 기록한다.

## 3-3-17 결정 16 — 자유 게시판은 평문·불변으로 시작한다

**상태** 승인됨 · 2026-08-23 · [#235](https://github.com/HackerKHU/hacker_HP/issues/235)

**배경** 부원끼리 자유롭게 글을 올리는 게시판을 더한다. **이 저장소에서 일반 부원이 자유 서술을 남기는 첫 기능이다** — 지금까지 텍스트를 남기는 길은 공지(`ADMIN` 전용)와 자료 메타데이터뿐이었다. 승인된 모든 부원이 쓰는 입력이 처음 생기므로, 편의 기능을 얹기 전에 기본형을 정한다.

**결정** 세 가지를 좁게 시작한다.

| | 결정 | 버린 것 |
|---|---|---|
| 본문 | **평문만** 저장·응답하고 화면은 텍스트 노드로 그린다 | 마크다운·리치텍스트 |
| 정렬 | `created_at DESC, id DESC` **고정.** 파라미터를 받지 않는다 | 정렬 옵션 |
| 수정·삭제 | **없다.** 작성자도 관리자도 지울 수 없다 | 편집·삭제 |

**이유**

**평문** — 서식을 허용하는 순간 그 입력이 다른 부원의 브라우저에서 실행될 수 있는 표면이 생긴다. 관리자만 쓰는 공지와 달리 게시판은 **승인된 모든 부원이 쓴다.** 정화(sanitize)를 직접 구현하는 것은 이 기능의 값을 넘고, 라이브러리를 붙이면 그 라이브러리의 취약점이 우리 것이 된다.

**고정 정렬** — [3-2 §3-2-4](3-2-DESIGN-CONTRACT.md)의 "정렬의 마지막 기준은 언제나 `id`다"(MUST)를 지키는 가장 단순한 방법이다. 덤으로 **이상한 값으로 서버가 터질 자리가 없어진다** — 자료 목록이 `sort=bogus` 하나로 `500`이 났던 적이 있다 ([#52](https://github.com/HackerKHU/hacker_HP/issues/52)).

**불변** — 기능을 작게 유지하려는 선택이다. 다만 **이것은 오래 갈 상태가 아니다** (아래).

**트레이드오프** **잘못 올린 글을 아무도 지울 수 없다.** 개인정보가 담긴 글, 부적절한 글이 영구히 남는다. 서식이 없어 코드 블록이나 링크도 글자 그대로 보인다.

**언제 뒤집는가**

- **게시글 삭제는 후속 결정 20에서 열었다** ([#238](https://github.com/HackerKHU/hacker_HP/issues/238)). 관리자는 전체, 작성자는 본인 글을 완전히 지운다 — 그때 [2-2 §2-2-6](2-2-OPERATOR-REQUIREMENTS.md#2-2-6-콘텐츠-관리) 표에 게시판 행이 생겼다
- **서식**이 필요해지면 새 결정으로 이 결정의 첫 줄을 대체하고, **정화 방식을 그 결정 안에서 함께 정한다.** "마크다운을 켠다"만으로 끝나는 변경이 아니다

## 3-3-18 결정 17 — 상태가 경로마다 다르게 작용하는 것은 필터의 경로 목록으로 가른다

**상태** 승인됨 · 2026-08-26 · [#228](https://github.com/HackerKHU/hacker_HP/issues/228)

**배경** 매 학기 활동하는 부원을 구분하려고 `INACTIVE`를 더한다 ([3-1 §3-1-2](3-1-DESIGN-ARCHITECTURE.md#3-1-2-status)). 그런데 이 상태는 **자료 경로에서만** 막힌다 — 공지·활동사진·게시판은 그대로 쓴다.

**지금까지 상태는 경로와 무관했다.** `PENDING`·`SUSPENDED`는 어디서든 막히므로 "상태는 필터가, 권한은 `@PreAuthorize`가" 라는 분담이 깨끗했다. `INACTIVE`는 **그 분담의 첫 예외**라, 어디서 막을지를 정해 두지 않으면 구현하는 사람마다 다르게 고른다.

**결정** **`AccountStatusFilter`가 막는다.** 경로 목록을 하나 더 둔다 — 지금 있는 `ALWAYS_OPEN`·`PENDING_ONLY` 옆에 **자료 경로 목록**이 생기고, `INACTIVE` 세션이 그 목록에 맞는 요청을 보내면 `403 INACTIVE`로 끝낸다.

`@PreAuthorize`로 내리는 쪽은 버린다.

**이유**

**거절 코드가 뭉개진다.** `@PreAuthorize`가 거부하면 `AccessDeniedException` 하나만 나와 전부 `403 FORBIDDEN`이 된다. 그런데 계약은 네 코드를 구분한다 — `PENDING_APPROVAL`·`SUSPENDED`·**`INACTIVE`**·`FORBIDDEN`. 넷 다 같은 상태 코드를 쓰므로 **화면이 가르는 근거는 코드뿐이다.** 뭉개지면 비활동 부원에게 "권한이 없습니다"가 뜨는데, 그 사람이 할 수 있는 일(운영진에게 활동 의사를 알린다)과 전혀 다른 안내다. `AccountStatusFilter`가 이미 같은 이유로 존재한다.

**규칙이 한 곳에 모인다.** `@PreAuthorize`로 내리면 자료 컨트롤러 **열한 개 경로마다** 상태 조건이 흩어지고, 자료 API가 하나 늘 때 거기에 붙이는 것을 잊으면 **비활동 부원에게 열린 채로 배포된다.** `NoteController`가 이미 같은 말을 적어 두었다 — "같은 규칙을 두 곳에 두면 한쪽만 고쳐진다".

**기본값이 안전한 쪽인가.** 이 점에서는 필터가 불리하다. `ALWAYS_OPEN`은 *"여기 없는 것은 전부 막힌다"* 라 새 경로가 기본적으로 닫히지만, 새로 두는 자료 경로 목록은 **여기 없는 것이 열린다.** 그래서 [3-2 §3-2-4](3-2-DESIGN-CONTRACT.md#3-2-4-api--자료즐겨찾기)에 *"자료 경로가 늘면 여기도 늘어야 한다"* 를 적었고, 테스트가 그 목록을 지킨다 (T-338).

**트레이드오프** 필터가 경로를 아는 것은 그 자체로 결합이다. 자료 API의 URL을 바꾸면 필터도 함께 고쳐야 하고, 잊으면 **조용히 열린다** — 컴파일도 되고 테스트도 자료 쪽만 보면 통과한다. 그 구멍을 메우는 것이 T-338이다: **비활동 세션으로 자료 경로 전체를 한 번씩 두드려 본다.**

**언제 뒤집는가**

- **상태별로 갈리는 경로가 자료 말고 더 생기면** 목록이 둘, 셋으로 늘어난다. 그때는 "경로 목록"이 아니라 **상태마다 접근 가능한 갈래를 선언하는 구조**로 바꿀 때다. 지금은 갈래가 하나뿐이라 그 추상을 만들 값이 없다.
- **자료 경로가 `/notes` 밖으로 흩어지면** 패턴으로 묶을 수 없어 목록이 길어진다. 그 전에 경로를 정리하는 쪽이 낫다.

> **2026-08-28 노트 ([#229](https://github.com/HackerKHU/hacker_HP/issues/229) 구현) — 경로를 열거하지 않고 접두사로 막는다.**
>
> 위 트레이드오프가 *"새로 두는 자료 경로 목록은 여기 없는 것이 열린다"* 를 이 결정의 약점으로 적어 뒀다. 구현하며 실측해 보니 **계약이 세는 열한 경로가 전부 `/api/v1/notes/**`와 `/api/v1/bookmarks/**` 아래**였다. 접두사 둘로 막으면 그 집합을 정확히 덮으면서 **기본값이 닫힘으로 뒤집힌다** — 자료 갈래에 API가 늘어도 자동으로 막히고, 열어야 할 것이 생기면 **그때 예외를 적는 것이 결정이 된다.**
>
> **T-338은 그대로 둔다** (MUST). 접두사가 맞다는 것을 접두사로 재면 아무것도 재지 않는 것과 같다 — 그 사례는 이제 *"계약이 세는 열한 경로가 실제로 그 접두사 아래에 있는가"* 를 본다. 목록은 §3-2-4 표에서 **손으로 옮겨 적는다.**
>
> 결정을 뒤집는 것이 아니라 *"경로 목록"* 을 어떤 모양으로 쓰는지를 정하는 노트다. 원문은 고치지 않는다. 위 "언제 뒤집는가"의 둘째 항목은 여전히 유효하다 — **자료 경로가 그 접두사 밖으로 나가면** 이 방식이 무너진다.

## 3-3-19 결정 18 — 표시 이름에 학번 끝 두 자리를 붙인다

**상태** 승인됨 · 2026-08-30 · [#300](https://github.com/HackerKHU/hacker_HP/issues/300)

**배경** 동아리에 **이름이 같은 부원이 있다.** 자료·공지·활동사진·자유 게시판은 올린 사람의 이름만 보여주므로, 목록에 `권승원`이 둘 뜨면 어느 쪽인지 가릴 방법이 없다. "그 사람 정리본"을 찾아 달라는 말이 통하지 않는다.

구별에 쓸 수 있는 값은 서버가 이미 들고 있는 것 중 **학번·학과·이메일**이다. 셋 다 지금은 다른 부원에게 보이지 않고, [#178](https://github.com/HackerKHU/hacker_HP/issues/178)이 *"학번·이메일이 서로에게 보이는 것은 별도 판단이 필요하다"* 며 그 판단을 미뤄 두었다.

**결정** 이름 뒤에 **학번 끝 두 자리**를 구분자 없이 붙인 것을 표시 이름으로 쓴다 (`권승원66`). **언제나 붙이고**, 학번이 없으면 붙이지 않으며, 탈퇴한 회원은 `"탈퇴한 회원"` 그대로다. 만드는 곳은 한 곳이고 네 도메인이 그것만 쓴다. 관리자 회원 목록은 대상이 아니다 — 학번 열이 따로 있다.

**부원끼리 학번 뒷자리를 보는 것을 허용한다.** #178이 미뤄 둔 판단에 대한 답이며, **개인정보처리방침에 고지한다.**

**이유**

**학번 뒷자리가 가장 적게 드러내면서 가장 잘 가른다.** 학과는 같은 과 동명이인을 못 가르고 표시가 길어진다. 이메일은 학번보다 더 드러내고 그 자체가 연락 수단이다. 입학 연도가 같은 동명이인이 아니면 뒤 두 자리로 갈리고, **그 두 자리만으로는 학번 전체를 알 수 없다.**

**언제나 붙이는 쪽이 예측 가능하다.** 겹칠 때만 붙이면 **남이 가입하는 순간 내 표시 이름이 바뀌고** 이미 올려 둔 자료의 표시까지 따라 바뀐다. 조회할 때마다 동명이인 여부를 따져야 하는 비용도 붙는다. 겹치지 않는 사람의 뒷자리까지 노출되는 것은 그 대가로 받아들인다.

**서버가 만든다.** `"탈퇴한 회원"`을 서버가 채우기로 한 것과 같은 이유다 ([3-2 §3-2-2](3-2-DESIGN-CONTRACT.md#작성자를-내려주는-규칙)) — 화면이 조립하면 화면마다 갈리고, 규칙을 바꾸려면 웹을 배포해야 한다.

**트레이드오프**

**부원끼리 서로의 학번 뒷자리를 보게 된다.** 이 사이트는 승인제라 보는 사람이 이미 부원이고, 회원 관리 화면에서는 관리자가 학번 전체를 본다. 그래도 **"서로에게 보인다"는 새로 여는 것**이라 개인정보처리방침에 고지하는 것을 조건으로 붙였다.

**이름이 같고 학번 뒷자리도 같으면 여전히 못 가른다.** 같은 해 입학한 동명이인이 그렇고, 입학 연도가 달라도 뒤 두 자리가 겹칠 수 있다 (`2021102466`·`2022102466`). 그때 자리를 늘리는 것은 노출을 키우는 일이라 **드물다는 이유로 받아들인다** — 결함이 아니라 값이므로 사례로 남긴다 (T-433).

**언제 뒤집는가**

- **학번 뒷자리도 같은 동명이인이 실제로 생기면.** 그때는 자리를 늘릴지, 다른 값을 쓸지를 다시 정한다.
- **부원 명부처럼 학번을 정면으로 보여주는 화면이 생기면.** 이 결정이 붙잡고 있던 "최소한만 드러낸다"가 그 화면 때문에 이미 무너진 뒤다.

## 3-3-20 결정 19 — 자료게시판 갈래 메뉴만 320px 반응형 예외로 둔다

**상태** 승인됨 · 2026-08-30 · [#325](https://github.com/HackerKHU/hacker_HP/issues/325)

**배경** 화면 전체의 모바일 대응은 범위 밖이지만, 자료게시판 첫 줄의 시험 정리본·과목
정리본·즐겨찾기는 원하는 목록을 고르는 공통 진입 조작이다. 320px에서 각 문구가 줄바꿈되고
"즐겨찾기만 보기"가 가로 공간을 차지해 세 조작이 한 줄을 벗어났다.

**결정** 이 메뉴만 320 CSS px부터 반응형 예외로 둔다. 세 링크는 글자 크기를 줄이지 않고
한 줄에 두며 최소 44px 터치 높이를 갖는다. 표시 문구는 "즐겨찾기"로 줄이되 별표와 선택
상태, `?category=`·`?bookmarked=true` 이동은 유지한다. 좁은 화면에서는 링크 내부 패딩과
바깥 행·즐겨찾기 내부 간격을 줄이되, 두 갈래 링크 사이는 터치 대상을 구분할 `8px`를
유지한다. 넓은 화면에서는 기존 값을 복원한다. 자료 표·검색·필터 전체의 모바일 재배치는
포함하지 않는다.

**이유** 세 조작 중 하나를 다음 줄이나 별도 메뉴로 옮기면 같은 목록을 고르는 선택지가
갈라지고 현재 상태를 한눈에 비교할 수 없다. 문구와 빈 공간을 줄이면 정보·동작을 버리지
않고 320px 안에 들어간다.

**트레이드오프** 모바일 전용 간격 규칙과 검증할 폭이 늘어난다. 메뉴 항목이나 문구가 더
늘면 지금의 한 줄을 유지할 수 없으므로 그때는 축약을 반복하지 않고 조작 구조를 다시
결정해야 한다. 이 예외만으로 자료 표와 필터가 모바일용이 되는 것은 아니다.

## 3-3-21 결정 20 — 관리자와 작성자가 자유 게시판 글을 삭제할 수 있다

**상태** 승인됨 · 2026-08-28, 작성자 권한 보완 2026-08-31 · [#238](https://github.com/HackerKHU/hacker_HP/issues/238)

| 지우는 방식 | **완전 삭제.** 공지 삭제와 같은 모양이다 | 감춤(soft delete) |
| 이력 | **남기지 않는다.** `admin_actions`는 회원에 대한 조작 테이블이라(#143) 글 id를 넣으면 대상 종류가 섞인다 — 자료 삭제(#54)와 같은 판단 | 삭제 이력 보관 |

**이유**

**관리자와 작성자 본인** — 잘못 올린 글을 지우기 위해 매번 운영진에게 요청하게 하면 되돌릴 수 없는 조작의 확인 책임이 작성자에게 있는데 실행 권한은 운영진에게만 남는다. 관리자는 부적절한 글을 정리할 수 있도록 작성자와 무관하게 전체 삭제를 유지한다. `INACTIVE`는 자료만 막히므로 자기 게시글 삭제도 `ACTIVE`와 같다. `PENDING`·`SUSPENDED`와 탈퇴·제거되어 작성자 관계가 끊긴 계정에는 열지 않는다.

**완전 삭제** — 감추는 방식을 쓰면 "삭제해도 DB에 남는다"를 개인정보처리방침에 고지해야 하는데, 그 값을 지금 하지 않는다. §2-2-6이 임시로 하던 것도 실제 `DELETE`였다.

**이력 없음** — `admin_actions.target_id`는 회원 id 전용이다(#143). 게시글 id를 같은 컬럼에 넣으면 "이 행이 가리키는 것이 회원인지 글인지"를 스키마가 말해주지 못한다. 관리자 삭제와 작성자 본인 삭제 모두 자료 삭제(#54)와 같은 결론을 따른다.

**트레이드오프** 지운 글은 정말 사라진다 — 관리자든 작성자든 실수로 지워도 되돌릴 수 없고 삭제 이력도 없다. 그래서 같은 확인 창과 동기 중복 실행 잠금을 두 권한에 똑같이 적용한다.

**언제 뒤집는가**

- **삭제 복구**가 필요해지면 완전 삭제 대신 보존 기간이 있는 휴지통을 둘지 먼저 결정한다.
- **삭제 이력**이 필요해지면(예: 분쟁이 실제로 생기면) `admin_actions`를 확장할지 별도 테이블을 둘지부터 다시 정한다.

## 3-3-22 결정 21 — 작성자가 자유 게시판 글을 수정할 수 있다

**상태** 승인됨 · 2026-08-28 · [#256](https://github.com/HackerKHU/hacker_HP/issues/256)

**배경** 결정 16의 "수정 없음"이 남긴 결과는 분명했다 — **오타 하나도 고칠 수 없다.** 글을 다시 쓰려면 잘못된 글이 그대로 남은 채 새 글이 하나 더 생긴다. 결정 20이 관리자와 작성자에게 삭제를 열었으니 이제 수정 차례다.

**결정** 결정 16의 "수정·삭제: 없다" 중 **수정**을 대체한다. 삭제는 결정 20을 따른다.

| | 결정 | 버린 것 |
|---|---|---|
| 누가 고치나 | **작성자 본인만.** 관리자는 넣지 않는다 | 관리자 수정 |
| 무엇을 고치나 | **제목·본문을 보낸 것으로 통째로 바꾼다.** 자료 수정(#54)과 같은 판단 | 부분 수정(diff), 수정 이력 보관 |
| 수정 표시 | `updated_at`이 `created_at`과 달라지면 그 자체가 표시다. 별도 플래그를 두지 않는다 | 별도 "수정됨" 컬럼 |
| 수정 기한 | **두지 않는다.** 등록 뒤 언제든 고칠 수 있다 | 기한부 수정 |

**이유**

**작성자 본인만** — 관리자 수정은 남의 글을 고치는 것이라 삭제와 성격이 다르다. 삭제는 "지우기만" 하므로 원문이 뭐였는지가 안 남아도 되지만, 수정은 관리자가 임의로 내용을 바꿔 놓고 원문을 증명할 길이 없다는 문제가 생긴다. 필요해지면 별도 결정으로 연다.

**통째로 교체** — 자료 수정(#54)에서 이미 같은 판단을 했다. 부분 수정(제목만, 본문만)을 지원하려면 요청 스키마가 갈리고 "보내지 않은 필드는 그대로 둔다"는 규칙이 하나 더 생긴다. 값이 크지 않다.

**별도 표시 컬럼 없음** — `posts.updated_at`은 이미 있고 등록 시 `created_at`과 같은 값이 들어간다(#236). 수정하면 그 값이 달라지는 것 자체가 "수정됨"의 근거다. 화면이 `updatedAt !== createdAt`으로 판단하면 되므로 별도 불리언 컬럼을 추가할 이유가 없다.

**기한 없음** — 오타는 등록 직후에 발견될 수도, 한참 뒤에 발견될 수도 있다. 기한을 두면 그 값(1시간? 하루?)을 근거 없이 정하게 된다.

**트레이드오프** 수정 이력이 없으므로 **원문을 증명할 수 없다.** 분쟁이 생기면 "무엇을 어떻게 고쳤는지"를 서버가 답할 수 없다 — 지금은 그 값을 감수한다.

**언제 뒤집는가**

- **관리자 수정**이 필요해지면(예: 명백히 부적절한 표현만 지우고 싶을 때) 별도 결정으로 연다. 그때 삭제와 달리 "무엇을 바꿨는지"를 남길지도 함께 정한다.
- **수정 이력**이 필요해지면(분쟁이 실제로 생기면) 결정 20의 "언제 뒤집는가"와 같은 질문을 다시 본다 — `admin_actions`를 확장할지 별도 테이블을 둘지.

## 3-3-23 결정 22 — 자료 제목은 신규·변경만 50자로 제한한다

**상태** 승인됨 · 2026-08-31

**배경** 자료 제목은 DB와 API가 200자까지 받아 왔다. 표에서 장문 제목이 폭을 차지하면 과목,
학기, 업로더와 삭제 조작이 밀리지만, 상한을 바로 50자로 내리면 이미 저장된 51~200자 자료는
첨부 하나나 과목명만 고쳐도 제목부터 줄여야 한다. 응답에서 원문을 잘라 버리면 검색·수정과
화면이 서로 다른 제목을 갖는다.

**결정** Java `String.trim()`과 같이 양끝의 U+0000~U+0020 문자만 제거한 저장값을 기준으로
신규 제목과 기존 제목의 **변경 결과만 유니코드 코드포인트 50자 이하**로 제한한다.
NBSP(U+00A0)는 제거하지 않고 의미 문자로 센다. 기존 51~200자 제목은 그 값이 DB 원문과 같을
때 전체 교체 수정에서도 유지할 수 있고 조회·삭제도 그대로 지원한다. `notes.title
varchar(200)`과 수정 요청의 정규화 뒤 200자 저장 외피는 유지하되 raw OpenAPI `maxLength`는
선언하지 않는다. 목록은
한 줄, 상세는 제한된 줄 수로 시각적 말줄임하되 DOM·API·접근성 이름에는 원문을 둔다.

**이유** 데이터 마이그레이션이나 강제 축약 없이 새 입력의 밀도만 바로 개선한다. 코드포인트로
세면 이모지 같은 보충 문자를 브라우저와 Java가 한 글자로 동일하게 다룬다. 시각적 말줄임은
메타데이터와 조작을 보호하면서 제목 자체를 손실시키지 않는다.

**트레이드오프** ECMAScript `String.trim()`은 NBSP까지 제거하므로 Web에 Java 범위를
재현하는 작은 helper가 필요하다. 정규화 뒤 상한은 OpenAPI의 raw `maxLength`로 표현할 수
없고, 수정 서비스가
"원문 유지인지"를 잠근 자료로 한 번 더 판정한다. 기존 장문은 상세에서도 전부 펼치지 않으므로 전체 문구는
접근성 이름이나 브라우저 제목 도움말로 확인해야 한다.

**언제 뒤집는가** 기존 51~200자 자료가 더는 없다고 DB로 확인하고, 외부 클라이언트도 50자
계약으로 전환됐을 때 `varchar(50)` 마이그레이션과 수정 요청 상한 축소를 함께 검토한다.

## 3-3-24 결정 23 — 자유 게시판 댓글을 신설한다

**상태** 승인됨 · 2026-08-31 · [#347](https://github.com/HackerKHU/hacker_HP/issues/347)

**배경** 자유 게시판은 결정 16에서 "댓글 없음"으로 시작했다 — 글 하나를 두고 나눌 대화를 담을 자리가 없다. 결정 20·21이 게시글 자체의 수정·삭제를 열면서, 게시판이 부원 사이의 실제 상호작용 공간으로 쓰이기 시작했다. 댓글이 그 다음 자연스러운 확장이다.

**결정**

| | 논점 | 결정 | 버린 것 |
|---|---|---|---|
| D1 | 본문 형식 | **평문만.** 게시글과 같다(결정 16) | 마크다운·리치텍스트 |
| D2 | 수정·삭제 권한 | **게시글과 동일.** 수정=작성자 본인만(관리자 예외 없음), 삭제=활성 관리자 또는 작성자 본인 | 댓글만 다른 권한 모델(예: 삭제만 열고 수정은 막음) |
| D3 | 구조 | **평면 목록.** 대댓글(중첩) 없음 | 중첩 댓글 |
| D4 | 게시글 삭제 시 처리 | **CASCADE.** 게시글이 지워지면 댓글도 함께 지운다 | 댓글만 남기기 |
| D5 | 작성자 표시 | 게시글과 같은 규칙 (`DisplayName`, 결정 18) | 별도 표시 규칙 |
| D6 | 도배 제한 | **두지 않는다.** #255(게시글 도배 제한, 착수 조건 미충족)와 같은 판단 | 사전 방지형 제한 |
| D7 | 권한 게이팅 | **게시판 조회·작성과 같다** (`ACTIVE`·`INACTIVE`, `PENDING`·`SUSPENDED` 제외) | 별도 권한 체계 |
| — | 정렬 | **오래된순** (`created_at ASC, id ASC`). 게시글 목록(최신순)과 반대 — 대화를 읽는 순서 | 최신순 |
| — | 상한 | **2,000자.** 게시글 본문(10,000자)보다 낮다 — 댓글은 더 가벼운 콘텐츠로 본다 | 같은 10,000자 |

**이유**

**D2, 게시글과 동일** — 이슈를 처음 쓸 때는 "댓글은 가벼운 콘텐츠니 작성자 본인 삭제를 더 쉽게 열 수도 있다"는 여지를 남겼다. 하지만 그 사이 게시글의 삭제 권한 자체가 결정 20에서 관리자 전용으로 시작해 작성자 본인까지 넓어졌다 — 지금 게시글의 최종 모델이 이미 "관리자 또는 작성자 본인 삭제, 작성자 본인만 수정"이다. 댓글만 다른 모델을 새로 만들 이유가 없다 — 같은 게시판 안에서 글과 댓글의 권한이 다르면 부원이 매번 "이건 되고 저건 안 되나"를 헷갈린다.

**D4, CASCADE** — 댓글은 게시글 없이 독립적으로 존재할 수 없다. 게시글이 사라졌는데 댓글만 남으면 화면이 그 댓글을 보여줄 자리가 없다 — 자료 파일이 자료 없이 존재할 수 없는 것과 같은 구조다. `author_id`의 `ON DELETE SET NULL`(회원은 지워도 콘텐츠는 남긴다, 2-2 §2-2-4)과는 의도가 다르다 — 거기서 지우는 것은 "누가 썼는지"이고, 여기서 지우는 것은 "무엇에 달렸는지"다.

**D6, 도배 제한 없음** — #255가 이미 "실제로 관찰되는 문제가 생기기 전에는 만들지 않는다"고 결정했다. 댓글은 게시글보다 진입장벽이 낮아 도배 위험이 이론적으로는 더 크지만, 아직 관찰된 사례가 없는 것은 게시글과 같다. 관찰되면 그때 게시글·댓글을 함께 다룬다.

**상한 2,000자** — 댓글은 짧은 응답·반응이 대부분이라 게시글 본문만큼 길 필요가 없다. 정확한 숫자에 사용자 데이터 근거는 없다 — 지나치게 낮지도 게시글과 같지도 않은 값으로 정했고, 실제 사용 패턴이 쌓이면 조정한다.

**트레이드오프** D2를 게시글과 통째로 묶으면서 "댓글은 더 가벼우니 규칙도 더 가벼워야 한다"는 감각을 반영하지 않았다 — 상한(D6 옆의 2,000자)에서만 그 감각을 반영했다. 상한 숫자와 도배 제한 부재는 실사용 없이 정한 값이라 근거가 약하다.

**언제 뒤집는가**

- **댓글 좋아요·대댓글**이 필요해지면 별도 이슈·결정으로 연다 — 이 결정의 범위 밖이다.
- **도배**가 실제로 관찰되면 #255와 함께 게시글·댓글의 제한을 같이 설계한다.
- **2,000자가 부족하다는 신호**(잘림 문의, 긴 댓글을 여러 개로 쪼개는 패턴)가 쌓이면 상한을 재검토한다.

## 3-3-25 결정 24 — 공지사항에 좋아요를 더한다

**상태** 승인됨 · 2026-09-01 · [#343](https://github.com/HackerKHU/hacker_HP/issues/343)

**배경** 공지는 `ADMIN`만 쓰고 부원은 읽기만 한다. 부원이 그 글에 반응을 남길 방법이 없었다 — 댓글을 달기엔 무겁고(공지는 공지고 토론 게시판이 아니다), 아무 반응 없이 읽고 지나간다.

**결정**

| | 논점 | 결정 | 버린 것 |
|---|---|---|---|
| D1 | 저장 방식 | **`bookmarks`와 같은 `(user_id, notice_id)` 복합 PK.** 누가 눌렀는지 남긴다 | `notes.view_count`류의 단순 카운터 |
| D2 | 취소 가능 여부 | **가능하다.** D1이 이미 그 전제다 | 취소 불가(카운터 방식이었다면 자동으로 이랬을 것) |
| D3 | 권한 | **공지 조회와 같다** (`ACTIVE`·`INACTIVE`) | 별도 권한 체계 |
| D4 | 관리자 전용 콘텐츠에 좋아요가 왜 필요한가 | **공감 표시로 그대로 연다.** 관리자만 쓰는 콘텐츠라도 부원이 반응을 남길 수 있게 한다 | 이 기능 자체를 보류 |
| D5 | 정지·탈퇴 시 처리 | **CASCADE.** `bookmarks`와 같은 판단 — 좋아요는 회원이 지금 누른 사실이 값이라, 탈퇴해도 남길 표시("탈퇴한 회원")가 없다 | 좋아요 주인을 "탈퇴한 회원"으로 표시하고 남기기 |

**이유**

**D1, `bookmarks` 패턴** — 좋아요의 자연스러운 사용자 기대는 "다시 누르면 취소된다"이다. 카운터 컬럼(`notes.view_count`)은 애초에 취소를 표현할 수 없다 — 조회수는 "몇 번 열렸나"를 세는 것이지 "지금 열려 있나"를 추적하지 않으므로 취소 개념이 없다. 좋아요는 다르다: "지금 내가 눌렀나"가 상태이고, 그 상태를 사용자가 바꿀 수 있어야 한다. 이미 이 저장소에 있는 `bookmarks`가 정확히 같은 모양(복합 PK, 있거나 없거나, 양쪽 CASCADE)이라 새 패턴을 만들 이유가 없다.

**D4, 공감 표시로 그대로 연다** — 공지가 관리자 전용 콘텐츠라는 사실이 좋아요를 막을 이유는 아니다. 부원이 글을 쓰는 것이 아니라 글을 향한 반응을 남기는 것이라 작성 권한과 무관하다. "이 공지를 봤다·동의한다·중요하게 여긴다"는 신호를 관리자가 얻을 수 있다는 점에서 오히려 관리자 전용 콘텐츠에 더 유용할 수 있다.

**D5, CASCADE** — `notice_likes`는 `notices.author_id`(`SET NULL`, "탈퇴한 회원" 표시)와 다른 성격이다. 작성자 표시는 "누가 이 글을 남겼나"라는 콘텐츠의 일부라 회원이 나가도 보존하지만, 좋아요는 "그 회원이 지금 이 글에 공감한다"는 실시간 상태라 회원이 사라지면 그 상태 자체가 성립하지 않는다. `bookmarks`가 이미 같은 결론을 냈다(§3-2-2).

**트레이드오프** 몇 명이 좋아요를 눌렀는지는 정확하지만, "그 반응이 지금도 유효한가"는 회원 상태(정지·비활동)와 무관하게 그대로 집계에 남는다 — 정지된 회원의 과거 좋아요도 개수에 포함된다. 이 정도 오차는 감수한다.

**언제 뒤집는가**

- **다른 도메인(자료·자유게시판·갤러리)의 좋아요**는 각각 별도 이슈(#344·#345·#346)에서 같은 패턴을 검토하되, 그 도메인의 사정(예: 자료는 이미 즐겨찾기가 있다)에 따라 다르게 결정할 수 있다.
- **좋아요 알림**(작성자에게 누가 눌렀는지 알림)이 필요해지면 별도 결정으로 연다.
- **좋아요 이력**(언제 취소했는지 등)이 필요해지면 CASCADE 삭제 대신 소프트 삭제나 별도 이력 테이블을 검토한다 — 지금은 그 값을 두지 않는다.
