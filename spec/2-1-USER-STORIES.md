# 2-1. 사용자 스토리

승인된 부원(`USER`)이 이 사이트에서 하려는 일과, 각 기능의 완료 조건을 잡아준다. 관리자 전용 기능은 [2-2](2-2-OPERATOR-REQUIREMENTS.md)에 있다.

**전제가 기능마다 다르다** (2026-08-26, [#228](https://github.com/HackerKHU/hacker_HP/issues/228)). **자료(§2-1-1 ~ §2-1-5)는 `ACTIVE`만** 쓸 수 있고, **나머지(§2-1-6 ~ §2-1-9)는 `ACTIVE`와 `INACTIVE`가 함께** 쓴다. 이 문서를 읽고 공통 `ACTIVE` 가드 하나로 묶으면 **비활동 부원이 공지·활동사진·게시판에서도 막혀** 이 구분이 통째로 사라진다. 권한 조합은 [3-1](3-1-DESIGN-ARCHITECTURE.md) 매트릭스가 원본이다.

> **출시 단계** — MVP에는 공개 랜딩(정적, [3-3 결정 8](3-3-DESIGN-DECISIONS.md#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다))과 공지 조회·관리, 인증 화면을 포함한다. 자료·즐겨찾기·활동사진은 요구사항을 유지하되 `Post Launch`에서 구현한다 ([1-BACKGROUND §1-6](1-BACKGROUND.md#1-6-1차-출시-범위)).

```text
§2-1-1   자료 목록·검색·필터    쌓인 정리본에서 원하는 것을 찾는다
§2-1-2   자료 업로드            정리본을 올린다
§2-1-3   자료 수정·삭제         내가 올린 것을 고치거나 지운다
§2-1-4   자료 다운로드          파일을 받는다
§2-1-5   즐겨찾기               다시 볼 자료를 표시한다
§2-1-6   공지                   공지를 읽는다
§2-1-7   활동 사진              사진을 본다
§2-1-8   자유 게시판            부원끼리 글을 올리고 읽는다
§2-1-9   마이페이지             내 정보를 보고, 원하면 탈퇴한다
§2-1-10  화면 목록              위 기능이 어떤 화면으로 묶이는가
```

자료는 시험 정리본과 과목 정리본을 통칭하며, `category` 필드로만 구분된다. 데이터 구조와 기능은 동일하다.

| category | 설명 | 추가 필드 |
|---|---|---|
| `EXAM` | 시험 정리본 | `exam_type` (중간/기말) 필수 |
| `SUBJECT` | 과목 정리본 | `exam_type` 미사용 (NULL) |

> **비활동 부원(`INACTIVE`)은 자료 갈래 전체를 쓸 수 없다** (MUST, 2026-08-26 [#228](https://github.com/HackerKHU/hacker_HP/issues/228)). 아래 §2-1-1 ~ §2-1-5가 모두 그 대상이다 — 목록·검색·상세·다운로드·업로드·수정·삭제·즐겨찾기. 매 학기 활동하는 사람만 자료를 받아 가게 하려는 것이고, 공지·활동사진·자유 게시판은 그대로 열려 있다 ([3-1 §3-1-2](3-1-DESIGN-ARCHITECTURE.md#비활동-부원inactive은-자료만-막힌다)).

## 2-1-1 자료 목록·검색·필터

**목록** — 카테고리별로 조회하며 페이지네이션을 지원한다 (MUST). 기본 정렬은 최신순이고 제목순을 MAY 제공한다. **조회수순은 MUST다** (아래 조회수 참고) — 계약이 `sort=views`를 받게 되어 있어([3-2 §3-2-4](3-2-DESIGN-CONTRACT.md)) 고를 수 없으면 그 값이 갈 곳이 없다.

**검색** — 제목·과목명·교수명을 단일 키워드로 통합 검색한다 (MUST). 필드를 나눠 입력받지 않는다.

**필터**

| 필터 | 값 |
|---|---|
| 과목 | 등록된 과목명 목록 |
| 교수 | 등록된 교수명 목록 |
| 연도 | 등록된 연도 목록 |
| 학기 | 1학기 / 여름 계절학기 / 2학기 / 겨울 계절학기 |
| 시험 구분 | 중간 / 기말 (`EXAM`에만 노출) |

**학기는 네 값이다** (2026-08-29, [#272](https://github.com/HackerKHU/hacker_HP/issues/272)). 계절학기에 만든 정리본을 올릴 방법이 없었다. **학사 순서대로 보여준다** — 1학기 → 여름 → 2학기 → 겨울. `enum`으로 고정된 값이라 필터 옵션은 등록 현황과 무관하다 ([3-2 §3-2-4](3-2-DESIGN-CONTRACT.md) — `GET /notes/filters`가 학기를 담지 않는 이유).

> 서버가 네 값을 받는 것과 화면이 넷을 보여주는 것은 다른 작업이다. 화면은 [#273](https://github.com/HackerKHU/hacker_HP/issues/273)이 맡는다 — **그 전까지 업로드 폼과 필터에는 두 값만 뜬다.** 서버가 먼저 받게 해 두지 않으면 화면이 없는 값을 보내 `400`이 된다.

검색어와 필터는 **AND 조건**으로 함께 적용된다 (MUST). 필터 옵션 목록은 실제 등록된 값에서 만든다.

**조회수** (2026-08-29 확정, [#244](https://github.com/HackerKHU/hacker_HP/issues/244)) — 자료가 몇 번 열렸는지 센다. **목록에 숫자를 보이고 조회수순 정렬을 제공한다** (MUST) — 정렬만 되고 숫자가 안 보이면 왜 그 순서인지 알 수 없다.

**상세를 여는 것이 1회다** (MUST). 목록에 뜨는 것은 세지 않는다. 스크롤만 해도 오르면 이 숫자는 "몇 번 열렸나"를 뜻하지 못하고, 한 번 훑을 때마다 스무 건이 함께 오른다.

**같은 사람이 다시 열면 다시 센다.** 새로고침해도 오르고, 올린 사람이 자기 자료를 열어도 오른다. **중복을 걸러내지 않기로 한 결과다** — 걸러내려면 (회원, 자료) 쌍을 남겨야 하고, 그 표는 회원이 지워질 때(관리자 제거·본인 탈퇴 두 경로다) 함께 지워져야 한다. 부원 수십 명 규모에서 새로고침이 만드는 왜곡보다 **표 하나와 삭제 규칙이 더 비싸다.**

> 그 대가로 **이 숫자는 "몇 명이 봤나"가 아니다.** 인기 자료 랭킹처럼 정확도가 필요한 것을 여기에 얹으려면 세는 규칙부터 다시 정해야 하고, 그때 이미 쌓인 값은 **이전 규칙의 값으로 남는다.** 그 경계를 사후에 표시할 방법이 없다.

**누가 언제 봤는지는 남기지 않는다** (MUST). 이 기능의 목적이 아니고, 남기는 순간 개인정보가 는다.

**완료 조건** — 자료가 100건 쌓인 상태에서 과목명 일부를 입력하면 해당 과목 자료만 20건 단위로 페이징되어 나온다.

## 2-1-2 자료 업로드

입력: 카테고리, 제목, 과목명, 교수명, 연도, 학기, (시험 구분), 파일

- 파일은 1개 이상 첨부하며 다중 첨부를 허용한다 (MUST).
- 허용 확장자와 최대 용량은 설정값으로 제한한다 (MUST). 권장: `pdf, docx, pptx, hwp, zip, png, jpg` / 파일당 20MB / 최대 10개.
- 업로드자는 로그인 사용자로 자동 기록된다 (MUST).

**업로드 흐름** (MUST) — 서버는 파일 바이트를 직접 받지 않는다.

```text
① 브라우저 → 서버   presigned PUT URL 요청 (파일명·크기)
② 브라우저 → S3     파일을 직접 업로드 (서버를 거치지 않음)
③ 브라우저 → 서버   메타데이터 + 업로드된 파일 키 목록 등록
```

이 구조 덕분에 Vercel 프록시의 요청 본문 제한(4.5MB)에 걸리지 않는다. 20MB 제한은 presigned URL 발급 조건으로 강제한다 — **presigned PUT은 용량을 강제할 수 없으므로, presigned POST의 `content-length-range`를 쓰거나 ③ 단계에서 `HeadObject`로 크기를 검증하고 초과분을 삭제해야 한다** (MUST).

## 2-1-3 자료 수정·삭제

- 본인이 업로드한 자료만 수정·삭제할 수 있다 (MUST). `ADMIN`은 전체 가능하다.
- 수정은 메타데이터 변경과 첨부파일 추가·삭제를 지원한다.
- 삭제 시 연결된 첨부파일 레코드와 즐겨찾기 레코드를 함께 제거한다 (MUST). DB 제약(`ON DELETE CASCADE`)으로 보장하며 애플리케이션 코드에만 의존하지 않는다.
- S3 오브젝트도 함께 삭제한다 (SHOULD). 남아도 접근 경로는 없지만 저장 비용이 쌓인다.
- **정리 실패가 응답을 바꾸지 않는다** (2026-08-22, #54). DB는 이미 커밋됐고 사용자에게 삭제는 끝난 일이다 — 여기서 실패로 답하면 **재요청해도 자료가 없어 영원히 실패한다.** 실패한 키는 로그에 남겨 사람이 찾아 지울 수 있게 한다.
- **수정은 보낸 것으로 통째로 바꾼다** (2026-08-22, #54). 첨부는 "남길 것 전부"를 보내고, 빠진 것은 삭제된다. **업로더는 바뀌지 않는다** (MUST) — 관리자가 남의 자료를 고쳐도 그렇다. 업로더는 "누가 이 자료를 제공했나"이지 "누가 마지막에 만졌나"가 아니다.

## 2-1-4 자료 다운로드

- 로그인한 `ACTIVE` 사용자만 다운로드할 수 있다 (MUST).
- 파일 바이트는 서버를 거치지 않는다. 서버가 **짧은 유효시간의 presigned GET URL**을 발급하고, 브라우저가 그 URL로 S3에서 직접 받는다 (MUST).
- **영구적인 공개 URL은 존재하지 않는다** (MUST). S3 버킷은 완전 비공개이며 퍼블릭 액세스 차단이 켜져 있다.

## 2-1-5 즐겨찾기

- 자료 상세와 목록에서 추가·해제할 수 있다.
- `(회원, 자료)` 조합은 유일하다 (MUST). 복합 PK로 중복 등록을 막는다.
- **별도 화면이 아니라 자료게시판의 필터다** (2026-08-25, #261). 담아둔 자료를 보는 것은 다른 목적지가 아니라 **그 목록을 추리는 방법**이라, 자료게시판에 "즐겨찾기만 보기" 토글을 둔다 — 갈래를 탭으로 접은 것과 같은 판단이다 (§2-1-10). 그 상태는 주소에 남긴다(`?bookmarked=true`).
- **토글이 켜지면 검색·필터·갈래 탭이 사라진다.** `GET /bookmarks`가 그것을 받지 않기 때문이다 ([3-2 §3-2-4](3-2-DESIGN-CONTRACT.md) — "이미 본인이 추린 목록이다"). 남겨 두고 눌러도 안 먹으면 화면이 거짓말을 한다. 대신 **갈래 열을 보여준다** — 시험·과목이 섞여 오기 때문이다.
- **옛 `/bookmarks` 주소는 그 상태의 자료게시판으로 보낸다** — 공유했거나 북마크해 둔 사람이 빈 화면을 보면 안 된다.

## 2-1-6 공지

- 목록에서 **고정 공지가 최상단**에 오고 그 아래 일반 공지가 최신순으로 정렬된다 (MUST). 정렬 기준은 `is_pinned DESC, created_at DESC`다.
- 고정 공지는 목록에서 시각적으로 구분한다 (SHOULD).
- 고정 개수 상한은 두지 않되, 여러 개가 고정되면 등록일 최신순으로 정렬한다.
- 등록·수정·삭제·고정 토글은 `ADMIN` 전용이다 ([2-2](2-2-OPERATOR-REQUIREMENTS.md)).

## 2-1-7 활동 사진

- 최신순 그리드로 표시하며 페이지네이션을 지원한다.
- 각 이미지는 개별 레코드로 저장된다. **앨범 그룹은 두지 않는다.**
- 업로드·삭제는 `ADMIN` 전용이다.

**리사이즈** — 서버가 업로드된 이미지를 변환 후 저장한다 (MUST). 권장 기준은 가로 최대 1920px, 비율 유지, JPEG 품질 85이며, 기준 미만 이미지는 원본을 유지한다. 허용 형식은 `jpg`, `jpeg`, `png`다.

**업로드 경로** — 원본은 presigned PUT으로 브라우저가 S3에 직접 올리고, 서버는 그 원본을 읽어 리사이즈한 뒤 최종 위치에 저장한다 (확정, [1-BACKGROUND §1-5](1-BACKGROUND.md) #5). multipart로 원본을 서버가 그대로 받는 방식은 Vercel 프록시 본문 제한(4.5MB)에 걸려 채택하지 않는다 — presigned PUT과 서버의 S3 읽기는 둘 다 Vercel을 거치지 않으므로 이 제한과 무관하다. 절차는 [3-2 §3-2-5](3-2-DESIGN-CONTRACT.md)를 따른다.

## 2-1-8 자유 게시판

- 부원끼리 자유롭게 글을 올리고 읽는다. **글 쓰기와 목록·상세 보기가 전부다.**
- 목록은 **최신순**이다. 정렬 기준은 `created_at DESC, id DESC`이며 **정렬 옵션을 받지 않는다** (MUST).
- 작성자는 **로그인한 사람으로 자동 기록된다** (MUST). 본문으로 받지 않는다.
- 본문은 **평문으로만 다룬다** (MUST). 아래를 보라.

**목록은 본문을 담지 않는다** (MUST). 상세에서만 준다 — 자료 목록이 파일을 개수만 담는 것과 같은 판단이다. 본문 상한이 10,000자인데 그것이 20건 실리면 목록 응답이 그것만으로 200KB가 된다. 앞 몇 글자를 미리보기로 담는 방식은 **자를 위치를 서버가 정하게 되고**, 나중에 길이를 바꾸면 계약이 바뀐다. 필요해지면 그때 더한다.

**정렬 옵션을 받지 않는 이유는 둘이다.** 하나는 [3-2 §3-2-4](3-2-DESIGN-CONTRACT.md)의 "정렬의 마지막 기준은 언제나 `id`다"(MUST)를 지키는 가장 단순한 방법이기 때문이고 — 같은 시각에 올라온 글이 있으면 페이지를 넘길 때마다 배치가 달라져 **같은 글이 두 번 보이거나 아예 빠진다.** 다른 하나는 받지 않으면 **이상한 값으로 서버가 터질 자리가 없기 때문이다** (자료 목록이 `sort=bogus` 하나로 `500`이 났던 적이 있다, #52).

### 본문은 평문이다

**마크다운·리치텍스트·HTML을 받지 않는다** (MUST, [3-3 결정 16](3-3-DESIGN-DECISIONS.md#3-3-17-결정-16--자유-게시판은-평문불변으로-시작한다)). 저장도 평문, 응답도 평문이고, 화면은 줄바꿈만 살려 텍스트 노드로 그린다.

**전 부원이 쓰는 자리라 공지와 위험도가 다르다.** 공지는 `ADMIN`만 쓰지만 게시판은 승인된 모든 부원이 쓴다 — 서식을 허용하는 순간 그 입력이 다른 부원의 브라우저에서 실행될 수 있는 표면이 생긴다. 서식이 정말 필요해지면 **그때 새 결정으로 기록하고 정화(sanitize) 방식을 함께 정한다.**

### 길이 상한

| | 상한 | 근거 |
|---|---|---|
| 제목 | **200자** | `notices.title`과 같다. 같은 종류의 값은 같은 상한을 쓴다 |
| 본문 | **10,000자** | 부원이 쓸 글로는 넉넉하다. 상한이 없으면 `TEXT`는 무제한이라 **글 하나로 목록 응답이 망가진다** |

**DB 제약과 요청 검증 양쪽에 건다** (MUST). 검증만 두면 다른 경로로 들어온 값이 새고, DB에만 두면 위반이 사용자 오류가 아니라 `500`으로 나간다.

### 작성자가 나가면

**글은 남고 작성자 자리만 빈다.** 응답의 작성자 이름은 서버가 "탈퇴한 회원"으로 채운다 — 자료·공지와 같은 규칙이다 ([2-2 §2-2-4](2-2-OPERATOR-REQUIREMENTS.md#2-2-4-회원-제거), [3-2 §3-2-2](3-2-DESIGN-CONTRACT.md)).

그래서 `posts.author_id`는 **`ON DELETE SET NULL`이어야 한다** (MUST). 빠뜨리면 **글을 한 번이라도 쓴 회원은 삭제 자체가 FK 위반으로 실패한다** — `notices.author_id`가 정확히 그 상태로 만들어져 뒤늦게 마이그레이션으로 고쳤다 (#58).

### 수정·삭제는 없다

**이번 범위에 넣지 않는다** ([3-3 결정 16](3-3-DESIGN-DECISIONS.md#3-3-17-결정-16--자유-게시판은-평문불변으로-시작한다)). 그 결과를 분명히 해 둔다 — **잘못 올린 글을 아무도 지울 수 없다. 관리자도 마찬가지다.** 자유 서술이 쌓이는 자리에서 오래 갈 상태가 아니므로 관리자 삭제를 후속으로 잡아 두었다 ([#238](https://github.com/HackerKHU/hacker_HP/issues/238)) — 그때 [2-2 §2-2-6](2-2-OPERATOR-REQUIREMENTS.md#2-2-6-콘텐츠-관리) 표에 게시판 행이 생긴다.

댓글·좋아요·첨부파일·카테고리·검색도 범위 밖이다.

## 2-1-9 마이페이지

*(2026-08-28 확정, [#223](https://github.com/HackerKHU/hacker_HP/issues/223). 구현은 [#178](https://github.com/HackerKHU/hacker_HP/issues/178)·[#225](https://github.com/HackerKHU/hacker_HP/issues/225)·[#226](https://github.com/HackerKHU/hacker_HP/issues/226)이다.)*

내 정보를 보는 화면이고, 계정을 지우는 자리도 여기다.

### 보기 전용이다

**고치는 기능을 두지 않는다** (MUST). 승인 후 정보 정정은 이 범위 밖이다.

값마다 이유가 다르다. **이름**은 구글 프로필에서 오고 신청서로도 바꿀 수 없다 ([3-1 §3-1-4](3-1-DESIGN-ARCHITECTURE.md#3-1-4-auth-01-가입-신청)) — 여기서만 열면 그 결정이 뒤집힌다. **학번·학과**는 관리자가 승인 심사에 쓴 값이라, 승인 뒤에 본인이 갈아치우면 **심사한 내용과 저장된 내용이 달라진다.** 바꿔야 할 사정이 생기면 정정 경로를 따로 설계하는 것이 결정이고, 조회 화면에 입력란을 더하는 것은 결정이 아니다.

**새 조회 API가 필요 없다** — `GET /auth/me`가 이름·이메일·학번·학과·상태·가입 신청일·승인일을 이미 전부 내려준다 ([3-2 §3-2-3](3-2-DESIGN-CONTRACT.md#get-authme--세션-확인)).

### 회원 탈퇴

**관리자의 회원 제거와 같은 처리다** (MUST). 자료·공지·활동사진·게시글은 남고 작성자 표시만 "탈퇴한 회원"이 되며, 즐겨찾기는 함께 지워진다. 규칙 원본은 [2-2 §2-2-4](2-2-OPERATOR-REQUIREMENTS.md#2-2-4-회원-제거)이고 **여기서 다시 정의하지 않는다** — 두 벌이 되면 한쪽만 고쳐진다.

**확인 창이 남을 콘텐츠 건수를 보여준다** (MUST) — 자료·공지·활동사진·게시글 각각. 관리자 제거보다 여기서 더 쓸모 있다: 관리자는 건수를 보고 **지울지 남길지 정할 뿐**이지만, **본인은 창을 닫고 직접 지운 뒤 다시 올 수 있다.** 계정이 사라지고 나면 로그인할 수 없어 손댈 방법이 없다.

**마지막 활성 관리자는 탈퇴할 수 없다** (MUST). 관리자가 0명이 되면 아무도 가입을 승인할 수 없다 ([2-2 §2-2-7](2-2-OPERATOR-REQUIREMENTS.md#2-2-7-안전장치)) — 남이 지우든 본인이 나가든 결과가 같으므로 규칙도 같다.

**같은 구글 계정으로 다시 가입할 수 있다** (MUST). 탈퇴는 계정 레코드를 지우므로
`google_sub`·`email` UNIQUE를 붙잡는 행이 남지 않고, 다음 로그인에서 새 계정을 만든다.
가입 거부는 다르다 — 계정을 유지한 채 신청 정보만 비워 미승인으로 되돌리고, 같은 id로
다시 신청한다 ([2-2 §2-2-2](2-2-OPERATOR-REQUIREMENTS.md#2-2-2-가입-승인거부)).

**승인을 기다리는 중에도 탈퇴할 수 있다** (MUST). `PENDING`을 빼면 **본인이 자기 계정을 지울 방법이 없다.** 관리자는 지울 수 있다 — 신청 전 계정도 회원 목록에는 나온다 ([5-TESTING T-48](5-TESTING.md#5-2-필수-테스트-사례)) — 하지만 `applied_at IS NULL`이라 **승인 목록(`status=PENDING&applied=true`)에는 뜨지 않아** 관리자가 알아서 치워 주기를 기대할 수 없고, 개인정보처리방침 §6이 고지하는 *"삭제를 요구할 수 있다"* 를 **본인이 스스로 실행할 경로가 없다.** 승인을 기다리다 마음이 바뀌는 것은 드문 일도 아니다.

> **그래서 진입점이 두 곳이다.** `PENDING`은 마이페이지를 볼 수 없으므로([3-1 §3-1-6](3-1-DESIGN-ARCHITECTURE.md#3-1-6-auth-04-신청대기-화면) — 인증 화면 중 유일하게 볼 수 있는 곳이 신청·대기 화면이다), **탈퇴 버튼을 신청·대기 화면에도 둔다.** 승인을 기다리다 마음이 바뀐 사람이 있는 자리가 거기다.

**`SUSPENDED`는 이 경로에 닿지 못한다.** 로그인 자체가 차단되고([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md#3-1-5-auth-02-로그인--auth-03-로그아웃)) 상태 필터가 보호 API를 열지 않으므로 **따로 막을 규칙이 필요 없다.** 열려 있었다면 정지된 사람이 탈퇴 후 재가입으로 정지를 지웠을 것이다.

**재인증을 요구하지 않는다.** 구글 OAuth라 확인할 비밀번호가 없다. 확인 창과 건수 표시가 그 자리를 대신한다.

> **개인정보처리방침은 탈퇴가 배포되는 PR이 함께 고친다** (MUST, 2026-08-28 결정). 방침을 미리 고치면 **없는 기능을 실제 이용자에게 고지하게 된다** — [#254](https://github.com/HackerKHU/hacker_HP/pull/254)에서 같은 실수를 하고 리뷰에서 잡혔다. **#226이 그 체크박스를 들고 갔다** (2026-08-29): §5에 본인 탈퇴와 재가입을, §6에 마이페이지 열람과 두 곳의 탈퇴 경로를 적었다. 반대 방향도 같은 잘못이다 — **있는 길을 방침에서 빼면** 스스로 할 수 있는 것을 문의처로 떠넘기게 된다.

### 완료 조건

- 마이페이지에서 내 이름·이메일·학번·학과·상태·가입 신청일·승인일을 본다. **고칠 수 있는 입력란이 없다.**
- 탈퇴 확인 창이 남을 콘텐츠 **네 갈래의 건수**를 보여준다.
- 탈퇴하면 다시 로그인할 수 없고, **같은 구글 계정으로 새로 가입할 수 있다.**
- 승인 대기 중인 계정도 신청·대기 화면에서 탈퇴할 수 있다.

### 공통 목록 페이지네이션

공지·자료게시판(전체·즐겨찾기)·갤러리·자유게시판·회원 관리 목록은 한 공통 pager를 쓴다
(MUST). 순서는 `이전` → 직접 누르는 1-based 페이지 번호 → `다음`이며, 각 번호의 accessible
name은 `{n}페이지로 이동`, 현재 번호는 `aria-current="page"`다. `이전`·`다음`의 시각
텍스트는 767px 이하에서 공간을 위해 감추되 한국어 accessible name은 유지한다.

767px 이하에서는 숫자 버튼을 최대 5개, `md`(768px) 이상에서는 최대 10개 보인다. 총
페이지 수가 상한 이하면 모두 보이고, 넘으면 첫·마지막과 현재 주변의 연속된 창만 남긴다.
실제로 감춘 페이지가 있는 간격에만 비대화형 `…`를 한 번 표시한다. 반응형으로 감춘 번호는
접근성 트리와 tab 순서에서도 빠져야 하며, viewport마다 현재 페이지는 정확히 하나다.

페이지 이동은 기존 URL query와 필터를 보존하고 API에는 0-based `page`를 보낸다. 1페이지는
`page=0` 대신 `page` 파라미터를 지운다. 첫 페이지의 `이전`과 마지막 페이지의 `다음`은
비활성화하며 눌러도 URL이나 조회를 바꾸지 않는다. pager는 좁은 화면에서 줄바꿈할 수 있고
페이지 전체의 가로 overflow를 만들지 않는다.

**별도 가입 화면(`/signup`)은 없다.** 가입과 로그인이 같은 구글 버튼이기 때문이다 ([3-3 결정 13](3-3-DESIGN-DECISIONS.md#3-3-14-결정-13--가입로그인을-구글-oauth로-한다)). 이전에 안내했거나 저장된 `/signup` 주소로 들어오면 **로그인 화면으로 보낸다** — 랜딩으로 보내면 가입하러 온 사람이 다시 길을 찾아야 한다.

> 위 표는 **한 표다.** 예전에는 이 문단이 표 가운데를 갈라 `Post Launch` 행들이 머리글 없는 별개 표로 그려졌다 (2026-08-28에 고쳤다).

**위 표의 `ACTIVE`에서 자료 세 화면만 `INACTIVE`를 뺀다** (MUST, 2026-08-26 #228). 자료게시판·자료 상세·자료 등록/수정이다. 나머지는 비활동 부원도 그대로 쓴다 — **가드가 그것보다 넓게 잡히면 로그인은 되는데 갈 곳이 없는 사람이 생긴다.**

> 비활동 부원이 자료 화면에 닿았을 때 **로그인 화면으로 내보내지 않는다** ([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md#클라이언트가-세션-상태를-바꾸는-근거)). 로그인은 되어 있고 다른 화면은 멀쩡히 쓰는 상태다. 무엇을 보여줄지는 [#231](https://github.com/HackerKHU/hacker_HP/issues/231)이 정한다.

**즐겨찾기는 별도 화면이 아니다** (2026-08-25, #261). 자료게시판의 "즐겨찾기만 보기" 토글로 접혔다 — 담아둔 자료를 보는 것은 다른 목적지가 아니라 그 목록을 추리는 조건이다. 근거와 제약은 [§2-1-5](#2-1-5-즐겨찾기)에 있다.

**활동사진 화면의 이름은 "갤러리"다** (2026-08-23, #60). §2-1-7이 정의하는 것은 여전히 활동사진이고 라우트도 `/photos`지만, **화면 이름은 사용자에게 보이는 모든 자리에서 이 하나를 쓴다** — 헤더 메뉴·화면 제목·돌아가기 링크가 서로 다른 이름으로 부르면 같은 곳인지 알 수 없다. 회원 제거 확인 창처럼 **콘텐츠의 갈래를 세는 자리는 그대로 "활동사진"이다** ([2-2 §2-2-4](2-2-OPERATOR-REQUIREMENTS.md#2-2-4-회원-제거)) — 거기서 세는 것은 화면이 아니라 사진이다.

**자료게시판은 한 화면이고 갈래는 탭으로 가른다** (2026-08-23, #59). 시험 정리본과 과목 정리본은 `category` 하나만 다르고 검색·필터·정렬·페이지네이션 규칙이 전부 같다(§2-1-1). 화면을 나누면 메뉴도 둘이 되어 **"자료를 보러 간다"는 한 가지 일이 두 갈래로 갈린다** — 갈래는 거기서 고르는 조건이지 다른 목적지가 아니다.

**선택한 갈래는 주소에 남긴다** (MUST). `?category=EXAM|SUBJECT`이며 이름은 API 파라미터와 같다(§3-2-4). 새로고침·뒤로가기·링크 공유에 살아남아야 하고, 경로 조각(`/notes/{category}`)으로 두지 않는 이유는 그 패턴이 자료 상세(`/notes/{id}`)까지 삼키기 때문이다.

랜딩은 **한 페이지**다. 동아리 소개·활동사진·통계·FAQ·후원은 섹션 앵커로 이동하며 섹션마다 별도 라우트를 만들지 않는다 (MUST). 다만 **개인정보처리방침과 이용약관은 랜딩 섹션이 아니라 별도 법적 문서**이므로 `/privacy`·`/terms` 라우트를 따로 가진다 — 앵커로 넣지 않는다. 둘 다 **가드를 붙이지 않는다** — 정지된 사람도 자기가 무엇을 어겼다는 것인지 읽을 수 있어야 한다. 콘텐츠는 코드에 포함하고 API를 쓰지 않는다 ([3-3 결정 8](3-3-DESIGN-DECISIONS.md#3-3-9-결정-8--공개-랜딩-페이지를-1차-출시에-포함하고-정적으로-구현한다)).
