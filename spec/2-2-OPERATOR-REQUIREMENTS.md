# 2-2. 운영자 요구사항

관리자(`ADMIN`)가 이 사이트를 유지하기 위해 해야 하는 일을 잡아준다. 가입 승인제가 제품의 전제이므로, 여기 적힌 회원 관리가 실질적인 운영 업무의 전부다.

```text
§2-2-1   회원 목록          누가 있는지 본다
§2-2-2   가입 승인·거부      신청을 처리한다
§2-2-3   회원 상태 변경      정지·해제한다
§2-2-4   회원 제거          계정을 지운다
§2-2-5   권한 부여·회수      관리자를 늘리고 줄인다
§2-2-6   콘텐츠 관리        공지·사진을 관리한다
§2-2-7   안전장치           관리자가 스스로를 잠그지 못하게 한다
```

## 2-2-1 회원 목록

- 표시 항목: 이름, 학번, 이메일, Role, Status, 가입 신청일, 승인일
- 검색: 이름, 학번, 이메일
- 필터: Status, Role
- 정렬: 이름, 학번, 가입 신청일
- 페이지네이션 지원

## 2-2-2 가입 승인·거부

가입 신청은 계속 쌓이므로 **한 건씩 처리하는 UI로는 운영이 안 된다.**

- `PENDING` 목록에서 체크박스로 여러 명을 선택해 한 번에 처리한다 (MUST).
- 전체 선택 체크박스를 제공한다 (MUST).
- **승인**: `PENDING` → `ACTIVE`, 승인일시를 기록한다.
- **거부**: 계정 레코드를 삭제한다. 별도 상태를 두지 않는다 — 거부된 사용자는 재신청할 수 있다.
- 처리 전 확인 다이얼로그를 표시하고, 처리 결과(성공/실패 건수)를 안내한다 (MUST).

## 2-2-3 회원 상태 변경

- `ACTIVE` ↔ `SUSPENDED` 전환
- 정지된 회원은 **즉시 로그인이 차단된다** (MUST). 이미 로그인된 세션도 다음 요청에서 차단되어야 한다.

## 2-2-4 회원 제거

- 계정을 삭제한다.
- 해당 회원이 업로드한 자료의 처리 정책이 필요하다. 권장은 자료를 유지하고 업로더 표시만 "탈퇴한 회원"으로 대체하는 것이다.

> **상태: 미결정** — 위 처리 정책이 확정되지 않았다 ([1-BACKGROUND §1-5](1-BACKGROUND.md) #4). 자료를 함께 지우면 다른 부원이 참조하던 정리본이 사라지므로, 착수 전에 결정해야 한다.

## 2-2-5 권한 부여·회수

- `USER` ↔ `ADMIN` 전환
- 대상 회원의 Role만 바꾼다. Status는 건드리지 않는다.

## 2-2-6 콘텐츠 관리

| 대상 | 관리자가 할 수 있는 것 |
|---|---|
| 공지 | 등록, 수정, 삭제, 상단 고정 토글 |
| 활동 사진 | 다중 업로드, 삭제 |
| 자료 | 타인이 올린 자료도 수정·삭제 가능 |

공지·사진의 동작 상세는 [2-1 §2-1-6, §2-1-7](2-1-USER-STORIES.md)에 있다.

## 2-2-7 안전장치

**마지막 관리자가 사라져 시스템에 아무도 접근할 수 없게 되는 상황을 막는다.**

- **본인 계정은 권한 회수 대상에서 제외한다** (MUST). UI에서 버튼을 비활성화하고, 서버에서도 `요청자 id == 대상 id`인 경우 `403`으로 차단한다.
- **본인 계정 삭제도 동일하게 차단한다** (MUST).
- 두 검사 모두 서버 측에서 수행한다. UI 비활성화만으로는 API 직접 호출을 막지 못한다.

> 관리자가 한 명뿐일 때 그 계정이 스스로를 강등하면 복구 수단이 DB 직접 수정밖에 없다. 최초 관리자 계정 생성 방법이 아직 미결정이라([1-BACKGROUND §1-5](1-BACKGROUND.md) #3) 복구 절차도 확정되지 않았다.
