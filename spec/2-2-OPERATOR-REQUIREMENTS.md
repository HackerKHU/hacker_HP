# 2-2. 운영자 요구사항

관리자(`ADMIN`)가 이 사이트를 유지하기 위해 해야 하는 일을 잡아준다. 가입 승인제가 제품의 전제이므로, 여기 적힌 회원 관리가 실질적인 운영 업무의 전부다.

> **출시 단계** — MVP에는 회원 목록, 가입 승인, 회원 상태 관리, 공지 관리만 포함한다. 가입 거부, 회원 제거, 관리자 권한 부여·회수, 자료·사진 관리는 `Post Launch`에서 구현한다.

```text
§2-2-1   회원 목록          누가 있는지 본다
§2-2-2   가입 승인·거부      신청을 처리한다
§2-2-3   회원 상태 변경      정지·해제한다
§2-2-4   회원 제거          계정을 지운다
§2-2-5   권한 부여·회수      관리자를 늘리고 줄인다
§2-2-6   콘텐츠 관리        공지·사진을 관리한다
§2-2-7   안전장치           관리자가 스스로를 잠그지 못하게 한다
```

## 2-2-1 회원 목록

- 표시 항목: 이름, 학번, 학과, 이메일, Role, Status, 가입 신청일, 승인일
- 검색: 이름, 학번, 이메일
- 필터: Status, Role
- 정렬: 이름, 학번, 가입 신청일
- 페이지네이션 지원

페이지 번호 창·한국어 라벨·0-based URL·경계 비활성화·767/768px 반응형 규칙은 모든 목록의
공통 계약([2-1 §2-1-10](2-1-USER-STORIES.md#공통-목록-페이지네이션))을 따른다 (MUST).
회원 목록에서 번호·이전·다음 이동은 기존 검색·상태·권한·정렬 query를 모두 보존한다.

회원 목록의 체크박스는 status·role과 무관하게 **현재 페이지에 보이는 모든 행**을 고른다
(MUST, 2026-08-30, #297). 헤더 체크박스도 현재 페이지만 전체 선택하며 다른 페이지나
검색 결과 전체를 선택하지 않는다. 검색어·상태·권한·정렬·페이지가 바뀌면 선택과 열린
확인 창을 함께 해제하고 그 이유를 알린다.

**"가입 신청일"은 `applied_at`(신청서 제출 시각)이다** (MUST). 계정 생성 시각(`created_at`, 첫 구글 로그인)이 아니다 — 둘은 며칠 차이가 날 수 있다 ([3-2 §3-2-2](3-2-DESIGN-CONTRACT.md), [3-3 결정 13](3-3-DESIGN-DECISIONS.md#3-3-14-결정-13--가입로그인을-구글-oauth로-한다)). 표시·정렬 모두 이 필드를 쓴다.

## 2-2-2 가입 승인·거부

가입 신청은 선택 승인·거부와 행별 처리 두 경로로 다룬다.

- 선택한 회원은 `선택한 회원 승인`·`선택한 회원 거부`로 한 번에 처리한다 (MUST, #297).
  화면은 상태로 미리 거르지 않고 고른 id 전체를 기존 승인·거부 API에 한 번만 보내며,
  대상이 아닌 회원은 서버의 항목별 실패 사유로 안내한다.
- 한 명은 행의 `…` 관리 메뉴에서 승인·거부하여 같은 확인·결과 흐름을 거친다 (MUST).
  행 안에 별도 inline 승인·거부 버튼을 두지 않는다.
- **승인**: `PENDING` → `ACTIVE`, 승인일시를 기록한다.
- **거부**: 계정은 유지하고 신청서의 학번·학과·제출 시각을 지워
  `PENDING + applied_at NULL`인 미승인 상태로 되돌린다. 같은 계정과 세션으로 다시
  신청할 수 있다. 세 신청 필드가 이미 모두 비어 있으면 멱등 성공이며 새 이력은 남기지 않는다.
- 처리 전 확인 다이얼로그를 표시하고, 처리 결과(성공/실패 건수)를 안내한다 (MUST).

## 2-2-3 회원 상태 변경

네 상태 사이의 전이는 아래가 전부다 (2026-08-26, #228에서 `INACTIVE`를 더하며 개정).

| 전이 | 어디서 | 비고 |
|---|---|---|
| `PENDING` → `ACTIVE` | 일괄 승인 ([§2-2-2](#2-2-2-가입-승인거부)) | 승인일시를 기록한다 |
| 신청 완료 `PENDING` → 미승인 `PENDING` | 일괄 거부 ([§2-2-2](#2-2-2-가입-승인거부)) | 계정은 유지하고 `student_no`·`department`·`applied_at`을 비운다 |
| `ACTIVE` ↔ `SUSPENDED` | 선택 상태 변경 (아래) | `ADMIN`을 정지하려면 먼저 `USER`로 권한을 회수한다 |
| `INACTIVE` → `ACTIVE` / `SUSPENDED` | 선택 상태 변경 (아래) | 비활동 부원을 활성화하거나 곧바로 정지한다 |
| `ACTIVE` → `INACTIVE` | **비활성화 API** (아래 절) | 본문 없으면 학기 전환 전원, id가 있으면 선택 회원 |
| `SUSPENDED` → `INACTIVE` | **선택 비활성화 API** (아래 절) | 1인 배치도 허용하며 그 배치 시각을 기록한다 |
| 어느 상태든 → *(삭제)* | 회원 제거 ([§2-2-4](#2-2-4-회원-제거)) | 지우기 전에 `SUSPENDED`를 먼저 확정한다 |
| **`SUSPENDED`를 뺀 어느 상태든 → *(삭제)*** | **본인 탈퇴** ([§2-2-4](#본인-탈퇴--같은-처리-다른-문)) | 2026-08-28, #223. 처리는 회원 제거와 같다. 정지 계정은 로그인이 막혀 이 문에 닿지 못한다 |

**표에 없는 전이는 없다** (MUST). `PENDING` → `INACTIVE`, `INACTIVE` → `PENDING`은
승인 절차를 건너뛰거나 낸 신청서를 다시 내게 하므로 금지한다. 승인된 `USER`의
`ACTIVE`·`INACTIVE`·`SUSPENDED`는 위 전용 경로를 통해 서로 나머지 두 상태로 옮길 수 있다.

**`SUSPENDED` 해제는 언제나 `ACTIVE`다** (MUST). 정지 전이 `INACTIVE`였어도 `ACTIVE`로 돌아온다 — 이전 상태를 기억하려면 열을 하나 더 두어야 하는데, 그 값을 하지 않는다. 잘못 올라온 사람은 **다음 학기 전환에서 다시 내려간다.**

**`PENDING`과 `INACTIVE`는 서로 오가지 않는다** (MUST). 승인 전 계정을 비활동으로 만들면 승인 절차를 건너뛰고, 비활동 부원을 승인 대기로 되돌리면 이미 낸 신청서를 다시 내게 된다.

> **관리자 승격은 항상 `ACTIVE ADMIN`으로 끝난다.** 최초 관리자 승격과 관리자의
> 권한 부여 모두 상태를 `ACTIVE`로 정규화한 뒤 `ADMIN`으로 바꾸며, 중간
> `INACTIVE ADMIN`/`SUSPENDED ADMIN`을 커밋하지 않는다. `PENDING`은 일반 권한 부여
> 경로의 대상이 아니다 ([§2-2-5](#2-2-5-권한-부여회수)).

### 정지·해제

- 정지된 회원은 **즉시 로그인이 차단된다** (MUST). 이미 로그인된 세션도 다음 요청에서 차단되어야 한다.
- **세션 반영에 실패하면 성공으로 답하지 않는다** (MUST, 2026-08-22, #58). 규칙과 근거는 [§2-2-5 "차단이 강해지는 변경은 세션에 닿아야 성공이다"](#차단이-강해지는-변경은-세션에-닿아야-성공이다)에 있다.
- **본인이 마지막 남은 활성 관리자일 때는 자기 자신을 `SUSPENDED`로 바꿀 수 없다** (MUST) — [§2-2-7](#2-2-7-안전장치). 정지도 권한 회수·삭제와 마찬가지로 활성 관리자를 0명으로 만든다.
- **`ADMIN`은 바로 정지할 수 없다** (MUST, 2026-08-30, #296). 자기 자신인지, 활성
  관리자가 몇 명인지, 대상 상태가 무엇인지와 무관하다. 먼저 권한을 `USER`로 회수한 뒤
  별도 정지 요청을 해야 권한 회수와 이용 차단의 이력·세션 효과가 섞이지 않는다. 거절은
  `403 FORBIDDEN`이고 권한 회수를 먼저 하라는 사유를 돌려준다.
- 권한 회수와 정지는 서로 다른 결정이며 `REVOKE_ADMIN`과 `SUSPEND` 이력·세션 반영을
  각각 남긴다. 회원 제거·본인 탈퇴의 내부 선행 정지는 접근 차단을 위한 예외다.
- **기존 `PATCH /admin/users/{id}/status`는 `INACTIVE`를 받지 않는다** (MUST).
  행 단건 조작도 선택 API에 `[user.id]`를 보내며, `SUSPENDED` → `INACTIVE`는
  선택 비활성화 API만 책임진다. 하위 호환 단건 endpoint를 불필요하게 넓히지 않는다.

### 회원 목록의 선택 상태 조작

선택 요약 오른쪽에는 같은 디자인과 순서로 아래 다섯 버튼만 항상 둔다 (MUST, #297).

1. `선택한 회원 승인`
2. `선택한 회원 거부`
3. `선택한 회원 활성화`
4. `선택한 회원 비활성화`
5. `선택한 회원 정지`

선택이 없거나 다섯 요청 중 하나가 진행 중이면 모두 잠기고, 응답 대기 중에는 행·헤더
체크박스도 잠궈 대상을 추가하지 못하게 한다. 승인·거부는 선택 id를 기존 전용 API에 보내고
서버의 처리·실패 배열을 그대로 안내한다. 활성화는 신청 완료 `PENDING`의 승인, `INACTIVE`
복구, `SUSPENDED` 해제와 이미 `ACTIVE`인 멱등 처리를 한 요청으로 다룬다.
비활성화는 선택한 `ACTIVE`/`SUSPENDED USER`를 `INACTIVE`로 바꾸며 다른 조합을 실패
결과로 남긴다.
정지는 허용된 `USER`를 `SUSPENDED`로 바꾸고, `ADMIN`과 `PENDING`은 실패 결과로 남긴다.

확인 실행을 누른 순간에는 React가 다시 그려지기 전에도 동기 잠금을 잡아 같은 요청을 두 번
보내지 않는다 (MUST). 선택 승인·거부·상태 조작과 행 단건 상태 조작이 잠금을 공유하며,
요청 중에는 확인 창의 실행 버튼과 위 다섯 버튼을 모두 잠근다.

다섯 조작은 모두 실행 전에 대상 수·이름·상태별 실패 가능성을 확인 창으로 보여준다 (MUST).
응답의 처리·실패 배열과 사유 순서를 그대로 요약하고 목록을 다시 조회한다. 세션 반영 실패로
`500`이 나도 DB 변경은 남을 수 있으므로 "아무것도 바뀌지 않았다"고 단정하지 않고, 다시
불러온 상태를 확인해 대상을 다시 선택하고 재시도하도록 안내한다.

### 회원 행 관리 메뉴 (#324)

행 관리 메뉴는 비모달로 열어 `body` scroll lock이나 scrollbar 보정 폭을 추가하지
않는다 (MUST). 반복해 열고 닫아도 페이지 가로 위치가 바뀌지 않아야 하며, `Escape`로
닫으면 포커스는 해당 행의 `⋯` 트리거로 돌아온다.

행 메뉴는 현재 상태로 이미 도달한 조작을 보이지 않는다. 승인 전 계정을 영구 삭제하는
경로는 신청 거부와 구분한다. 신청 완료 `PENDING USER`는 `승인` → `거부` → 구분선 →
destructive `제거`, 신청 전 `PENDING USER`는 destructive `제거`만 보인다 (MUST).
`PENDING` 분기를 권한보다 먼저 적용하며 유일한 항목 앞에는 구분선을 두지 않는다.
나머지 `USER`의 메뉴는 아래 순서를 지키고, 상태 조작 뒤에 `관리자 지정`, 구분선,
destructive `제거`를 둔다 (MUST).

| 현재 상태·권한 | 행 메뉴 |
|---|---|
| 신청 완료 `PENDING USER` | `승인` → `거부` → `제거` (제거 앞 구분선) |
| 신청 전 `PENDING USER` | `제거`만 노출, 구분선 없음 |
| `ACTIVE USER` | `비활성화` → `정지` → `관리자 지정` → `제거` |
| `INACTIVE USER` | `활성화` → `정지` → `관리자 지정` → `제거` |
| `SUSPENDED USER` | `활성화` → `비활성화` → `관리자 지정` → `제거` |
| `ADMIN` | `권한 회수`만 노출 |

활성화·정지는 선택 상태 변경 API에 `[user.id]`를 보내고, 비활성화는 선택 비활성화
API에 `[user.id]`를 보낸다. `정지 해제`라는 별도 표현은 쓰지 않고 `활성화`로 통일한다.
`INACTIVE`/`SUSPENDED USER`의 관리자 지정 확인 창은 **활성 관리자로 전환**된다는 최종
결과를 명확히 말한다. 신청 완료 `PENDING`의 승인·거부 확인·결과 흐름은 메뉴에서도
유지하고, 두 `PENDING` 메뉴에는 상태 변경·관리자 지정·권한 회수를 노출하지 않는다.

### 선택 회원 일괄 활성화·정지

*(2026-08-30, #313.)*

**프론트엔드가 단건 `PATCH`를 여러 번 병렬로 부르지 않는다** (MUST). 선택 id와 목표 상태 `ACTIVE` 또는 `SUSPENDED`를 한 요청으로 보내야, 요청자와 모든 대상을 한 잠금 순서로 판단하고 일부 성공을 한 트랜잭션에 커밋할 수 있다.

| 목표 | 잠금 후 대상 | 결과 | 이력 |
|---|---|---|---|
| `ACTIVE` | 신청서를 낸 `PENDING` | 승인, `approved_at` 기록 | `APPROVE` |
| `ACTIVE` | 미신청 `PENDING` | 항목 실패 `NOT_APPLIED` | 없음 |
| `ACTIVE` | `INACTIVE` | 학기 복구, `deactivated_at=NULL` | `REACTIVATE` |
| `ACTIVE` | `SUSPENDED` | 정지 해제. 정지 전 상태와 무관하게 `ACTIVE` | `ACTIVATE` |
| `ACTIVE` | `ACTIVE` | 멱등 성공 | 없음 |
| `SUSPENDED` | `USER` `ACTIVE`/`INACTIVE` | 정지, `deactivated_at=NULL` | `SUSPEND` |
| `SUSPENDED` | `USER` `SUSPENDED` | 멱등 성공 | 없음 |
| `SUSPENDED` | 모든 `PENDING` | 항목 실패 `PENDING_NOT_ALLOWED` | 없음 |
| `SUSPENDED` | 모든 `ADMIN` | 항목 실패 `ADMIN_SUSPEND_REQUIRES_ROLE_REVOCATION` | 없음 |

**`ADMIN` 정지 정책이 멱등보다 먼저다** (MUST). 과거 데이터의 `ADMIN`/`SUSPENDED`도 일괄 정지에서 성공으로 돌리지 않고 권한 회수를 요구한다. 단건 `PATCH`는 계속 `403 FORBIDDEN`이고, 일괄은 혼합 부분 성공을 지키기 위해 `200` 항목 실패로 돌린다. 권한을 `USER`로 회수한 **별도 요청 뒤** 정지할 수 있다.

**응답의 성공은 멱등을 포함한다** (MUST). 이미 목표 상태인 id도 `processed`에 담아 같은 요청을 세션 반영 실패의 복구 수단으로 쓴다. 실패와 멱등은 조작 이력을 남기지 않고, **실제 성공 전이만** 대상별 한 행을 남긴다. 한 요청의 모든 성공 전이는 잠금 안에서 잡은 같은 `occurredAt`을 쓰고, 응답은 첫 등장 상대 순서이지만 이력 저장은 target id 오름차순이다.

**세션 반영 집합은 `processed` 전체다** (MUST). `ACTIVE`는 완화 변경이므로 모든 id를 끝까지 시도하고 실패를 기록하되 `200`을 유지한다. `SUSPENDED`는 차단 강화라 끝까지 시도한 뒤 하나라도 실패하면 `500 INTERNAL_ERROR`다. **상태와 성공 이력은 되돌리지 않고**, 같은 요청을 다시 보내 이미 정지된 `USER`의 세션도 복구한다.

### 학기 전환 — 일괄 비활성화와 복구

*(2026-08-26, #228. 2026-08-30, #295에서 선택 경로 추가.)*

**학기가 바뀌면 관리자가 일반 부원을 한 번에 내리고, 이번 학기에 활동하는 사람만 다시 올린다.** 비활성화는 전원과 선택 두 모드를 지원하고, 복구는 선택만 지원한다.

| | 대상을 고르는 방법 | 왜 |
|---|---|---|
| **비활성화 — 기본** | **조건이다.** 본문 없이 `ACTIVE`인 일반 부원 **전원** | 학기 전환의 기본은 전원이다. 페이지마다 나눠 체크하게 하면 **한 페이지를 빠뜨려도 아무도 모른다** |
| **비활성화 — 선택** | **id 목록이다.** 관리자가 명단에서 고른다 | 학기 중 일부 회원만 내리는 운영도 필요하다. 개별 `PATCH`에 `INACTIVE`를 열지 않고 같은 학기 전환 규칙을 적용한다 |
| **복구** | **id 목록이다.** 관리자가 명단에서 고른다 | 올라올 사람은 매번 다르다. 조건으로 전원을 올리면 비활성화가 무의미해진다 |

본문 없음·JSON 최상위 `null`·`userIds` 누락·`null`·빈 배열은 모두 **기존 전원 경로와 정확히 같다** (MUST). 선택 경로는 `userIds`가 하나 이상일 때만 시작하며 최대 100개, 양수 id만 받는다. 중복 id는 **첫 등장만 남겨** 처리와 성공·실패 응답 순서를 유지하고, 교착 방지를 위한 행 잠금만 id 오름차순으로 수행한다. 이력은 기존 규칙대로 id순으로 결정적으로 기록하되 변경 대상마다 한 행만 남긴다.

**대상에서 빼는 것** (MUST):

- **`ADMIN`.** 운영자가 자기 손으로 자기 자료 접근을 끊는다.
- **`SUSPENDED`.** 학기 전환이 제재를 일괄로 해제하지 않게 전원 경로에서는 뺀다.
- **`PENDING`.** 승인 절차를 건너뛴다.

선택 경로는 `ACTIVE`/`SUSPENDED USER`를 받는다. 정지 회원을 고르는 것은 정지를
비활동으로 바꾸려는 명시적인 관리자 의도이므로 허용한다. 한 명을 고른 경우도 하나의
배치이며, `deactivated_at`은 그 배치의 시각이다. 따라서 그 한 명이 가장 최근 복구 후보가
되는 것은 의도된 정책이다.

본문 없는 전원 경로는 기존 호출자를 위한 **하위 호환 API 계약일 뿐 현재 화면 계약이 아니다.**
#297의 현재 회원 관리 화면에는 이 전원 경로 버튼이나 복구 전용 버튼을 두지 않는다 (MUST).
화면의 일괄 조작은 앞 절의
`선택한 회원 승인`·`선택한 회원 거부`·`선택한 회원 활성화`·`선택한 회원 비활성화`·
`선택한 회원 정지` 다섯 버튼뿐이며, 선택 비활성화는
목록에서 대상 수와 이름을 직접 보여준다. 전원 경로를 제공하는 별도 운영 도구가 있다면 실행
전에 `GET /admin/users?status=ACTIVE&role=USER&size=1`로 얻은 대상 건수를 보여줘야 한다.

> **그 건수는 확인 창을 여는 시점의 참고치이지 실행의 조건이 아니다.** 그 사이 누가 가입 승인을 받아 늘어나도 비활성화는 그대로 진행한다. 제거 확인 창의 콘텐츠 건수와 같은 규약이다 ([§2-2-4](#제거-전에-확인한다)).

**바뀐 회원의 id를 응답에 담는다** (MUST). `deactivated`는 두 경로 모두 실제로 바뀐 id뿐이다. 선택 경로는 바꾸지 못한 id를 `failed: [{ userId, reason }]`으로 함께 돌려주며, `reason`은 없는 계정의 `NOT_FOUND`와 비활성화할 수 없는 계정의 `NOT_ACTIVE_USER` 둘이다. 관리자·승인 대기·이미 비활동인 계정은 후자로 보호하고, 명시적으로 고른 `SUSPENDED USER`는 비활성화한다. 일부 실패도 전체 응답은 `200`이고 성공한 변경을 되돌리지 않는다.

전원 경로의 응답은 기존 `{"deactivated": [...]}` 모양을 유지하며 `failed` 필드도 더하지 않는다 (MUST). 본문 없는 기존 클라이언트의 요청·응답 호환을 함께 지키기 위해서다.

> **되돌릴 근거는 응답이 아니라 데이터다** (MUST, 2026-08-28 리뷰). 응답은 잃을 수 있다 — 아래 세션 반영 규칙 때문에 **상태는 바뀌었는데 응답은 `500`인 경우**가 있고, 브라우저가 닫히거나 연결이 끊기기도 한다. 재요청은 "이미 전원 `INACTIVE`"라 빈 목록을 돌려주므로, 그 뒤로는 **원래 비활동이던 사람과 방금 내려간 사람을 영영 가르지 못한다.** 그래서 **내려간 시각을 계정에 남긴다**(`deactivated_at`) — 상태 변경과 같은 트랜잭션이라 실패해도 남고, 한 배치가 같은 값을 가져 "직전 배치"를 그대로 고를 수 있다. **이력은 이 자리를 대신하지 못한다**: 이력은 세션 반영보다 뒤에 남기고 실패를 삼키므로([§2-2-7](#2-2-7-안전장치) MUST) 정확히 그 실패 경로에서 비어 있다. 계약은 [3-2 §3-2-6](3-2-DESIGN-CONTRACT.md#학기-전환--일괄-비활성화복구-2026-08-26-확정-228)에 있다.

**회원 목록이 `INACTIVE`를 구분해 보여주고 필터로 추릴 수 있어야 한다** (MUST, 2026-08-28 리뷰). 복구는 id 목록을 받는데, 화면에서 비활동 회원을 **찾을 수도 고를 수도 없으면 전원을 내린 뒤 아무도 다시 올릴 수 없다** — API만 있고 누를 곳이 없는 상태가 된다. 상태 칸이 `INACTIVE`를 `SUSPENDED`와 같은 낱말로 보여주는 것도 안 된다: 관리자가 **정지된 사람을 복구하려다 실패하고** 비활동인 사람을 정지로 오해한다.

**되돌리는 길은 복구 하나뿐이다** (MUST). 비활성화에 별도의 취소를 두지 않는다 — 복구가 이미 그 일을 하고, 두 벌을 만들면 한쪽만 고쳐진다.

**비활성화는 차단이 강해지는 변경이다.** 세션 반영에 실패하면 성공으로 답하지 않는다 ([§2-2-5](#차단이-강해지는-변경은-세션에-닿아야-성공이다) MUST). 복구는 완화되는 변경이라 그 규칙의 대상이 아니다.

> **재요청이 복구 수단이려면 대상 조건이 넓어야 한다** (MUST). 위 규칙은 "같은 요청을 다시 보내는 것이 복구 수단"에 기대는데, 이미 `INACTIVE`가 된 사람을 빼면 세션이 영영 낡은 채 남는다. 그래서 본문 없는 전원 경로의 세션 반영은 `ACTIVE`와 `INACTIVE USER` 전원에게 한다. 선택 경로는 고른 id 중 `ACTIVE`·`SUSPENDED`·`INACTIVE USER`에게 반영하고, 상태·이력은 실제로 `ACTIVE`/`SUSPENDED` → `INACTIVE`가 된 대상만 남긴다 ([§2-2-7](#조작-이력)).

**비활성화·복구도 이력에 남긴다** ([§2-2-7](#조작-이력)). 대상마다 한 행이고, 두 방향을 가른다 — 뭉치면 이력을 읽어도 내려간 것인지 올라온 것인지 알 수 없다. **학기마다 전원이 대상이라 행이 많이 쌓이는데, 그것이 이 이력의 목적이다** — "저는 지난 학기에 활동했는데 왜 자료가 안 보이나요"에 답할 수 있어야 한다.

## 2-2-4 회원 제거

- 계정을 삭제한다.

### 남긴 것을 어떻게 하는가

**그 사람이 올린 것은 남기고, 그 사람만의 것은 지운다.**

| 남긴 것 | 처리 | 왜 |
|---|---|---|
| 자료(`notes`)와 딸린 파일 | **유지**, 업로더 표시를 "탈퇴한 회원"으로 | 다른 부원이 참조하던 정리본이다 |
| 공지(`notices`) | **유지**, 작성자 표시를 "탈퇴한 회원"으로 | 공지는 동아리의 기록이지 개인의 것이 아니다 |
| 활동사진(`photos`) | **유지**, 업로더 표시를 "탈퇴한 회원"으로 | 아카이브다 |
| 게시글(`posts`) | **유지**, 작성자 표시를 "탈퇴한 회원"으로 | 오간 이야기가 한쪽만 사라지면 남은 글이 맥락을 잃는다 |
| 즐겨찾기(`bookmarks`) | **함께 삭제** | 그 사람만 보던 목록이라 남길 이유가 없다 |

**자료 공유가 이 사이트의 존재 이유다** ([2-1 §2-1-2](2-1-USER-STORIES.md#2-1-2-자료-업로드)). 올린 사람이 나갔다는 이유로 시험 정리본이 사라지면 손해를 보는 것은 남은 부원이다.

**이것은 익명화가 아니다.** 지우는 것은 **작성자 표시**까지다 — 자료 본문·파일 이름·공지 내용·게시글 내용·사진 자체에 이름이나 학번, 얼굴이 담겨 있으면 그대로 남고, 그것만으로 누구인지 알아볼 수 있다. 그래서 개인정보처리방침이 **"표시만 바뀐다"는 범위를 그대로 고지한다.** 콘텐츠 안에 담긴 개인정보는 **자동으로 판별할 수 없으므로** 요청이 오면 운영자가 [§2-2-6](#2-2-6-콘텐츠-관리)의 권한으로 개별 처리한다.

### 제거 전에 확인한다

**제거는 관리자가 혼자 시작할 수 있다.** 사전 통지가 없고, [본인 탈퇴](#본인-탈퇴--같은-처리-다른-문)가 생긴 뒤에도 그것을 기다려 주지 않는다. 그래서 *"본인이 미리 지우면 된다"* 는 전제는 성립하지 않는다 — **관리자가 먼저 지우면 그 사람은 다시 로그인할 수 없어 손댈 방법이 없다.**

작성자 관계가 끊기고 나면 **운영자도 그 회원의 콘텐츠를 찾을 수 없다.** `uploader_id`가 `NULL`이 된 뒤에는 "탈퇴한 회원" 여럿의 자료가 구분되지 않으므로, 사후 삭제 요청은 제목을 기억해 내는 것 말고는 처리할 길이 없다.

그래서 **제거 확인 창은 그 회원이 남길 콘텐츠의 건수를 보여준다** (MUST) — 자료·공지·활동사진·게시글 각각. 관리자는 그것을 보고 **관계를 끊기 전에** 지울지 남길지 정한다. 건수를 보여주지 않으면 무엇이 남는지 모르는 채로 되돌릴 수 없는 조작을 하게 된다.

> 되돌릴 수 없는 조작에 확인 창을 붙이는 것은 [§2-2-2](#2-2-2-가입-승인거부)·[§2-2-3](#2-2-3-회원-상태-변경)과 같은 규칙이다. 제거만 **무엇이 남는지까지** 보여주는 것은, 제거가 그 뒤로 되돌아갈 수단을 없애는 유일한 조작이기 때문이다.

### 어떻게 보장하는가

작성자를 가리키는 FK는 **`ON DELETE SET NULL`이어야 한다** (MUST) — `notes.uploader_id`, `notices.author_id`, `photos.uploader_id`, `posts.author_id`. `bookmarks.user_id`만 `ON DELETE CASCADE`다.

**DB가 정책을 지키게 한다.** 애플리케이션이 삭제 전에 일일이 `NULL`로 바꾸는 방식은, 한 곳만 빠뜨려도 회원 삭제가 FK 위반으로 막힌다. 기본값(`NO ACTION`)을 그대로 두면 **자료를 한 번이라도 올린 회원은 삭제할 수 없다** — "자료를 유지한다"는 이 정책과 DB가 정반대로 동작하는 셈이다.

**"탈퇴한 회원" 문구는 응답을 만들 때 채운다** (MUST). 작성자 id가 `NULL`이면 그 자리에 넣는다. 필드 이름과 직렬화 규칙은 [3-2 §3-2-2](3-2-DESIGN-CONTRACT.md#3-2-2-테이블-정의)에 있다. 삭제 시점에 이름을 다른 컬럼으로 복사해 두는 방식은 **계정을 지운 뒤에도 개인정보를 남기는 것**이라 쓰지 않는다.

### 로그인 중인 회원을 지우면

**대상의 세션을 모두 폐기한다** (MUST). `users` 행만 지우는 것으로는 접근이 끊기지 않는다.

인가 상태는 세션에 들어 있고([3-3 결정 12](3-3-DESIGN-DECISIONS.md#3-3-13-결정-12--인증은-jwt-인가-상태는-서버-세션으로-나눈다)), 매 요청마다 `users`를 읽지 않는다. 세션 테이블에는 `users`를 가리키는 FK도 없다. 그래서 세션을 따로 지우지 않으면 **계정이 사라진 사람이 만료(30분)까지 `ACTIVE`나 `ADMIN`으로 보호 API를 계속 부른다.**

정지도 **즉시 차단**을 요구한다([§2-2-3](#2-2-3-회원-상태-변경) MUST). 제거는 정지보다 강한 조작이므로 더 느슨할 수 없다.

**정지와 달리 세션을 갱신하지 않고 지운다.** 갱신하려면 `role`·`status`를 써넣어야 하는데 지울 계정에는 그럴 값이 없다. 세션이 사라지므로 대상의 다음 요청은 `403`이 아니라 **`401 UNAUTHENTICATED`** 다.

**"지금 있는 세션을 모두 지운다"로는 부족하다** (MUST). 로그인 요청이 계정을 읽은 뒤 세션이 아직 저장되기 전이면, 폐기하는 쪽에서는 **그 세션이 보이지 않는다.** 잠시 뒤 저장되고 나면 계정은 없는데 세션은 `ACTIVE`나 `ADMIN`으로 남는다.

승인·정지에도 같은 창이 있지만([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md)) 그쪽은 **재로그인이 회복 수단이다.** 제거에는 **돌아갈 계정이 없어 아무것도 되돌리지 못한다.** 그래서 회원 제거는 그 창을 닫은 뒤에 구현한다 ([#127](https://github.com/HackerKHU/hacker_HP/issues/127)).

**"저장하고 다시 읽는다"만으로는 닫히지 않는다** (MUST). 재조회와 삭제가 서로를 막지 않으면 이렇게 어긋난다.

```
삭제  ── 세션 조회(없음) ────────────────── 행 삭제·커밋 ──
로그인 ──────── 세션 저장 ── 계정 재조회(있음) ───────────
```

새 세션은 폐기 대상에서 빠지고 재조회는 아직 살아 있는 계정을 본다. **둘 다 통과하는데 결과는 계정 없는 `ADMIN` 세션이다.**

**계정 행 잠금으로 둘을 한 줄로 세운다** (MUST). 이 저장소에는 이미 그 규칙이 있다 ([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md)) — 여기서는 순서까지 정한다.

- **로그인은 계정 행을 잠근 채 읽고, 세션이 저장소에 들어가는 것까지 그 잠금 안에서 끝낸다** ([3-1 §3-1-5](3-1-DESIGN-ARCHITECTURE.md)). 계정이 없으면 세션을 만들지 않고 로그인을 실패시킨다.
- **삭제는 계정 행을 잠근 채** 지우고, **세션 폐기는 커밋한 뒤에** 한다.

그러면 어느 쪽이 먼저 잠그든 결과가 하나다. 로그인이 먼저면 **세션은 이미 저장된 뒤**라 삭제의 폐기가 반드시 본다. 삭제가 먼저면 로그인이 **사라진 계정을 보고** 세션을 만들지 않는다.

### 제거는 정지를 먼저 확정한다

> **본인을 지울 때는 요청자를 다시 확인하지 않는다** (2026-08-22, #58). 정지가 방금 그 사람을 `SUSPENDED`로 만들었으므로, 삭제 단계에서 "요청자는 활성 관리자여야 한다"를 다시 보면 **자기 손으로 만든 상태에 걸려 본인 제거가 영영 실패한다.** 인가가 느슨해지는 것은 아니다 — 정지 단계가 같은 검사와 마지막 활성 관리자 검사를 이미 통과했고, 실패하면 삭제까지 오지 못한다.

**계정을 지우기 전에 `SUSPENDED`로 만들고 그 반영까지 끝낸다** (MUST). 그 뒤에 지운다.

세션 폐기는 계정이 사라진 **뒤에** 일어나므로 실패할 수 있고, **실패해도 되돌릴 방법이 없다.** 계정이 이미 없으니 트랜잭션을 물릴 수도, 같은 요청을 다시 보내 복구할 수도 없다 — 그러면 `ACTIVE`나 `ADMIN` 세션이 만료까지 그대로 인증에 쓰인다.

정지를 먼저 확정하면 **어느 지점에서 실패하든 그 사람은 이미 막혀 있다.**

| 어디서 실패하나 | 남는 상태 | 결과 |
|---|---|---|
| 정지 반영 | 계정이 `SUSPENDED`로 남는다 | 이미 차단됨. **같은 요청을 다시 보내 복구한다** |
| 삭제 | 계정이 `SUSPENDED`로 남는다 | 이미 차단됨. 재요청으로 복구한다 |
| 세션 폐기 | 계정은 없고 세션만 남는다 | 그 세션은 **`SUSPENDED`라 `403`으로 막힌다** |

정지 경로는 이미 즉시 차단이 보장된다([§2-2-3](#2-2-3-회원-상태-변경) MUST) — 새 장치를 만드는 것이 아니라 **검증된 차단을 앞에 세우는 것**이다.

**정지 반영이 실제로 끝났는지 확인하고 나서 지운다** (MUST, 2026-08-22, #58). 세션 반영은 실패를 삼키는 경로다 — 이미 커밋된 상태 변경까지 실패한 것처럼 보이면 안 되기 때문인데, **그 관용이 제거에서는 위험하다.** 조용히 실패한 채로 계정을 지우면 그 세션은 `ACTIVE`·`ADMIN`인 채 남고 되돌릴 계정이 없다. 확인에 실패하면 지우지 않고 멈춘다 — 대상은 `SUSPENDED`로 남아 재요청으로 복구된다.

**지우기 직전에 그 사람이 아직 막혀 있는지 다시 본다** (MUST, 2026-08-22, #58). 정지는 커밋되며 잠금을 놓으므로, 그 사이에 다른 관리자가 대상을 다시 `ACTIVE`로 돌릴 수 있다. 그러면 세션도 함께 되살아나 **"정지가 먼저 확정된다"는 전제가 무너진 채 계정만 사라진다.** 대상이 `ACTIVE`면 지우지 않고 **`409 CONCURRENT_CHANGE`** 로 멈춘다([3-2 §3-2-7](3-2-DESIGN-CONTRACT.md#3-2-7-공통-에러-코드)) — 다른 관리자가 의도를 갖고 되살린 상태이므로 여기서 조용히 다시 정지시키지 않고 관리자에게 되돌려 판단하게 한다.

이 검사가 **마지막 활성 관리자 보호도 함께 한다**([§2-2-7](#2-2-7-안전장치)). 활성이 아닌 계정은 활성 관리자로 세지 않으므로, 여기를 통과한 대상을 지워도 그 수는 줄지 않는다. 정지 단계에서 이미 같은 검사가 걸리므로 삭제 단계에서 수를 다시 셀 필요가 없다.

### 본인을 지우면 지금 요청의 세션도 함께 끝낸다

활성 관리자가 둘 이상이면 **자기 자신도 지울 수 있다** ([§2-2-7](#2-2-7-안전장치)). 이때는 **저장소에서 세션 행을 지우는 것만으로 부족하다** (MUST).

지금 요청에 붙어 있는 세션은 응답을 내보낼 때 **다시 저장된다.** 방금 지운 `ADMIN` 세션이 되살아나 만료까지 살아남는다.

그래서 본인 제거는 **현재 세션을 무효화하고 신원 토큰 쿠키까지 지운다** (MUST). 로그아웃과 같은 처리다 — 계정이 사라졌으므로 로그아웃보다 덜할 수 없다.

> **가입 거부([§2-2-2](#2-2-2-가입-승인거부))는 계정 제거 규칙을 밟지 않는다.**
> 거부 전후의 인가 값은 모두 `USER/PENDING`이고 계정도 같은 id로 남는다. 세션을
> 폐기하거나 갱신하지 않아야 그 세션으로 신청 폼을 다시 열어 같은 계정에 재신청할 수 있다.
> 신청서에서 받은 학번·학과·제출 시각만 지우고, 실제 신청을 초기화한 때만 `REJECT` 이력을
> 한 행 남긴다.

### 본인 탈퇴 — 같은 처리, 다른 문

*(2026-08-28 확정, [#223](https://github.com/HackerKHU/hacker_HP/issues/223). 경로는 `DELETE /auth/me`이고 요구사항 원본은 [2-1 §2-1-9](2-1-USER-STORIES.md#2-1-9-마이페이지)다.)*

**처리는 이 §2-2-4 전부와 같다** (MUST). 남기는 것과 지우는 것, `ON DELETE SET NULL`, "탈퇴한 회원" 문구, 세션 폐기, 정지를 먼저 확정하는 순서, 지우기 직전의 재확인, 마지막 활성 관리자 보호 — **여기서 다시 정의하지 않는다.** 두 벌이 되면 한쪽만 고쳐지고, 그 한쪽이 계정을 지우는 경로다.

다른 점은 셋뿐이다.

- **요청자와 대상이 언제나 같다.** 그래서 위의 *"본인을 지울 때는 요청자를 다시 확인하지 않는다"* 와 *"현재 세션과 신원 토큰 쿠키를 함께 버린다"* 가 예외가 아니라 **이 경로의 기본**이다. 다만 **지우기 직전의 `409 CONCURRENT_CHANGE` 검사는 그대로 살아 있다** (MUST, 2026-08-28 리뷰) — 그 검사의 근거는 *누가 되살렸는가*가 아니라 **차단이 먼저 확정되어야 한다**는 것이라, 문이 달라져도 사라지지 않는다.
- **확인 창의 건수가 여기서 더 쓸모 있다.** 관리자는 건수를 보고 **지울지 남길지 정할 뿐**이지만, 본인은 **창을 닫고 직접 지운 뒤 다시 올 수 있다.** 그래서 이 경로에서도 건수 표시는 MUST다.
- **`PENDING`도 부를 수 있다** (MUST). 가입 거부는 같은 계정을 미승인으로 되돌리는
  조작이고, 본인 탈퇴는 계정 자체를 지우는 별도 조작이다. 이 문을 닫으면 신청서를 내지
  않은 계정을 **본인이 지울 방법이 없다** — 관리자 제거는 그대로 되지만 승인 목록에
  뜨지 않아 눈에 띄지 않는다 ([3-1 §3-1-2](3-1-DESIGN-ARCHITECTURE.md#3-1-2-status)).
  **그 갈래는 정지를 건너뛴다** (MUST, 2026-08-28 리뷰) — `PENDING → SUSPENDED`는
  [§2-2-3](#2-2-3-회원-상태-변경)에 없는 전이라 밟으려 하면 탈퇴가 그 자리에서 실패한다.
  회원 제거가 이미 같은 예외를 두고 있다. **세션 반영 확인은 그래도 한다.**

**이력에는 `WITHDRAW`로 남긴다** (MUST). `REMOVE`와 뭉치지 않는다 — 계정이 사라진 뒤 남는 것은 숫자 id뿐이라([§2-2-7](#2-2-7-안전장치)) 두 값을 합치면 **"관리자가 지웠다"와 "본인이 나갔다"를 영영 가를 수 없다.** *"저는 탈퇴한 적 없는데 계정이 사라졌다"* 가 이 이력이 답해야 할 바로 그 질문이고, 부여와 회수를 가른 것과 같은 이유다. `actor_id`와 `target_id`는 같은 값이며, 그 조합은 최초 관리자 승격에 이미 있다.

**정지만 남고 끝나면 관리자가 이어받는다** (MUST, 2026-08-28 리뷰). 정지가 커밋된 뒤 세션 반영이나 삭제가 실패하면 계정은 `SUSPENDED`로 남는데, **본인은 로그인과 API 접근을 함께 잃어 재시도할 수 없다** — 관리자 제거의 *"같은 요청을 다시 보내 복구한다"* 가 여기서는 성립하지 않는다. 그 계정은 회원 목록에 `SUSPENDED`로 그대로 보이므로 관리자가 **제거해 완결하거나 해제해 되돌린다.** `SUSPENDED`에게 탈퇴를 열어 이어가게 하지는 않는다 — 그러면 정지된 사람이 탈퇴 후 재가입으로 정지를 지운다. **서버 로그에 대상 id를 남겨** 운영자가 알아볼 수 있게 한다: 겉보기에는 관리자가 정지시킨 계정과 구별되지 않는다.

> **관리자가 자기 자신을 제거하는 것과 다르다.** 그쪽은 `DELETE /admin/users/{id}`로 들어와 `REMOVE`로 남는다 — 관리 화면에서 한 조작이기 때문이다. 같은 사람이 같은 계정을 지워도 **어느 문으로 들어왔는지가 기록에 남아야** 나중에 읽을 수 있다.

## 2-2-5 권한 부여·회수

- `USER` ↔ `ADMIN` 전환
- `ACTIVE`/`INACTIVE`/`SUSPENDED USER`에게 `ADMIN`을 요청하면 **한 트랜잭션에서
  `ACTIVE ADMIN`으로 정규화한다** (MUST). `deactivated_at`은 `NULL`이며 중간
  `INACTIVE ADMIN`/`SUSPENDED ADMIN`을 커밋하거나 세션에 반영하지 않는다.
- `ADMIN`을 `USER`로 회수하면 `ACTIVE USER`로 남는다. 최종 `ADMIN`의 상태는
  `ACTIVE`만 허용하므로 회수가 별도 상태 변경을 만들지 않는다.
- **뒤집는 것이 아니라 원하는 권한을 말한다** (MUST, 2026-08-22, #58). 화면이 들고 있는 값이 낡았을 때 토글은 **의도와 반대로 바꾼다** — 상태 변경([§2-2-3](#2-2-3-회원-상태-변경))과 같은 모양이다.
- **회수는 그 사람의 기존 세션에도 즉시 반영된다** (MUST). DB만 바꾸면 권한이 회수된 관리자가 세션 만료까지 관리 화면을 계속 쓴다 ([5-TESTING T-34](5-TESTING.md#5-2-필수-테스트-사례)).
- **반영에 실패하면 성공으로 답하지 않는다** (MUST, 2026-08-22, #58). 정지도 같다 ([§2-2-3](#2-2-3-회원-상태-변경)) — 규칙과 근거는 아래 "차단이 강해지는 변경은 세션에 닿아야 성공이다"에 한 번만 적는다.
- **승인 대기 계정은 이 경로의 대상이 아니다.** 신청서 승인과 승인일시
  기록을 건너뛰 승인일시 없는 `ADMIN`을 만들지 않는다.
- 승격은 상태 정규화와 Role 변경을 하나의 원자적 조작으로 처리하고, 세션에도
  최종 `ACTIVE ADMIN`만 반영한다. 이력은 대상당 `GRANT_ADMIN` **한 행만** 남긴다.
- **부여와 회수를 이력에서 가른다** ([§2-2-7](#2-2-7-안전장치)). 하나로 뭉치면 이력을 읽어도 어느 방향인지 알 수 없다.

### 차단이 강해지는 변경은 세션에 닿아야 성공이다

*(2026-08-22, #58. 정지([§2-2-3](#2-2-3-회원-상태-변경))와 권한 회수([§2-2-5](#2-2-5-권한-부여회수))에 함께 적용된다.)*

**세션 반영에 실패하면 `200`을 돌려주지 않는다** (MUST).

세션 반영은 **실패를 삼키는 경로다.** 이미 커밋된 변경까지 실패한 것처럼 보이면 안 되기 때문인데, 차단을 강하게 만드는 변경에서는 그 관용이 위험하다. 인가는 매 요청 세션 값으로 판단하고 필터는 `users`를 다시 읽지 않으므로([3-3 결정 12](3-3-DESIGN-DECISIONS.md#3-3-13-결정-12--인증은-jwt-인가-상태는-서버-세션으로-나눈다)), 반영이 조용히 실패하면 **DB만 바뀐 채 그 사람이 만료(30분)까지 계속 쓴다.** 그 사이 응답은 `200`이라 **관리자는 차단된 줄 안다** — 그것이 이 규칙이 막는 것이다.

- **변경은 되돌리지 않는다.** 이미 커밋됐고, 되돌리면 차단이 오히려 풀린다. **같은 요청을 다시 보내는 것이 복구 수단이다** — 그래서 값이 이미 목표와 같아도 반영을 건너뛰지 않는다.
- **이력을 남긴 뒤에 실패를 알린다** ([§2-2-7](#2-2-7-안전장치)). 곧장 빠져나가면 변경은 남고 "누가 무엇을 했는지"만 사라진다.
- **완화되는 변경(정지 해제·권한 부여·승인)은 이 규칙의 대상이 아니다.** 세션에 늦게 닿아도 그 사람이 아직 못 쓰는 것뿐이라, 실패로 알리면 되레 관리자를 헷갈리게 한다.

응답 코드는 `500 INTERNAL_ERROR`다. 실제로 서버 쪽 장애이고 관리자가 할 수 있는 일은 다시 시도하는 것뿐이라, 화면이 코드로 분기할 대상이 아니다 ([5-TESTING §5-4](5-TESTING.md#5-4-오류-응답-규칙)).

## 2-2-6 콘텐츠 관리

| 대상 | 관리자가 할 수 있는 것 |
|---|---|
| 공지 | 등록, 수정, 삭제, 상단 고정 토글 |
| 활동 사진 | 다중 업로드, 삭제 |
| 자료 | 타인이 올린 자료도 수정·삭제 가능 |
| 게시글 | 상세 화면에서 완전 삭제 |

공지·사진의 동작 상세는 [2-1 §2-1-6, §2-1-7](2-1-USER-STORIES.md)에 있다.

### 게시글은 상세 화면에서 완전히 지운다

**`DELETE /api/v1/posts/{id}`가 관리자와 작성자 본인의 완전 삭제를 지원하고 게시글 상세 화면이 그 경로를 사용한다** ([3-3 결정 20](3-3-DESIGN-DECISIONS.md#3-3-21-결정-20--관리자와-작성자가-자유-게시판-글을-삭제할-수-있다), [#238](https://github.com/HackerKHU/hacker_HP/issues/238), [#278](https://github.com/HackerKHU/hacker_HP/issues/278)). 감춤이 아니라 완전 삭제이며 되돌릴 수 없다 — 개인정보처리방침이 고지하는 "삭제해 달라고 요구할 수 있다"([§2-2-4](#2-2-4-회원-제거))를 이 경로가 이행한다.

삭제 진입점은 `ACTIVE ADMIN`에게 작성자 여부와 무관하게 보이고, `ACTIVE`·`INACTIVE USER`에게는 작성자 본인의 글에서만 보인다. `PENDING`·`SUSPENDED`와 탈퇴·제거되어 `author_id`가 비어 있는 글에는 본인 삭제가 성립하지 않는다. 제목과 되돌릴 수 없다는 사실을 확인 창에서 보여준 뒤 한 번만 실행한다. 성공하면 자유게시판 목록으로 이동해 결과 알림을 남기고, 4xx 확정 실패나 네트워크·5xx의 불확정 결과에서는 상세 화면을 성공처럼 떠나지 않는다.

**반대로 수정 권한은 관리자 역할이 아니라 작성자 여부로 정한다.** `PATCH /api/v1/posts/{id}`와 상세의 수정 진입점은 작성자 본인에게만 열리며, 관리자가 남의 글 내용을 임의로 바꿀 수 없다 ([3-3 결정 21](3-3-DESIGN-DECISIONS.md#3-3-22-결정-21--작성자가-자유-게시판-글을-수정할-수-있다), [#256](https://github.com/HackerKHU/hacker_HP/issues/256), [#279](https://github.com/HackerKHU/hacker_HP/issues/279)). 관리자가 자신이 작성한 글을 수정할 때도 관리자 권한이 아니라 작성자 자격으로 동작한다.

삭제 직전에는 요청자 계정과 게시글을 잠근 최신 DB 행으로 관리자 권한·상태·작성자 관계를 다시 확인한다.

## 2-2-7 안전장치

**활성 관리자(`role=ADMIN`, `status=ACTIVE`)가 0명이 되는 상황을 막는다.** 활성 관리자가 사라지면 아무도 로그인해서 시스템을 운영할 수 없다.

- **그 조작 뒤에 활성 관리자가 한 명도 남지 않으면 `403`으로 막는다** (MUST). 권한 회수와 계정 삭제, 삭제·탈퇴의 내부 선행 정지는 활성 관리자를 0명으로 만들 수 있다. 일반 상태 PATCH는 [§2-2-3](#정지해제)의 더 강한 규칙이 모든 `ADMIN` 직접 정지를 먼저 막는다.

  > **`요청자 id == 대상 id`만 검사하는 것으로는 부족하다** (2026-08-13, #31 리뷰에서 확인). 활성 관리자가 둘일 때 각자 자기 권한을 동시에 회수하거나 탈퇴하면 둘 다 옛 수를 보고 통과할 수 있다. 자기 대상 여부와 무관하게 **"이 조작 뒤에도 활성 관리자가 남는가"**를 봐야 한다. 요청자 본인이 활성 관리자라는 사실도 이 순간까지 참이라는 보장이 없다.

  안내 문구는 자기 대상과 남 대상을 가른다 — 화면이 서버 문구를 그대로 보여주므로(§2-2-1, [5-TESTING T-80](5-TESTING.md#5-2-필수-테스트-사례)) 상황에 맞아야 한다.
- 관리자가 2명 이상이면 본인 계정의 권한 회수·삭제는 허용한다. 직접 정지는 관리자 수와 무관하게 먼저 권한을 회수해야 한다([§2-2-3](#정지해제)).
- 활성 관리자 수를 셀 때는 `status=ACTIVE`인 관리자만 포함한다 (MUST). `SUSPENDED` 상태인 관리자는 로그인할 수 없어 실질적으로 시스템을 운영하지 못하므로, DB에 role만 남아있어도 안전을 보장하지 않는다.
- 검사는 서버 측에서 수행한다 (MUST). UI 비활성화만으로는 API 직접 호출을 막지 못한다.
- **활성 관리자 수 확인과 변경(권한 회수·삭제·삭제 선행 정지)은 하나의 원자적 연산으로 처리한다** (MUST). 두 관리자가 동시에 각자 자기 자신을 회수하거나 삭제하면, 카운트를 따로 읽고 따로 쓰는 구현은 둘 다 "활성 관리자 2명"을 보고 통과시켜 결과적으로 0명이 될 수 있다. 단일 트랜잭션 안에서 잠금(`SELECT ... FOR UPDATE`)을 걸거나, 카운트 조건을 변경 쿼리 자체의 `WHERE` 절에 포함시켜 확인과 변경 사이에 다른 트랜잭션이 끼어들 수 없게 한다.

### 조작 이력

**계정의 상태·가입 신청·존재를 바꾸는 조작은 모두 이력에 남긴다** (MUST). 승인·거부·정지·해제·비활성화·복구·제거·**본인 탈퇴**·권한 부여·권한 회수·최초 관리자 승격 **열하나가 전부이고**, [3-2 §3-2-2](3-2-DESIGN-CONTRACT.md#3-2-2-테이블-정의) `admin_actions.action`의 값과 하나씩 짝이 맞아야 한다 (비활성화·복구는 2026-08-26 #228, 탈퇴는 2026-08-28 #223에서 추가). 모두 되돌릴 수는 있지만 **분쟁이 생기는 조작**이라, *"나는 정지당한 적 없다"* · *"저는 지난 학기에 활동했다"* 는 말에 근거를 댈 수 있어야 한다. 로그만으로는 부족하다 — 보존 기간이 지나면 사라진다. 이미 미승인인 계정의 반복 거부는 실제 변경이 없으므로 `REJECT`를 더 쌓지 않는다.

- **대상마다 한 행이다.** 일괄 승인을 한 행으로 뭉치면 "이 사람이 언제 승인됐나"를 물을 수 없다.
- **성공한 조작만 남긴다.** 아무것도 바꾸지 않은 재요청도 남기지 않는다 — 그러면 이력을 읽는 사람이 두 번 정지된 것으로 읽는다. 거절된 시도는 별개 문제다 ([#144](https://github.com/HackerKHU/hacker_HP/issues/144)).
- **시크릿을 남기지 않는다.** 승격은 "승격했다"만 남고 무엇으로 승격했는지는 남지 않는다.
- **시각은 계정 행을 잠근 채 잡는다** (MUST). 기록하는 시점에 잡으면 커밋과 세션 반영이 끝난 뒤라, 같은 회원을 두 관리자가 잇따라 건드리면 **실제와 반대 순서로 남을 수 있다** — 이력의 목적이 "언제"인데 순서가 뒤집히면 남긴 의미가 없다. 잠금이 순서를 세워 주므로 나중에 잠근 조작이 반드시 더 나중 시각을 갖는다.

**기록은 조작의 조건이 아니다** (MUST). 남기지 못해도 승인·정지 자체는 성공한다 — 실패를 예외로 올리면 **이미 커밋된 조작까지 실패한 것처럼 보이고**, 관리자는 다시 누른다. 대신 **실패 로그에 대상 id를 남긴다** (MUST): 그 로그가 남은 유일한 단서인데 건수만 있으면 누구에게 일어난 일인지 알 수 없어 보정할 수도 없다. 그래서 **변경이 커밋된 뒤에**, 세션 반영보다 **뒤에** 남긴다. 차단이 먼저다([§2-2-3](#2-2-3-회원-상태-변경) MUST) — 이력이 늦는 건 참을 수 있지만 차단이 늦는 건 아니다.

스키마와 FK를 두지 않은 이유는 [3-2 §3-2-2](3-2-DESIGN-CONTRACT.md#3-2-2-테이블-정의) `admin_actions`에 있다.

> 조회 화면·API는 아직 없다. **기록이 먼저다** — 남기지 않은 것은 나중에 만들 수 없지만, 쌓인 기록은 언제든 읽을 수 있다.

---

> 관리자가 한 명뿐일 때 그 계정이 스스로를 강등·삭제하려는 시도는 이 §2-2-7이 막고, 직접 정지는 관리자 수와 무관하게 §2-2-3이 막는다. 그래도 다른 이유(계정 탈취, 운영 실수 등)로 마지막 관리자가 사라지면, [3-3 결정 11](3-3-DESIGN-DECISIONS.md#3-3-12-결정-11--최초-관리자는-가입-후-토큰으로-본인을-승격한다)의 `POST /auth/bootstrap-admin`이 복구 경로로도 쓰인다.
